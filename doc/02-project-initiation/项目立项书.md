## 1. 立项结论

建议立项，但必须采用分阶段策略：第一阶段做一个覆盖排程、目标、习惯、执行、开销和复盘的完整生活管理版本；各模块保持轻量，暂不投入银行接入、原生双端、复杂财务、社交和全自动 AI 代理。

在 1–2 人、主要依靠 AI 开发、每月约百元现金预算的约束下：

- 做出个人使用版和 5–20 人邀请测试版：可行。
- 做出完整的 Web/PWA 产品并进行小范围验证：可行，但预计需要 11–16 周。
- 一开始做面向公众的稳定商业产品：不建议。
- 一开始做银行同步、复杂财务管理、原生多端和社交系统：不可行或风险过高。

本项目第一阶段的目标不是证明“可以做出很多功能”，而是验证：

> 将时间安排、实际执行、生活开销和目标复盘放在同一条闭环中，是否能让用户更容易完成重要的小行动，并愿意持续使用。

## 2. 业务背景与市场判断

### 2.1 业务背景

用户通常已经拥有日历、待办、习惯、记账和备忘录工具，但这些工具记录的是不同切片：

- 日历记录应该发生什么。
- 待办记录要做什么。
- 习惯应用记录有没有打卡。
- 记账应用记录花了多少钱。
- 目标工具记录想实现什么。

这些信息缺少共同的执行和复盘层。用户因此容易遇到：计划过满、目标无法落地、习惯中断后放弃、消费与生活目标脱节等问题。

### 2.2 当前市场形势

当前市场已经存在成熟的单点和组合产品：

- Todoist 覆盖任务、重复任务、日历集成和时间块。
- Structured 主打视觉时间线和日/周/月排程。
- Tiimo 已覆盖视觉化 AI 规划、任务拆解、倒计时和心情记录。
- 滴答清单覆盖任务、日历、习惯和番茄钟。
- 钱迹主打极简、低步骤记账。
- YNAB、Monarch 等产品在预算、目标和消费管理上已经形成成熟心智。

因此，直接做“另一个待办 + 打卡 + 记账”竞争力不足。本项目的切入点必须是：

> 用较低记录负担，把计划、执行、开销和目标之间的关系呈现出来，并帮助用户做下一步调整。

### 2.3 市场判断结论

这是一个需求真实、竞争激烈、差异化难度较高的市场。适合以低成本验证产品价值，不适合在没有用户留存证据前投入大量基础设施或商业化成本。

## 3. 项目目标

### 3.1 总目标

构建一个低负担的个人生活管理系统，使用户能够：

1. 把想法和目标转成现实可行的今日行动。
2. 按时间线执行和调整计划。
3. 用极少输入记录实际完成情况和开销。
4. 通过每日/每周复盘调整生活安排。

### 3.2 第一阶段目标

第一阶段完成一个可供个人和小范围用户使用的 Web/PWA 版本，覆盖以下闭环：

```text
快速记录 → 目标/任务整理 → 今日排程 → 执行 → 记录实际情况
      ↑                                      ↓
      └──────── 每日/每周复盘与调整 ─────────┘
```

### 3.3 不属于第一阶段的目标

- 不追求成为完整的财务管理或投资产品。
- 不追求替代 Google Calendar、Outlook 或手机系统日历。
- 不追求通过游戏化、排行榜或社交压力让用户坚持。
- 不做医疗、心理或 ADHD 诊断。
- 不追求一开始支持所有平台和所有设备。
- 不追求让 AI 自动决定用户的人生安排。

## 4. 目标用户

### 4.1 首要用户

有改善生活意愿，但计划执行不稳定的个人用户：

- 经常把工作、学习、家务、锻炼和个人目标混在一起。
- 已经使用过日历、待办或记账工具，但容易中断。
- 不想学习复杂方法，希望打开应用就知道下一步做什么。
- 想知道时间和钱花到哪里，并据此做调整。

### 4.2 次要用户

需要视觉化结构和低启动成本的人，例如容易拖延、任务切换困难或对时间流逝不敏感的人。产品只提供结构化支持，不进行医疗判断或用户标签化。

### 4.3 第一阶段不重点服务的用户

- 需要复杂家庭财务、资产和投资管理的用户。
- 需要团队协作、审批和项目管理的用户。
- 需要专业健康、心理或医疗建议的用户。
- 只想使用单一记账或单一待办功能的用户。

## 5. 产品范围

### 5.1 第一阶段必须包含

| 模块 | 第一阶段范围 | 备注 |
|---|---|---|
| 今日时间线 | 固定事项、任务、预计时长、拖拽、延期、缓冲、当前事项 | 产品主入口 |
| 任务收集箱 | 快速添加想法、任务和未分类事项 | 降低输入门槛 |
| 目标管理 | 长期目标、周行动、今日行动 | 支持目标逐层落地 |
| 生活领域 | 健康、工作、财务、家务、关系、兴趣等 | 作为目标和行动的中间层 |
| 习惯与例程 | 重复任务、步骤、最低版本、完成/部分完成/跳过 | 不以连续打卡为唯一标准 |
| 执行记录 | 实际完成、部分完成、延期、跳过原因、备注 | 记录计划与现实的偏差 |
| 快速记账 | 金额、类别、日期、支付方式、备注 | 第一阶段手动录入 |
| 目标关联开销 | 将开销关联到目标、行动或生活领域 | 主要差异化能力之一 |
| 日/周复盘 | 完成情况、时长偏差、开销摘要、下一步调整 | 形成闭环 |
| 提醒 | 关键任务、例程、复盘提醒、安静时段 | 允许关闭和分级 |
| 数据管理 | 导出、导入、删除、备份、隐私设置 | 生活与财务数据必须可控 |
| Web/PWA | 手机和电脑浏览器可用，可安装到桌面 | 控制开发成本 |

### 5.2 第一阶段可选增强

这些能力可以加入，但不能阻塞核心版本：

- AI 任务拆解和自然语言添加。
- AI 生成日程建议。
- AI 将自然语言转换为开销记录。
- 心情和精力的轻量记录。
- 基础统计图表。
- 语音输入。
- 日历导入或同步。
- 多设备实时同步。
- 桌面/手机小组件。

### 5.3 第二阶段再考虑

- 银行账户和支付平台自动同步。
- 原生 iOS/Android 应用。
- 家庭、伴侣、教练或监督者共享。
- 社交挑战、排行榜和公开打卡。
- 复杂预算、负债、资产和投资管理。
- 穿戴设备接入。
- 全天候 AI 生活代理。
- 面向第三方的开放 API 和插件体系。

## 6. 产品成功标准

以下数字是本项目的内部验证目标，不是行业基准，需在测试后重新校准。

### 6.1 激活指标

- 60% 以上的测试用户在首次使用中创建一个今日行动。
- 60% 以上的测试用户完成一次“计划 → 执行 → 记录”闭环。
- 用户能够独立完成一次延期或最低版本调整。

### 6.2 使用质量指标

- 快速记录平均耗时不超过 60 秒。
- 至少 60% 的活跃测试用户每周使用 3 天以上。
- 用户能够完成任务状态记录，而不是只创建任务。
- 用户发生计划偏差时，能够重新安排或缩小任务。

### 6.3 价值验证指标

- 4 周后至少 30% 的邀请用户仍在使用核心闭环。
- 至少一半完成访谈的用户能够说出一个由记录带来的生活调整。
- 至少一半的活跃用户认为产品比单独使用待办或记账工具更容易复盘生活。
- 用户不是单纯创建更多目标，而是实际完成更多重要的小行动。

### 6.4 北极星指标

> 每周完成至少一次“基于记录做出下一步调整”的活跃用户比例。

## 7. 技术可行性评估

### 7.1 总体结论

技术上可行，且适合 AI 辅助开发。第一阶段应优先采用成熟的 Web 技术、简单的数据模型和低运维架构，不应一开始构建复杂微服务或多端原生体系。

### 7.2 推荐技术形态

| 层次 | 推荐方向 | 说明 |
|---|---|---|
| 前端 | TypeScript + React + Vite 或 Next.js | AI 代码生成资料多，适合快速迭代 |
| 应用形态 | 响应式 Web + PWA | 一套代码覆盖电脑和手机浏览器 |
| 本地数据 | IndexedDB/Dexie 或等价方案 | 支持离线记录和低成本试用 |
| 云端数据 | 小范围测试时使用托管数据库和认证服务 | 需要多设备同步时再启用 |
| AI | 服务端代理调用外部 API | 不把密钥放在前端，支持限额和审计 |
| 部署 | 静态托管 + 托管数据库 | 降低运维工作量 |
| 备份 | JSON/CSV 导出 + 数据库定期备份 | 避免用户被平台锁定 |

### 7.3 技术难度分级

| 能力 | 难度 | 判断 |
|---|---:|---|
| 任务、目标、习惯、记账 CRUD | 低 | AI 辅助开发容易实现 |
| 今日时间线与拖拽排程 | 中 | 需要处理时长、冲突、重复和移动端体验 |
| 计划与执行记录关联 | 中 | 数据模型必须从一开始设计正确 |
| 日/周复盘统计 | 中 | 统计规则要保持简单且可解释 |
| Web 提醒 | 中 | 浏览器权限、后台限制和兼容性需要测试 |
| 离线记录与同步 | 中高 | 冲突合并、重复提交和数据恢复有风险 |
| AI 任务拆解 | 中 | 技术可行，但要处理输出不稳定和成本 |
| 银行/支付同步 | 高 | 涉及供应商、权限、合规和持续维护 |
| 原生双端 | 高 | 增加发布、兼容和维护成本 |
| 多人协作与权限 | 高 | 需要更复杂的身份、权限和冲突处理 |

### 7.4 AI 使用边界

AI 可以承担：

- 代码脚手架和重复 CRUD 开发。
- 测试用例、数据迁移和文档生成。
- 自然语言任务解析。
- 任务拆解和日程建议。
- 复盘摘要和建议草稿。

AI 不应直接决定：

- 删除用户数据。
- 修改长期目标和财务记录。
- 自动发送重要提醒。
- 自动做预算、借贷、投资或健康判断。

所有 AI 结果都应可编辑、可撤销，并在发生外部 API 调用前明确告知用户发送了哪些内容。

## 8. 工期预估

### 8.1 单人主导开发

预计 12–16 周：

| 阶段 | 工期 | 主要产出 |
|---|---:|---|
| 项目准备 | 1 周 | 用户流程、数据模型、技术脚手架、开发规范 |
| 产品骨架 | 1–2 周 | 页面框架、路由、基础数据层、主题和响应式布局 |
| 核心生活数据 | 3–4 周 | 任务、目标、生活领域、习惯、例程、记账 |
| 时间线与执行闭环 | 2–3 周 | 排程、拖拽、状态、延期、计划/实际对比 |
| 复盘与提醒 | 2 周 | 日/周复盘、统计、通知和安静时段 |
| AI 增强与数据管理 | 1–2 周 | AI 代理、导出、备份、隐私控制 |
| 内测与修复 | 2–3 周 | 5–20 人邀请测试、问题修复、指标收集 |

### 8.2 两人协作

如果第二个人能稳定承担 UI、测试、数据和运营支持，可压缩到 9–12 周，但前提是：

- 不同时开发原生 App。
- 不做银行同步。
- 不做复杂多人协作。
- AI 功能只做增强，不阻塞核心版本。

## 9. 成本评估

以下是规划区间，不是供应商报价，实际费用随服务商、流量和调用量变化。

### 9.1 一次性开发成本

| 项目 | 预估 | 说明 |
|---|---:|---|
| AI 编程工具 | 已有套餐为主 | 不计入新增现金成本，但要计入使用额度和时间 |
| UI/原型工具 | 0–200 元 | 可使用开源或现有工具 |
| 域名 | 0–150 元/年 | 内测可以不购买 |
| 测试设备 | 0–1000 元 | 优先使用现有电脑和手机 |
| 外部 AI API 测试 | 0–300 元 | 通过限额、缓存和小样本控制 |

### 9.2 月度运行成本

| 阶段 | 预估 | 可支撑范围 |
|---|---:|---|
| 本地/静态原型 | 0–100 元/月 | 个人使用、无复杂同步 |
| 5–20 人内测 | 100–500 元/月 | 小量数据库、认证、日志和 AI 调用 |
| 公开测试 | 500–2000 元/月起 | 取决于用户数、同步、AI 调用和带宽 |

### 9.3 预算结论

每月约百元的预算可以支持：

- 个人使用版。
- 小范围邀请测试。
- 低频 AI 增强。
- 手动记账和本地/轻量云端数据。

每月约百元难以稳定支持：

- 大量公开用户。
- 高调用量 AI 助手。
- 银行账户同步。
- 原生 App 的持续发布和运维。

因此第一阶段必须设置 AI 调用上限、日志保留期限、数据库备份策略和用户数量上限。

## 10. 人力与职责

### 10.1 最小人力配置

**项目负责人/产品验收：用户本人**

- 确认产品取舍。
- 提供真实使用场景。
- 每周进行验收和体验反馈。
- 参与内测用户访谈。

**AI 主开发代理：Codex 或其他 AI 编程工具**

- 代码实现。
- 测试、重构和文档维护。
- 根据任务拆分逐步完成模块。

**可选第二人：体验与测试支持**

- 协助 UI 判断。
- 编写测试场景。
- 收集邀请用户反馈。
- 协助发布和数据整理。

### 10.2 用户本人最低投入

即使主要由 AI 开发，也不能完全无人参与。建议至少投入：

- 每周 2–4 小时进行产品决策和验收。
- 每周实际使用一次完整闭环。
- 每个阶段结束时集中测试。
- 参加首轮用户访谈和问题排序。

AI 可以替代大量编码工作，但不能替代产品取舍、真实体验判断和用户研究。

| 用户把工具当成压力来源 | 中 | 中高 | 恢复模式、最低版本、中性文案、可关闭提醒 | 用户反馈焦虑、羞耻或厌烦 |

## 12. 合规与隐私边界

第一阶段只处理用户主动输入的任务、目标、开销和可选心情/精力数据，不接银行、支付、医疗和穿戴设备数据。

最低要求：

- 明确隐私政策和数据用途。
- AI 调用前说明会发送哪些文本或结构化数据。
- 不在前端暴露 AI API 密钥。
- 数据库使用用户级权限隔离。
- 支持用户导出和删除数据。
- 日志中避免写入完整开销备注和敏感内容。
- 默认关闭公开分享。
- 不提供投资、借贷、医疗或心理诊断建议。

如果未来面向公众或接入账户、支付、健康数据，需要在立项前重新进行合规评估。

## 13. 项目阶段门与 Go/No-Go 决策

### Gate 0：设计完成后

继续条件：

- 核心用户流程已经确定。
- 数据模型能够表达目标、行动、计划和执行记录的关系。
- P0/P1/P2 范围冻结。
- 个人预算和 AI 调用上限明确。

### Gate 1：核心闭环完成后

继续条件：

- 用户可以在 10 分钟内创建目标、生成行动、安排时间并完成一次记录。
- 任务、习惯、开销和复盘数据不会互相割裂。
- 核心操作有基本测试。

若 AI 功能拖慢核心进度，应暂时移除 AI，只保留手动流程。

### Gate 2：邀请测试完成后

继续条件：

- 至少有一批用户完成两周以上使用。
- 用户能够描述产品带来的具体改变。
- 至少部分用户主动进行周复盘或计划调整。
- 数据丢失、隐私和成本问题可控。

若用户只使用单一功能，说明“整合式生活闭环”尚未被验证，应调整定位或缩小主线，而不是继续堆功能。

### Gate 3：公开发布前

必须重新评估：

- 运行成本。
- 数据保护和账号安全。
- 多设备同步稳定性。
- AI API 费用和服务条款。
- 用户支持、备份和故障恢复能力。

## 14. 立项后的第一批任务

1. 确定项目名称、目标用户和首轮邀请测试对象。
2. 冻结第一阶段 P0 范围，建立明确的“暂不做清单”。
3. 绘制四条核心流程：首次使用、今日排程、执行记录、周复盘。
4. 设计数据模型和本地数据存储方案。
5. 搭建 Web/PWA 技术骨架和测试框架。
6. 先实现任务、目标、时间线和执行记录闭环。
7. 再加入开销、复盘、提醒和数据导出。
8. 最后接入可选 AI，并设置调用限额。
9. 邀请 5–20 名用户进行两周以上测试。
10. 根据指标决定继续、调整、暂停或终止项目。

## 15. 最终立项建议

### 建议：立项，但限定为“可验证的完整第一阶段”

这个项目值得做的原因是：它有明确的个人痛点、可以低成本开始，也有机会通过“时间—行为—开销—目标—复盘”的连接形成差异化。

不建议盲目扩张的原因是：日程、习惯、记账和 AI 助手各自都已有成熟竞争者；如果没有真实用户留存和复盘价值证据，继续堆叠功能只会增加维护成本。

因此，项目的成功条件是：

1. 第一阶段覆盖完整生活闭环，但控制每个模块的深度。
2. 采用 Web/PWA，避免原生多端和复杂基础设施。
3. AI 作为增强功能，不让核心体验依赖 AI。
4. 先做个人和小范围邀请测试，再决定是否公开运营。
5. 把“用户是否根据记录做出生活调整”作为最重要的价值判断。

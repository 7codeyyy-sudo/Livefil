> 版本：v0.2

> 用途：按时间追加记录工程基建、工具链和协作流程中实际发生的事故、根因与恢复方法，供后续追溯和借鉴。

## 使用说明

- 本文件回答“发生了什么、为什么、怎么恢复、以后怎么防”；现行规则（“现在应该怎么做”）记录在 [开发环境规范](./开发环境规范.md)，“为什么这样决策”记录在 [工程决策记录](./工程决策记录.md)。
- 条目只追加，不删改。结论被新证据推翻时，新增一条记录并注明修正关系，旧条目保留。
- 事故分级：
  - **P1 重大事故**：发生不可逆的代码/数据/历史丢失、密钥泄漏，或影响生产/真实用户。
  - **P2 较大事故**：仓库或工具链一度不可用、同日复发，或存在明确的不可逆损失升级路径，但本次实际后果可控。
  - **P3 一般事件**：局部、瞬时、自行恢复且无复发信号的异常，仅做轻量备忘。
- 每条记录包含：状态与定级、影响评估、时间线、根因、证据、恢复方法、已落地措施、未闭环项和教训。

### 根因

两次受损是**两种不同机制**，但都源于“在隔离环境里操作 git，却没有机制边界”。实施方在事故后提交了三轮因果链复盘（命令写法 → 沙箱写入层 → git 向上发现），审查方逐环做了对照核验，结论按证据强度分层记录如下。

**第一次（18:32）——人工误删 + 并发竞争。** 连续手工删除多个同名沙箱 `.git` 后，一次删除点中了主仓 `.git`（回收站元数据：18:32:14 整件入站）；删除与正在运行的 `git stash` 并发（报错时间与 `index` 写入时间同为 18:31:46），导致对象库子树没有进入回收站。实施方陈述该时间窗内未执行任何 rm；FND-007 验收脚本的自动清理亦排除：清理路径先过 `isInside(PROBE_ROOT)` 白名单、先解联接再删除，且 18:32 前后没有脚本清理运行记录。需要诚实标注：本机存在系统级删除重定向（见下文），脚本删除同样可能进入回收站，因此“入站回收站”本身不能单独证明删除通道；第一次事故的通道结论依据的是时间线关联而非删除通道实证。

**第二次（18:51）——三轮因果链，逐环核验：**

- **① 引爆点（实施方主张，部分未获实验支持）：`git init -q -b main 2>&1 | head -3` 看似成功、嵌套仓库实际未建成。** 实施方复盘认为 `head -3` 读够即退出并关闭管道，git init 收到 SIGPIPE 半途被杀；因未开 `pipefail`，管道退出码取尾部 head 的 0，后续 `&&` 链照常执行。审查方在恢复当晚用同版本 Git for Windows 2.45.2、Git Bash 在隔离探针中对照实测（`GIT_CEILING_DIRECTORIES` 指向 probes 根）：
  - `git init -q -b main | head -3`：退出码 0/0，`.git` **正常建成**。原理上 `-q` 成功时零输出，git 不写管道就不可能收到 SIGPIPE；
  - 极端情形 `git init -b main | head -0`（不读即关管道）：退出码 0/0，`.git` 仍正常建成——本机 MSYS 运行时下 SIGPIPE 未杀死 git init；
  - 但管道退出码掩盖风险**实测成立**：`false | head -3` 的 `$?` 为 0，只有 `${PIPESTATUS[0]}` 为 1、`set -o pipefail` 时整体才为 1。
  - 结论：① 的**命令写法缺陷真实存在且必须立规**（管道尾部退出码会掩盖 init 失败，Linux 下 SIGPIPE 语义同样成立）；但“本机本次事故中 git init 被 SIGPIPE 杀死”**未获支持**，嵌套仓库缺失更可能直接由②号环节造成。实施方亦在复盘中主动标注：其读不到沙箱实现代码，该环节为行为反推。
- **② 放大器（行为实证，机制反推）：受限沙箱对 `.git` 的写入不跨命令持久、同命令内支持也不完整。** 实施方观测：同一条命令里 `git init`/`commit` 成功、`rev-parse --show-toplevel` 指向正确，下一条命令再看嵌套 `.git` 已消失（独立复现两次）；同一条命令内 commit 能建 `index.lock`，stash 建同名文件却报 ENOENT。两次受损形状一致——objects/HEAD/config/logs 都在，丢失的都是引用或目录条目（一次整件、一次 `refs/`），呈“条目层被回滚”特征而非随机损坏。该环节有行为证据但无沙箱源码佐证；“为何两次回滚落点不同（整件 vs refs/）”同样未证实，推测与命令被终止时的写入阶段有关。
- **③ 静默越界（确证）：git 按标准发现规则向上找到主仓。** 嵌套仓库缺失后，`add`/`commit`/`stash` 不报错地作用于主仓：主仓对象库中 18:51:02 的 stash 提交 `64c3bb02`/`a2d16f74`、`COMMIT_EDITMSG` 中的 `diag second`、`index` 时间戳均为物证；随后沙箱对 `.git` 写入的部分回滚将 `refs/` 逐件移除。git 2.45.2 将 `refs/` 目录存在作为仓库有效性的必要条件（对照实验：删 `refs/` 即报 not a git repository，补空壳即恢复识别），整仓因此不可用。

**放大因素（未查明的环境异常）。** 本机存在系统级“删除→回收站”重定向：在沙箱内、以及显式禁用沙箱后，.NET `File.Delete` 与 PowerShell `Remove-Item` 删除的文件都进入回收站；git 原子写产生的临时文件（`*.lock`、随机名、旧版 `config`）被 unlink 时也全部被捕获。来源未查明（候选：AI 沙箱的回滚实现、安全/防删类软件）。它意外保全了两次事故的证据，但会让回收站持续堆积 git 内部文件，并可能拖慢或干扰 git 的文件操作。

**责任归属（实施方自述、审查方认可）。** 第二次事故中，管道命令写法缺陷与在无 ceiling/toplevel 断言的情况下连续执行 git 写命令，责任在实施方；沙箱写入层是放大器而非替罪羊。第一次事故为人工文件管理操作误删，与实施方脚本无关。两次事故中工作区业务文件均零损伤，破坏全部局限于 `.git` 元数据层。

### 恢复方法（可复用）

**分诊顺序（禁止跳过取证直接动手）。**

1. `git rev-parse --is-inside-work-tree` 确认症状；列 `.git` 顶层，区分“整个 `.git` 消失”与“部分缺失（如 `refs/`）”。
2. 读 `.git/logs/HEAD` 末行第 2 个哈希确认事故前 tip；读 `HEAD`、`config`、检查 `objects/`（松散对象 + `pack/*.pack`）。
3. 先把残存 `.git` 整体复制到 `.runtime/forensics/<日期>/`；不要清空回收站，先从 `$I*` 元数据还原被删路径与时间。

**A 案：最小离线修复（本次第二次事故采用，零工作区改动）。**

```bash
cd E:/MyWork/Code/small_tool/livefil
tail -1 .git/logs/HEAD          # 末行第 2 个哈希即事故前 tip（本次为 92b55b1）
mkdir -p .git/refs/heads .git/refs/tags .git/refs/remotes/origin
git update-ref refs/heads/main <tip-sha>
git update-ref refs/remotes/origin/main <tip-sha>
git fsck --full && git log --oneline -5 && git status
```

注意：写 ref 必须用 `git update-ref`，不要用 PowerShell 5.1 的 `Set-Content`（默认编码会把 40 位哈希写坏）。dangling 对象是历史物证，确认无碍后可择期 `git gc`。

**B 案：远程重建（第一次事故采用，对象库整体丢失时）。**

```bash
git init -b main
git remote add origin https://github.com/7codeyyy-sudo/Livefil.git
git fetch origin --prune --tags
git reset --mixed <tip-sha>     # 只锚定 HEAD 与索引，绝不用 --hard：工作区改动必须保留
git branch --set-upstream-to=origin/main main
```

**红线。** 恢复前不得 `git init` 覆盖残存目录、不得 `reset --hard`、不得清空回收站；任何方案执行后必须用 `fsck` + `log` + `status` 三重核验，并对照取证副本确认工作区改动集合不变。

### 教训（未来分诊 checklist）

- 出现 `not a git repository` 时，第一反应不是“被删了”，而是先判定缺失范围：`refs/` 缺失与整个 `.git` 消失的恢复路径完全不同。
- 沙箱内 git 命令“成功”不代表作用在预期仓库；没有 ceiling 与 toplevel 断言时，git 向上发现主仓是默认行为而非异常。
- 先取证、后修复；能离线 `update-ref` 解决就不重克隆；必须重克隆时只用 `--mixed`，工作区是最后的底线。
- 删除类操作必须有路径白名单断言；递归删除目录联接前先解联接——这条规则对人和脚本同样适用。
- 必须跑完的命令绝不能接 `head`：管道会用尾部命令的退出码掩盖真实失败（本机实测 `false | head -3` 的 `$?` 为 0）；要留输出就重定向到文件，并在 `pipefail`/`PIPESTATUS` 下判断成败。
- 复盘者的自我归责也要过实验：命令级假设（如“SIGPIPE 杀死了 init”）应在同版本环境对照实测后再写入正式记录；实测能区分“真实机制”与“合理但不成立的推测”，两者的预防价值不同。

### 根因

**① 锁文件来源污染（控制项按预期拦截）。** 开发机 npm 配置了镜像 registry，`npm install <新依赖>` 时锁文件新增条目的 `resolved` 被写成镜像主机。项目的 `lockfile:check` 门禁设计正确并成功拦截；流程缺口是提交前未在本地先跑该校验。修复脚本只替换主机名、不动版本与 integrity，差异可逐行审计。

**② 跨平台验收盲区（本条核心教训）。** 验收脚本只在 Windows 单平台执行并据此宣布完成。代码处理了联接的**创建**差异（`symlinkSync(target, link, 'junction')` 的第三参数在 POSIX 被忽略、生成普通符号链接），却没有处理**删除**差异（junction 用 `rmdir`、POSIX 符号链接用 `unlink`）。本地 58/58 全绿不仅没有发现问题，还构成了“已经验收”的错误确定性。最终由 Linux CI 在合并前兜底。

**③ Windows 检出反复 EINVAL（机制未完全查明，处置预案已验证）。** 稳定复现于快进/检出替换 `.gitignore` 时；诊断显示文件属性普通（Archive）、无重解析点（`fsutil reparsepoint query` 报 4390）、.NET 可正常以 RW 方式打开且 `File.Delete()` 一次成功，因此不是只读属性、junction、权限或持续性占用。判断为 git 检出排除文件时的自身句柄与本机系统层扫描（安全软件/索引/删除重定向，参见条目 001 未闭环项 1 记载的同机异常）在密集检出窗口叠加，导致 git 的 unlink 拿到 Win32 EINVAL；手动删除成功后重试仍在 git 路径复现，排除“纯瞬时占用”。未用 Process Explorer 等工具实抓持有句柄的进程，底层归属存疑。

### 恢复方法（可复用）

**Linux 清理目录符号链接的跨平台写法（已在 main）：**

```js
// Windows junction：rmdirSync（unlink 对 junction 无效；递归 rm 会顺着链接清空目标）
// POSIX 目录符号链接：unlinkSync（rmdir 对符号链接报 ENOTDIR）
if (process.platform === 'win32') rmdirSync(linkPath);
else unlinkSync(linkPath);
```

**Windows 检出 `unable to unlink old '<file>': Invalid argument` 处置预案：**

1. 先分诊：确认无重解析点（`fsutil reparsepoint query <file>`）、属性非只读、.NET `[System.IO.File]::Open(...)` 可打开；排除 junction/权限类常见原因。
2. 不要反复重试 checkout（每次失败都会留下半更新工作区）；先 `git stash push -u` 收走半成品。
3. 预置目标内容并暂存，使索引先于工作区到达目标 blob，git 便无需对该路径执行 unlink：
   `git checkout origin/main -- <file>` → 核对 `git hash-object <file>` 等于 `git rev-parse origin/main:<file>` → `git add <file>`（该文件已在索引中即为目标版本）→ `git merge --ff-only origin/main`。
4. 全程禁止 `reset --hard`；完成后用 hash 比对、`status`、`diff origin/main` 三重核验；恢复用 stash 确认内容重复后再删除。

**无 CI 日志权限时的红灯取证：** 以步骤级耗时定位失败子命令 → 对照平台差异与官方文档做静态假设 → 提交最小修复让 CI 充当验证实验（单变量、可解释）；PR 状态为 closed 时新推送不触发检查，先用 API 核对 PR state，再请有权限者 reopen。

### 教训（未来分诊 checklist）

- **真实钩子、文件系统链接、子进程、行尾敏感的验收，合并前必须有目标平台（至少 Linux CI）的绿灯；单平台 58/58 不构成跨平台完成标准。** 代码里每个 `process.platform` 分支都必须在对应平台上实际跑到——只写分支而无平台验证，等于没写。
- **测试的清理路径（`after`/`finally`）与断言主体同等重要**：断言全过、清理抛错，测试进程照样非零退出；审查验收代码必须覆盖联接/临时仓库的删除语义。
- **本机配了镜像 npm registry 时，新增依赖后提交前先跑 `npm run lockfile:check`**；归一化只用项目自带脚本（只换主机名），差异必须逐行可审计。
- **Windows 上 git 检出对某一文件稳定 EINVAL 时，不要反复重试或上 `reset --hard`**：先分诊重解析点/占用，再用“预置目标 blob 入索引”绕过 unlink（见恢复方法）。
- **分支保护的价值在红灯时刻兑现**：两次缺陷都靠必需检查拦在 main 之外；“本地全绿”可以作为信心来源，但合并闸门必须由干净环境的 CI 执行。
- 日志拿不到时不下唯一结论：本条第二轮根因在修复时仍标注为“高置信假设”，直到第三轮 CI 单变量变绿才转为证实——静态推断与实验证实要分开表述。

# Livefil 开发环境规范

> 版本：v0.2  
> 日期：2026-09-16  
> 适用范围：本项目本地开发、测试、构建、运行数据和 CI

## 1. 总原则

Livefil 的项目依赖、构建产物、运行数据、缓存、日志和本地数据库数据默认放在项目所在的 E 盘目录，不依赖 C 盘的用户目录或全局项目安装。

项目根目录由启动脚本动态解析，统一记为 `PROJECT_ROOT`：

```text
PROJECT_ROOT
```

## 2. 路径规则

### 2.1 必须放在项目目录内

```text
PROJECT_ROOT/
├─ node_modules/              # 项目依赖
├─ .runtime/                  # 项目运行时数据和可选便携运行时
│  ├─ node/                   # 可选：便携 Node.js
│  ├─ postgres/                # 可选：本地数据库数据
│  ├─ logs/                   # 本地运行日志
│  └─ uploads/                # 本地上传测试数据
├─ .cache/                    # 包管理器和构建缓存
│  ├─ npm/
│  ├─ pnpm/
│  └─ next/
├─ .data/                     # 本地开发数据，可按环境分离
├─ .env.local                 # 本地配置，不提交到 Git
└─ .env.example               # 可提交的配置模板，不包含秘密
```

### 2.2 不允许的做法

- 不使用全局 `npm install -g` 安装项目运行依赖。
- 不把项目依赖安装到用户目录下的项目副本。
- 不把数据库、上传文件、日志和导出数据放在桌面、下载目录或 C 盘用户目录。
- 不把 API 密钥写入源代码、提交记录或共享文档。
- 不使用 `$HOME`、`%USERPROFILE%`、桌面或下载目录作为项目数据目录。
- 不把真实用户数据复制到开发环境。

## 3. 运行时和工具边界

### 3.1 Node.js

优先使用项目目录下的便携 Node.js：

```text
PROJECT_ROOT\.runtime\node
```

如果机器已经安装了 Node.js，也可以使用系统 Node.js，但必须满足：

- 项目依赖仍安装在 `livefil\node_modules`。
- 包管理器缓存重定向到 `livefil\.cache`。
- 不使用全局项目依赖。
- 版本由项目配置锁定，不能因系统升级自动改变。

### 3.2 包管理器

包管理器选择由项目负责人确认后固定一种，不允许不同 AI 任务随意切换。

缓存和依赖存储应指向项目目录，例如：

```text
PROJECT_ROOT\.cache\npm
PROJECT_ROOT\.cache\pnpm
```

必须提交锁定文件，例如 `package-lock.json` 或 `pnpm-lock.yaml`，确保 AI 和不同机器安装同一组依赖。

### 3.3 数据库

优先顺序：

1. 邀请测试环境使用托管 PostgreSQL。
2. 本地开发使用 Docker 或项目目录映射的数据卷。
3. 如果使用本机 PostgreSQL，数据目录必须显式放在 E 盘项目运行目录，不使用默认 C 盘数据目录。

Docker 引擎本身可能由 Windows 安装在其他位置，但数据库数据卷必须映射到项目目录，并且不得把真实用户数据写入本地开发库。

## 4. 环境变量和秘密

`.env.local` 只保存在本机项目目录，加入 `.gitignore`。提交 `.env.example` 时只保留变量名和说明：

```text
DATABASE_URL=
AUTH_SECRET=
AI_PROVIDER=
AI_API_KEY=
LOG_LEVEL=debug
```

要求：

- 生产密钥不复制到本地测试项目。
- 测试环境使用独立数据库和独立 AI 配额。
- 运行时读取密钥，不把密钥写入前端代码。
- 日志不得打印环境变量和完整请求头。

## 5. 构建、日志和临时文件

- Next.js 构建缓存应尽量使用项目目录的 `.cache/next`。
- 本地日志写入 `.runtime/logs`，不写桌面或系统用户目录。
- 测试导出文件写入 `.runtime/exports`，每次测试使用唯一文件名。
- 临时数据库迁移备份写入 `.runtime/backups`。
- AI 测试输入使用脱敏数据，结果缓存写入 `.runtime/ai-cache`，禁止保存真实敏感内容。

## 6. C 盘边界说明

本规范能控制项目级依赖和数据位置，但不能保证 Windows 完全不触碰 C 盘：

- 操作系统可能使用 C 盘临时目录。
- 编辑器、终端和杀毒软件可能维护系统级缓存。
- Docker Desktop 或系统级 Node.js 可能由机器管理员安装在 C 盘。
- 浏览器自身缓存通常不由项目控制。

因此本项目的准确要求是：

> 项目不把开发依赖、运行数据和业务数据主动安装或写入 C 盘；系统级软件和操作系统临时行为不属于项目可控范围。

如果需要做到更严格的全盘隔离，应使用 E 盘便携 Node、E 盘包管理器缓存、E 盘数据库数据卷和独立的开发工具配置，并由机器管理员进一步限制系统缓存位置。

## 7. 环境检查任务

开发开始前必须完成：

- [ ] 检查项目根目录由启动脚本解析为当前项目根目录，不使用写死的绝对路径。
- [ ] 检查 Node.js 版本是否符合项目要求。
- [ ] 检查包管理器版本并固定。
- [ ] 检查依赖安装路径为项目下的 `node_modules`。
- [ ] 检查缓存路径没有指向 C 盘用户目录，或明确记录系统限制。
- [ ] 检查 `.env.local` 未被 Git 跟踪。
- [ ] 检查本地数据库数据卷位于项目 `.runtime` 或使用托管数据库。
- [ ] 检查日志、导出和备份目录位于项目下。
- [ ] 检查没有真实用户数据进入开发环境。

## 8. CI 与仓库可见性

### 8.1 GitHub Actions 基线

- 工作流定义在 `.github/workflows/ci.yml`，在 `ubuntu-latest` 上运行，Node 版本取自 `.nvmrc`。
- 两个必需检查：
  - `ci-gate`：格式化、lint、typecheck、单元测试、集成测试、node:test 验收链和生产构建；
  - `browser-e2e`：Playwright 真实浏览器用例。
- 触发时机：推送到 main 和所有 pull request。
- CI 使用 setup-node 提供的系统 Node，不依赖便携运行时；受管目录（`.runtime`、`.cache`、`.data`）由 `env:bootstrap` 在安装依赖前创建。
- `package-lock.json` 的 resolved 地址必须指向官方源（`registry.npmjs.org`），由 `lockfile:check` 检查；镜像加速只通过本机用户级 npm 配置实现，不写入仓库。
- 合并规则：main 只接受 PR 合并，两个检查都通过且分支保持最新；规则对管理员同样生效，不允许绕过。紧急情况可临时关闭规则，事后必须恢复。

### 8.2 仓库公开后的约束

仓库自 2026-09-16 起为 Public（变更原因、备选方案和影响评估见 [工程决策记录 001](./工程决策记录.md)）。

- 仓库**无 LICENSE 文件**，默认保留所有权利（All Rights Reserved）：代码可查看，但无使用、修改或分发授权。
- 密钥只能通过 `.env.local`（本机）和 GitHub 仓库 Secrets（CI）传递；`.env.example` 只保留变量名和占位说明。
- CI 运行日志对任何人可见：禁止在测试输出、CI 日志、Issue 和 PR 中粘贴密钥、令牌或真实用户数据。
- 依赖漏洞随代码公开而可见，应及时处理 Dependabot 告警。
- 出现以下情况时必须重新评估公开决策并在《工程决策记录》追加条目：引入第三方专有代码或素材、商业模式发生变化、仓库中需要存放与真实用户数据相关的材料。

## 1. 使用规则

### 1.1 AI 每次只处理一个任务

给 AI 开发任务时，应提供：

1. 本文件中的任务 ID。
2. 任务目标和依赖任务。
3. 关联的 SRS/设计文档。
4. 允许修改的目录。
5. 验收标准。
6. 必须执行的测试和检查。

不允许 AI 一次跨越多个阶段，也不允许在没有确认的情况下顺便扩大需求范围。

### 1.2 推荐开发提示词

```text
请执行任务 <TASK-ID>。

先阅读：
- doc/README.md
- doc/03-requirements/需求规格说明书_SRS.md
- doc/05-technical-design/概要设计说明书.md
- doc/05-technical-design/详细设计说明书.md
- 本任务指定的关联文档

要求：
1. 先检查当前代码和已有改动，不覆盖用户已有工作。
2. 先给出实现计划和将修改的文件。
3. 只实现本任务，不顺便实现其他任务。
4. 遵循 universal-code-quality 规范。
5. 为核心逻辑补充测试。
6. 执行格式化、静态检查、测试和构建。
7. 最后报告修改内容、测试结果、风险和未完成事项。
```

### 1.3 完成定义（Definition of Done）

每个任务只有在以下条件全部满足时才能勾选：

- [ ] 功能符合任务描述和验收标准。
- [ ] 相关输入经过边界校验。
- [ ] 失败路径有明确错误和用户反馈。
- [ ] 核心逻辑有单元测试或集成测试。
- [ ] 没有把业务逻辑写进页面组件。
- [ ] 没有硬编码密钥、路径、金额或时区偏移。
- [ ] 涉及钱使用整数分/Decimal，涉及时间使用 UTC 和用户时区。
- [ ] 涉及外部网络调用时有超时、限流和降级。
- [ ] 迁移、删除和数据清理有备份/回滚方案。
- [ ] 格式化、lint、test、build 均通过。
- [ ] 文档、接口或数据库变更已同步。

### FND-003 建立测试框架（P0）

依赖：FND-001

- [ ] 配置单元测试框架。
- [ ] 配置组件/集成测试基础。
- [ ] 配置 E2E 测试基础。
- [ ] 建立测试数据工厂和随机测试用户。

已确认方案（2026-09-15）：

| 用途 | 选型 |
|---|---|
| 单元/集成测试 | Vitest 5.0.1，需显式安装其必需 peer `Vite 8.3.0` |
| React 组件测试 | `@vitejs/plugin-react` 6.1.1、React Testing Library 16.3.3、user-event 14.6.7、jest-dom 7.0.1、jsdom 30.0.1 |
| HTTP 拦截 | MSW 2.15.0，仅用于 Node 侧测试 |
| E2E | Playwright 1.63.0 |
| 覆盖率 | `@vitest/coverage-v8` 5.0.1 |

约定：

- 测试与测试工厂落在 `tests/` 下（`unit`、`integration`、`e2e`、`factories`、`helpers`、`setup`），不放进 `src/`。
- `vitest.config.ts` 分 unit（node 环境）与 integration（jsdom 环境）两个 project；`playwright.config.ts` 只匹配 `tests/e2e`，单 worker，先 build 再 start。
- 脚本名 `test:unit`、`test:e2e` 不得变更；`check` 不跑浏览器，`check:all` 含浏览器。
- E2E 浏览器安装到项目内 `.cache/playwright`，覆盖 Playwright 默认的系统级目录。
- 覆盖率产物输出到 `.cache/coverage/`，P0 不设通过阈值。
- MSW 只用于 Node 侧测试，不替代依赖注入，也不作为 E2E 的拦截手段；E2E 统一使用 `page.route()`。
- 已有 `tests/unit/validation/env.test.ts` 迁移到 Vitest；既有 `.mjs` 验收脚本继续保持 node:test。

验收：至少有一个单元测试、一个 API 测试和一个页面 E2E 测试通过。

## 4. Phase 1：设计系统与应用外壳

目标：先建立 PC Web 的高级简约视觉和移动端可扩展布局。

### UI-001 建立设计令牌（P0）

依赖：FND-001

- [ ] 在 `src/shared/ui/styles/tokens.css` 建立 18 个颜色令牌（9 基础语义色 + 9 派生/辅助色）与 2 个阴影令牌，字体/间距/圆角令牌一并建立，命名与浅色取值逐一对齐《UI 页面规范》§2.4，由根布局唯一导入；组件使用 CSS Modules，不引入 Tailwind 或其他样式框架（T-002 已确认）。
- [ ] 不得预造 §2.4「暂不收编」中的令牌（状态色边框、半透明白磨砂）。
- [ ] 断点不做成 CSS 变量：CSS（含组件 CSS Modules）按 §3.1 px 写媒体查询，不算第二份取值；仅当 JS 需要时新增唯一 TS 常量镜像。
- [ ] 第一阶段实现浅色主题，`:root` 声明 `color-scheme: light`。
- [ ] 深色只预留 `html[data-theme='dark']` 占位块，不实现切换：仓库内不得设置 `data-theme` 属性、不得出现 `prefers-color-scheme`（验收脚本断言）。
- [ ] 令牌纪律：`tokens.css` 之外禁止 hex/rgb/hsl 字面量（含内联 style），由验收脚本断言。
- [ ] 扩展 `scripts/env/check.mjs` 的硬编码绝对路径扫描到 `app/`、`src/`（`.ts`/`.tsx`/`.css`，暂不含 `tests/`）。
- [ ] 所有状态颜色同时有文字或图标表达（人工评审项，无法自动判定）。

交付批次（沙箱开发者只交文件、不做 git 写，由仓库维护者在真机分两次提交）：

- 批次 A `chore(env):` 仅含 check.mjs 扫描面扩展，作为独立提交先落地；验收为 `env:check` 对 `app/`、`src/` 零 FAIL 且 `test:e2e` 全绿（四个 fnd 验收脚本内含 env:check 断言，CI 无独立 env:check 步骤）。
- 批次 B `feat(UI-001):` 含 tokens.css、根布局唯一导入、UI-001 验收脚本，在批次 A 合并后开工。

验收：

- `tokens.css` 存在并被根布局唯一导入；§2.4 的 18 个颜色令牌与 2 个阴影令牌全部有定义且浅色取值逐行一致，字体/间距/圆角覆盖 §2.2–§2.3；
- 机器断言通过：令牌文件外无颜色字面量、无深色激活点（`data-theme` 设置点与 `prefers-color-scheme`）、断点像素值在 `.ts/.tsx` 中仅出现在唯一 TS 镜像文件（CSS 媒体查询不受限）；
- `env:check` 扩展后对 `app/`、`src/` 零 FAIL（误报先人工确认，再定行内豁免约定，不提前建豁免机制）；
- `npm run check` 全绿。

关联：[UI 页面规范](../04-product-design/UI页面规范.md) · T-002（[产品与技术设计决策清单](../05-technical-design/产品与技术设计决策清单.md)）

- [ ] 批次 4：EmptyState、LoadingState、ErrorState（可组合批次 1 的 Button）。
- [ ] 全部组件支持键盘焦点和移动端触控尺寸。

验收：组件有默认、禁用、加载、错误和窄屏状态，五态在 styleguide 双视口浏览器用例中可见；每批本地 `npm run check` 与 `test:browser` 全绿。

## 15. 任务状态规范

推荐状态：

```text
BACKLOG → READY → IN_PROGRESS → REVIEW → TESTING → DONE
                                  └──────→ BLOCKED
```

- `BACKLOG`：已识别但尚未满足开发条件。
- `READY`：依赖已完成，设计和验收标准明确。
- `IN_PROGRESS`：当前由一个开发任务执行者处理。
- `REVIEW`：代码和设计等待检查。
- `TESTING`：等待自动或人工测试。
- `BLOCKED`：有明确阻塞原因，必须记录原因和下一步。
- `DONE`：完成定义全部满足。

## 16. AI 开发安全规则

- AI 不得擅自执行破坏性数据库迁移、批量删除或覆盖数据。
- 任何删除、迁移和数据清理先备份、预览影响范围并请求确认。
- AI 不得为了通过测试删除测试、放宽类型或关闭安全检查。
- AI 不得在前端写入 API 密钥。
- AI 不得使用真实用户财务数据作为测试样本。
- AI 修改核心数据模型时，必须同步更新数据库文档、接口文档和迁移测试。
- AI 生成代码后必须报告未覆盖的风险，而不能只报告“完成”。

## 17. 任务 ID 规范

### 17.1 任务 ID 是什么

任务 ID 是开发任务清单中每一个可执行工作项的稳定唯一编号。它不是：

- 用户 ID。
- 数据库主键。
- API 请求 ID。
- Git commit hash。
- AI 会话 ID。

任务 ID 用于让人和 AI 对同一项工作使用相同名称，跟踪依赖、验收、代码提交和问题反馈。

### 17.2 当前任务 ID 格式

```text
<MODULE>-<NUMBER>
```

示例：

| 前缀 | 含义 |
|---|---|
| `ENV` | 开发环境 |
| `FND` | 基础工程 |
| `UI` | UI 和页面 |
| `IAM` | 身份、账户和设置 |
| `TASK` | 任务和收件箱 |
| `GOAL` | 目标和行动 |
| `SCHED` | 排程和时间块 |
| `ROUTINE` | 例程和重复任务 |
| `EXEC` | 执行记录 |
| `SYNC` | 云端数据和同步 |
| `EXP` | 开销 |
| `REVIEW` | 日周复盘 |
| `NOTIFY` | 提醒和通知 |
| `AI` | AI 向导和建议 |
| `OPS` | 安全、测试、部署和运维 |

例如：

- `ENV-001`：开发环境路径检查。
- `FND-001`：初始化 Next.js 项目。
- `TASK-002`：收件箱快速添加。
- `SYNC-004`：同步冲突处理。

### 17.3 使用规则

- 每个任务只能有一个主任务 ID。
- 已发布或已开始的任务不得随意改 ID。
- 新增任务必须使用新的编号，并更新本清单。
- 任务拆分时保留原任务作为父任务，并创建新的子任务 ID，例如 `TASK-002-A`、`TASK-002-B`。
- Git 分支建议使用：`feat/TASK-002-inbox-quick-add`。
- Commit 建议使用：`feat(TASK-002): add quick task creation`。
- AI 提示词必须明确写出任务 ID。
- 任务完成后保留历史，不重复使用旧编号。

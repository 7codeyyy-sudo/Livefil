## 1. 详细设计原则

- 页面组件只负责展示和交互。
- 用例服务负责业务编排和事务边界。
- 领域对象负责状态转换和不变量。
- 仓储接口隔离数据库实现。
- 外部 AI、通知和认证通过适配器接入。
- 所有外部数据先校验，再进入领域对象。
- 所有写操作考虑重复提交、并发修改和失败恢复。

## 3. 核心领域对象

### 3.1 Task

```text
Task
  id: TaskId
  userId: UserId
  title: string
  status: TaskStatus
  lifeAreaId?: LifeAreaId
  goalId?: GoalId
  actionId?: ActionId
  estimatedMinutes?: number
  minimumVersion?: string
  dueDate?: LocalDate
  recurrenceRule?: RecurrenceRule
  createdAt: Instant
  updatedAt: Instant
  version: number
  deletedAt?: Instant
```

规则：

- 标题不能为空或超过最大长度。
- 预计时长必须为正整数。
- 状态合法流转严格按 SRS §9.1（含「收件箱/已安排/完成/最低版本完成/部分完成/
  延期/跳过/归档」）；DB 枚举与其中文状态的对照见《数据库设计》§4.5。
- 延期不是删除，必须保存调整历史。
- 已完成任务可以被重新打开，但必须留下状态变更记录。

> 「调整历史 / 状态变更记录」的落点：每次流转写一条 `audit` 状态事件（见本章 §4
> 开头）；其中供复盘与统计长期使用的执行/调整数据，自 Phase 4 起持久化到
> `execution_logs`。Phase 3 不提前写该表，也不另建状态历史表。

### 3.2 Goal 和 Action

```text
Goal
  id: GoalId
  userId: UserId
  lifeAreaId: LifeAreaId
  name: string
  status: GoalStatus
  startDate?: LocalDate
  targetDate?: LocalDate
  reason?: string
  resultMetric?: ResultMetric
  version: number

Action
  id: ActionId
  goalId: GoalId
  name: string
  minimumVersion?: string
  targetFrequency?: Frequency
  estimatedMinutes?: number
  status: ActionStatus
```

结果目标和行动指标分开保存，不能用行动完成率直接覆盖结果进度。

### 3.3 ScheduleBlock

```text
ScheduleBlock
  id: ScheduleBlockId
  userId: UserId
  taskId?: TaskId
  actionId?: ActionId
  routineId?: RoutineId
  routineStepId?: RoutineStepId
  startsAtUtc: Instant
  endsAtUtc: Instant
  timezone: IanaTimezone
  source: Manual | Suggested | Imported | Routine
  status: Planned | Active | Completed | Adjusted | Cancelled
  conflictState: None | Warning | Confirmed
  version: number
```

规则：

- `endsAtUtc` 必须晚于 `startsAtUtc`。
- 创建或移动时间块时计算冲突，但不自动删除其他块；冲突规则以接口 §6
  冻结口径为准（半开区间、相邻不撞、含 fixed commitments）。
- 例程展开的块带 routineId/routineStepId 溯源；移动/取消块不改任务状态，
  完成经 ExecutionLog 联动（DB §4.6）。

### 3.4 ExecutionLog

ExecutionLog
  id: ExecutionLogId

  taskId?: TaskId
  actionId?: ActionId

  status: Completed | MinimumCompleted | Partial | Skipped | Deferred

历史执行记录不被任务改名或任务删除覆盖。status 五值与两表关系以

## 4. 应用服务设计

> **「记录审计事件」的统一形态（2026-09-21 明确）**：本章各用例所列的
> 「记录/写审计事件」，一律经 `src/shared/telemetry/audit-event.ts` 的 `audit`
> 日志通道写出，**不写数据库表**（SRS §6.7 只要求事件类型、时间、结果、匿名用户
> 标识与版本；早期 ER 图的 `audit_events` 已勘误删除）。审计只记事件类型、不记
> 变更内容。保留期/归档/导出随 OPS 批次。

> **Phase 3 补充规则（2026-09-21 冻结）：**
> - **状态流转判定**：各状态变更用例（含 Task §3.1 的「重新打开」）以
>   《数据库设计》§4.5 的完整合法流转表为准（含重开/恢复），表外跳转一律
>   `VALIDATION_ERROR`；删除不经状态值，由删除用例置 `deleted_at`。
> - **删除用例**：`DeleteTaskUseCase` 软删任务（重复删除返 404）；
>   `DeleteActionUseCase` 软删行动并在同一事务把关联任务的 action_id 置空
>   （goal_id 保留）。两者均写审计事件。
> - **写操作幂等**：请求带 `Idempotency-Key` 时先在 `idempotency_keys`
>   （DB §4.15）占位再执行业务，完成后存响应快照；重放返 `IDEMPOTENCY_REPLAY`；
>   同 key 不同请求体指纹返 `VALIDATION_ERROR`；不带 key 不强制幂等。
> - **列表取数**：收件箱分段加载经客户端原语 `useCursorListQuery`
>   （与 useAsyncQuery 同目录同纪律，累积而非替换）；列表查询固定
>   `createdAt desc`、limit 默认 20/上限 100、cursor 不透明。

### 4.1 CreateTaskUseCase

输入：`CreateTaskCommand`

处理：

1. 验证用户身份。
2. 校验标题、时长、日期和关联实体是否属于当前用户。
3. 创建任务领域对象。
4. 写入仓储。
5. 记录审计事件。
6. 返回任务 DTO 和版本号。

失败：

- 输入非法：`VALIDATION_ERROR`。
- 关联数据不存在：`RELATED_ENTITY_NOT_FOUND`。
- 数据库冲突：`WRITE_CONFLICT`。

### 4.2 ScheduleTaskUseCase

处理：

1. 解析用户本地时间和时区。
2. 转成 UTC。
3. 校验结束时间大于开始时间。
4. 查询同一用户指定范围内的时间块。
5. 计算重叠冲突。
6. 写入时间块和冲突结果。
7. 返回冲突提示，但不自动移动其他时间块。

### 4.3 RecordExecutionUseCase

处理：

1. 校验任务或行动属于当前用户。
2. 校验执行状态和时长。
3. 追加执行记录。
4. 更新行动汇总，不覆盖历史。
5. 生成复盘可用的统计事件。

执行记录写入必须支持幂等键，避免用户重复点击生成两条相同记录。

### 4.4 CreateExpenseUseCase

处理：

1. 接收金额最小单位和币种。
2. 校验金额范围、分类和关联实体。
3. 在事务中写入开销。
4. 更新必要的汇总缓存或统计查询。
5. 记录审计事件。

禁止：

- 浮点金额直接计算。
- 未校验分类 ID 就写入。
- AI 结果未经确认直接调用正式写入用例。

### 4.5 GenerateAiDraftUseCase

处理：

1. 检查用户是否开启 AI 和剩余额度。
2. 选择最小必要数据。
3. 对文本和上下文进行脱敏。
4. 使用 provider adapter 调用外部 API。
5. 设置超时、重试上限和退避。
6. 校验结构化 JSON 响应。
7. 写入 `AiDraft`，不写正式实体。
8. 用户确认后，调用普通业务用例完成写入。

### 4.6 EnsureLocalSessionUseCase（Phase 2 本地批次）

输入：请求携带的会话 Cookie（可能无）。

处理：

1. 无 Cookie：验签失败、或会话已失效——本地模式下**不返回 401**，而是：在单事务内幂等确保唯一本地用户（mode=local）存在、确保默认生活领域已初始化（见 4.8），签发新会话 Cookie。
2. 有有效 Cookie：解析出 userId，经仓储确认用户仍存在；不存在则回到第 1 步。
3. 返回 `{ userId, mode: 'local' }` 与会话 Cookie；`GET /me` 与设置页据此显示「本地模式」。

幂等约束：「确保用户」经单例行锁/唯一约束实现，并发首启只产生一个用户；默认领域播种同样幂等（条件＝该用户无任何领域行，见 §4.8）。

失败：依赖（DB）不可用→`DEPENDENCY_UNAVAILABLE`；本用例不产生 `AUTHENTICATION_REQUIRED`——该错误码只服务云端模式（挂账）。

### 4.7 UpdateUserSettingsUseCase

输入：`UpdateSettingsPatch`（locale/timezone/currencyCode/weekStartsOn/默认时长与缓冲/AI 开关与数据同意/提醒与安静时段）。

处理：

1. Zod 校验全部字段（含跨字段约束：`ai_enabled=true` 要求 `ai_data_consent=true`；安静时段起止合法；时长/缓冲非负）。
2. 单事务读取—修改—写回，带 `version` 乐观并发；版本不符→`CONFLICT`。
3. 写审计事件（不记录敏感内容）；返回新设置与自增 version。

禁止部分更新（校验失败不落库）、禁止前端自报时区而服务端不校验。

### 4.8 ManageLifeAreaUseCase

涵盖创建、重命名、排序、归档（不提供物理删除）：

- 创建：校验名称（≤60）、color_key ∈ 分类色集合（UI 规范 §2.1：blue/green/amber/violet/teal/rose）；同用户未归档同名→`CONFLICT`；sort_order 取末位。
- 排序：接收有序 id 列表，单事务内重排全部 sort_order；列表必须恰好等于该用户当前未归档领域集合（多/少/他人 id → `VALIDATION_ERROR`）。
- 归档：置 is_archived，不删行——关联任务/目标的 life_area_id 保持可解析；归档领域移出默认选择器，可经「显示已归档」查看；不允许重复归档。
- 所有读写强制 user_id 作用域；非本人 id 按 `NOT_FOUND` 处理（不泄露存在性）。

**默认领域播种（首启，2026-09-20 冻结）：** 名单取自 SRS 术语表对「生活领域」的六类举例，固定名称、color_key 与 sort_order：

| sort_order | 名称 | color_key |
|---:|---|---|
| 0 | 工作 | blue |
| 1 | 健康 | green |
| 2 | 财务 | amber |
| 3 | 关系 | rose |
| 4 | 兴趣 | violet |
| 5 | 家务 | teal |

播种条件＝该用户在 life_areas 中**一行都没有**（含已归档）时，整体写入六行（单事务）；这是「首启播种」而非「逐项补齐」——用户改名、归档甚至归档全部领域后重启，默认项都不复活（复活会覆盖用户已做出的整理）。EnsureLocalSessionUseCase（§4.6）在同一首启事务内完成「建用户 + 播种六领域」；条件经「该用户行数为 0」判定，故无需为 life_areas 增加 seed_key 列，并发首启经事务与用户行锁串行化。

> **Phase 4 冻结规则（2026-09-21）：**
> - 物化为唯一实例化方式：任务/固定事项的重复模板在查询或显式安排窗口内展开，
>   不预生成窗口外行；插入靠唯一约束冲突去重（不先查后插）；PATCH 模板不级联
>   实例，PATCH 实例不影响模板。
> - 冲突检测为独立 domain service，POST/PATCH 块与 /today 共用：
>   半开区间、UTC 比较、相邻不撞、跨块与固定事项两类对象。
> - 执行记录与块/任务联动口径：见接口 §7（completed/minimum_completed、
>   partial、deferred/skipped 各分支）。
> - 恢复建议由 domain service 产出（非前端文案），统计窗口与触发阈值、
>   建议顺序以接口 §7 为准。

### 4.9 ExpandRecurringTemplatesUseCase

输入：`userId`、窗口 `[from, to]`、`timezone`。处理：枚举窗口内模板
（tasks 与 fixed_commitments），按 RecurrenceRule 命中日批量插入实例行；
唯一约束冲突即已存在，跳过不报错；返回新实例数。幂等、可重入。

### 4.10 ManageRoutineUseCase / ScheduleRoutineUseCase

- Manage：创建（定义＋steps 一次写入，position 取数组序）、PATCH
  （version；steps 带 id 更新/无 id 新增/缺失软删）、软删；不重写已生成块。
- Schedule：输入 routineId、date、startAt、timezone；先查该例程当日是否已有
  块（有则 409 `CONFLICT`）；按步骤顺序以服务端 UTC 生成 blocks
  （source=routine、溯源列回填），逐块跑冲突检测；返回块数组。

### 4.11 GetTodayUseCase

处理：①窗口物化（4.9）；②取当日 blocks（未取消）、fixed commitment 实例、
planned 且 due≤date 且当日无块的任务（≤50）、命中例程及步骤块状态、
带 targetFrequency 的 active 行动及当日 logs 判定；③计算 load
（口径见接口 §6，960 清醒分钟）；④调 RecoveryModeService 填 recovery。
一次响应，不做写库副作用（物化除外）。

### 4.12 RecoveryModeService

- `SetManual(enabled)`：upsert recovery_states（since 记进入时刻）。
- `Evaluate(date)`：手动态直接产出建议列表；另算自动触发——最近 7 个有计划
  任务日中连续 2 天完成率 <50%。建议顺序 SHRINK→MINIMUM→RESCHEDULE→PAUSE，
  仅返回建议对象（code/target/text），不落库、不改计划。

## 5. 同步详细设计

### 5.1 本地数据结构

客户端 IndexedDB 至少包含：

```text
entity_snapshots
  entity_type
  entity_id
  payload
  server_version
  local_updated_at
  sync_state

outbox_operations
  operation_id
  entity_type
  entity_id
  operation_type
  payload
  created_at
  retry_count
  last_error
  status

sync_cursor
  user_id
  last_server_cursor
```

### 5.2 同步流程

1. 用户操作先写入本地实体快照。
2. 生成客户端 UUID 和 outbox 操作。
3. UI 显示待同步状态。
4. 在线时批量提交操作。
5. 服务端使用幂等键判断是否已处理。
6. 服务端校验实体版本。
7. 成功则返回服务端版本和同步游标。
8. 冲突则返回冲突实体和可解决信息。
9. 客户端更新快照并删除已确认的 outbox 操作。

### 5.3 冲突策略

| 数据类型 | 策略 |
|---|---|
| 执行记录 | 追加式，不覆盖；重复操作使用幂等键去重 |
| 开销 | 默认追加式；编辑形成新版本；金额冲突必须提示 |
| 任务标题/备注 | 版本冲突提示用户选择 |
| 任务状态 | 用户主动操作优先，冲突时显示最近两次状态 |
| 时间块 | 冲突不自动覆盖，显示两个版本并要求选择 |
| 删除 | 墓碑记录同步，避免离线恢复已删除数据 |

### 5.4 勘误（2026-09-23，SYNC-000 / PD-20260923-003）

依据 PD-20260923-001 终审口径（本地单用户 × 多设备同步、Service Worker 不进本批）
与 SYNC-000 技术 spike 结论补充；**不改变 §5.1–§5.3 原文**，冲突处以本节为准。

#### 5.4.1 本地存储选型（S1）：原生 IndexedDB + 项目内薄封装

**结论**：采用**原生 IndexedDB**，由项目内薄封装提供 `LocalStore` 端口；
**不引入 `idb` / `Dexie` 依赖**。

**理由**：

- **依赖纪律**：新增第三方依赖须走 lockfile 官方源纪律（事故记录 002）；Phase 5
  已按 PD-20260923-001 裁剪范围，多一个依赖即多一个变量。`idb`（Promise 包装，
  体积小）与 `Dexie`（查询 DSL，能力最强、体积最大）带来的便利，在「3 个 store、
  固定访问模式」下收益有限。
- **需求面窄且固定**：§5.1 仅需 `entity_snapshots` / `pending_operations`（见
  §5.4.2 改名）/ `sync_cursor` 三个 store，访问模式为「按 `(entityType, entityId)`
  读写」「按 `status` 扫待同步队列」「单行游标读写」，原生 API 足够。
- **事务语义可控**：原生提供 `readonly` / `readwrite` 事务与自动提交；薄封装可强制
  「一次读改写在同一事务内完成」。**这是选型最需显式约束的点**——原生 IndexedDB
  事务在 `await` 非 IDB 请求（如 `fetch`、`setTimeout`）后会**自动提交**，此后
  再发 IDB 请求会抛错；三种方案都必须面对，薄封装把它收敛成一条可测规则。
- **schema 升级路径**：原生 `onupgradeneeded` + 整数 `version`，集中在一个迁移函数里
  按版本逐级升级；可用 fake 实现断言「从 vN 升到 vN+1 的迁移序列」。
- **与 React 19 并发特性的兼容**：IndexedDB 是浏览器异步 API，**不参与 React 渲染
  路径**，三种方案在此点等价——选型不构成 React 兼容性差异。约束是统一的：不在
  render 阶段读写、不把 IDB 请求对象放进 state，改由事件/effect 驱动并经
  `useSyncExternalStore` 订阅变更。

**影响**：

- 需自建薄封装（3 个 store 的 CRUD + 迁移 + 事务助手）。
- 单测：现有 jsdom 环境无 IndexedDB，须注入 fake `LocalStore` 实现——与
  「route/use case 只依赖仓储接口、默认集成测试注 fake」的既有惯例同构。
- 真机行为（事务、升级、配额）只能由 Playwright 覆盖。
- 架构断言需扩展：页面不得直接访问 `indexedDB`，只能经端口访问（与
  「页面不直接访问数据库」同源）。

**回退方式**：端口隔离。domain 定义 `LocalStore` 接口、infrastructure 提供实现；
若薄封装复杂度超预期，可换 `idb`（语义最接近原生，迁移成本最低）或 `Dexie`，
用例层与页面零改动。

#### 5.4.2 命名消歧：客户端待同步队列改称 `pending_operations`

§5.1 中的 `outbox_operations` 与数据库设计文档 §4.14 的**服务端表同名不同物**。
为消除歧义：

- 客户端 IndexedDB 结构（§5.1）**改称 `pending_operations`**，字段不变；
- 服务端表保留 `outbox_operations` 名称，Phase 5 不启用（依据见数据库设计文档 §4.18.2）。

#### 5.4.3 离线边界与验收口径（S4，实测结论）

**环境**：Windows / Chromium（Playwright 1.63.0 内置）/ `next start` 生产构建 @
`127.0.0.1:3211` / **无 Service Worker**（实测 `navigator.serviceWorker
.getRegistrations().length = 0`、`caches.keys().length = 0`）。headless 与 headed
各测一轮，headed 记录「用户所见」。

**实测现象**：

| 步骤 | 现象 |
|---|---|
| A0 在线加载 `/today` | HTTP 200，DOM 完整渲染 |
| A1 断网·同页 | **DOM 完整保留**，客户端上下文存活；应用**自动出现离线提示条**「当前处于离线状态，显示的内容可能不是最新」 |
| A2 断网·脚本 | 客户端脚本仍可执行 |
| A3 断网·API | `fetch('/api/v1/today')` → `TypeError: Failed to fetch` |
| A4 断网·软导航 | 点击侧栏「收件箱」→ **软导航成功**（URL 变为 `/inbox`，页面正常渲染），数据区显示「收件箱没能加载」 |
| A5 断网·新路由载荷 | `fetch('/goals?_rsc=...')` → `TypeError: Failed to fetch` → **未预取路由无法软导航** |
| B1 断网·刷新 | `net::ERR_INTERNET_DISCONNECTED`，落到 `chrome-error://chromewebdata/`；**有头实测为 Chromium 原生错误页**（恐龙图标 +「按空格键即可开始游戏」+ 网络检查建议 + `ERR_INTERNET_DISCONNECTED`） |
| B2 断网·新标签 | 同上，`chrome-error://chromewebdata/` |
| C1 恢复网络 | HTTP 200，恢复正常 |

**结论**：

1. **无 SW 时，离线边界的形态是「浏览器原生错误页」，不是应用白屏**。刷新/重开时
   导航请求未到达服务器，应用层没有渲染机会，因此**应用无法提供任何离线兜底文案**
   （`chrome-error://` 属浏览器 UI，不受页面控制）。
2. **SYNC-002 的验收口径「已打开页面断网续用」成立，且只能按此口径验收**；
   「刷新/重开页面离线可用」在无 SW 前提下**不可能达成**，须明确排除在验收范围外。
3. **「续用」的准确含义**：DOM 与客户端脚本存活、离线提示条出现、**已预取路由可
   软导航**；但数据不可用（API 全 reject）、未预取路由不可达。即「已渲染内容可见 +
   可切到已预取页面 + 不崩溃」，**不是「可继续读写数据」**——离线读写依赖本批的
   `pending_operations` 队列，属 SYNC-002/003 实现目标。
4. 附带实测：数据层不可用（本次环境 Docker 未运行、无 PG，`/api/v1/today` 返回 500）
   时，页面渲染的是**应用级错误态**（「数据没能取回来。可以先重试。」+ 重试按钮），
   **不是白屏**——应用对服务端失败已有兜底。

**页面级提示文案建议**（供 PD-20260923-002 任务 1 对齐）：

- 离线（已打开页面）：沿用现有「当前处于离线状态，显示的内容可能不是最新」，建议
  补充可操作信息 →「当前处于离线状态，显示的内容可能不是最新；你的修改会先保存在
  本机，联网后自动同步」；
- 待同步计数：「N 项修改待同步」，可展开列表；
- 离线刷新/重开的说明（**无法在页面内实现**，只能置于帮助文档或首次进入提示）：
  「离线时请勿刷新或关闭页面，重新打开需要网络」；
- 恢复网络：「已恢复联网，正在同步 N 项修改」→ 完成后「已同步」。

**影响**：

- SYNC-002 的 e2e 用例须写成「已打开页面断网 → 断言 DOM 未变、离线提示条出现、
  已预取路由可切换」，**不得**写成「断网刷新后仍可用」；
- `context.setOffline(true)` 已验证可用于离线模拟，可作 e2e 夹具；
- 不引入 SW 相关实现（终审已定），本结论不改变本批范围。

**回退方式**：无（纯观测结论）。若后续 Phase 10 引入 SW 壳缓存，B1/B2 的边界将改变
（SW 可拦截导航并返回缓存壳），届时须重测并更新 SYNC-002 验收口径——本结论的适用
前提是「无 SW」。

## 6. API 和外部依赖异常处理

### 6.1 错误分类

```text
VALIDATION_ERROR        输入不合法
AUTHENTICATION_REQUIRED 未登录
FORBIDDEN               无权访问
NOT_FOUND               资源不存在
CONFLICT                版本冲突
IDEMPOTENCY_REPLAY      重复请求已处理
RATE_LIMITED            超过限额
DEPENDENCY_TIMEOUT      外部服务超时
DEPENDENCY_UNAVAILABLE  外部服务不可用
INTERNAL_ERROR          未预期错误
```

### 6.2 外部调用策略

- 所有网络调用必须有超时。
- 重试只用于幂等读取或明确可重试的外部调用。
- 使用指数退避 + jitter，最多 2–3 次。
- AI、通知和同步失败时不能阻塞手动核心流程。
- 不能使用无上限的队列和重试。
- 错误响应返回 request ID，不返回堆栈和敏感数据。

## 7. 缓存设计

P0 不引入 Redis：

- 今日任务和收件箱由客户端缓存。
- 服务器使用数据库索引优化查询。
- 复盘统计优先使用可复现查询，不做不可解释的长期缓存。
- 若后续需要服务端缓存，统一通过 `CacheStore` 接口接入。

缓存要求：

- 每个 key 有明确 TTL。
- 写操作后主动失效相关 key。
- 缓存不可作为唯一数据来源。
- 缓存损坏或不可用时回退数据库。

## 8. 安全详细设计

### 8.1 会话（Phase 2 本地批次形态）

- 使用服务端会话或安全 token，Cookie 设置 HttpOnly、Secure、SameSite。
- 本地模式会话＝**签名（HMAC）无状态 Cookie**，载荷仅含 userId、签发时间；密钥来自环境变量、不入库不进日志。本批**不建 sessions 表**（无登出黑名单/refresh 需求），云端会话形态（可吊销、多设备）随云端批次重定。
- 无/坏 Cookie 时经 EnsureLocalSessionUseCase（§4.6）自动建立本地会话，**不向用户暴露 401**；401/403 的强制路径按云端批次实现，本批只保留接口与代码位置。
- 「本地模式」标识必须在 `/me` 与设置页可见，防止用户误判数据存放位置。

### 8.2 数据与输入

- 所有数据访问带 `userId` 条件，服务端再次校验归属。
- 数据库查询使用参数化方式。
- 用户输入在展示前进行输出编码。
- 设置 Content Security Policy。
- 服务器端保存 AI、数据库和邮件服务密钥。
- AI prompt 和用户内容不写入普通日志。
- 导出、删除和登录失败记录安全事件。
- 账户删除和批量删除使用事务、备份和可恢复策略。

### 8.3 环境变量的分层必填（2026-09-20 冻结）

`DATABASE_URL`、`AUTH_SECRET` 在 env 根校验（`src/shared/validation/env.ts`，FND-001）中**保持 optional**：应用存在不依赖它们的运行入口（health、styleguide 及未来静态页），根校验强制会让这些路径和 CI 整体失败；根校验只保证「一旦提供必须合法」（连接串协议、secret 长度 ≥32）。

必填约束下沉到**使用方基础设施模块**，按能力显式强制：

- `src/infrastructure/database`：连接工厂创建客户端时若 databaseUrl 缺失，抛 `DEPENDENCY_UNAVAILABLE`（配置缺失语义，附变量名、不回显取值），不允许驱动抛出含义不清的 URL 错误。
- `src/infrastructure/auth`：会话签名模块以**工厂 + 显式注入**实现（`createSessionSigner({ secret })`）；生产组合根从 env 注入，缺失即在装配期失败（启动暴露，而非首个请求时才暴露）。
- 测试纪律：单元/集成测试经工厂注入固定测试 secret、经仓储接口注入 fake 实现——`check` 链在不配置 `DATABASE_URL`/`AUTH_SECRET` 的环境也能跑；真机 db 测试的 `TEST_DATABASE_URL` 同样经连接工厂注入。
- env.ts 中「Phase 0 尚未接入数据库」的过时注释随本批实现更新。

## 11. 发布和迁移策略

- 数据库迁移先在测试环境执行。
- 迁移前备份并记录受影响表。
- 优先执行向后兼容的加字段/加表迁移。
- 迁移工具＝**Drizzle Kit**：schema（`drizzle/`，经 §2 目录契约）经 `db:generate` 生成版本化 SQL 迁移文件，**迁移文件必须入库**（评审与回滚依据），经 `db:migrate` 只向前应用；禁止手改已发布的迁移文件，需要变更时新增迁移。
- 本地模式存储的最终形态（本机 PG 或嵌入式 SQLite）挂账（T-004），数据访问统一经仓储与 Drizzle，切换不波及业务层。
- 删除字段分为停止读、停止写、再删除三步。
- 每次发布包含回滚说明。
- 重大 AI 或同步功能使用 feature flag。
- 生产发布后观察错误率、延迟、同步失败和 AI 调用量。

## 1. 使用说明

本清单用于产品设计与技术架构设计定型前的决策确认。每一项都按照以下结构记录：

- 建议：我基于当前需求、预算、人力和运维风险给出的默认方案。
- 原因：为什么推荐这个方案。
- 影响：确认后会影响哪些开发和运维内容。
- 状态：待确认，除非项目负责人明确同意，否则不写入最终设计。

如果你不同意某项，直接回复对应编号和修改意见即可。没有列出的实现细节，在不改变已确认约束的前提下，按工程最佳实践落地。

## 2. 当前不可改变的约束

以下内容已经确认，不再作为开放选项：

1. 第一阶段面向个人使用和 5–20 人邀请测试。
2. 第一阶段覆盖排程、目标、习惯、执行记录、开销和复盘，但各模块保持轻量。
3. Web/PWA 优先，不在第一阶段同时开发原生 iOS/Android。
4. 外部 AI API 可以使用，但 AI 只能作为增强功能，核心功能不能依赖 AI。
5. 第一阶段不做银行、支付、投资、医疗、社交和复杂多人协作。
6. 每月现金预算约百元，必须控制第三方服务和 AI 调用成本。
7. 用户数据必须可导出、删除和恢复，不能被平台锁定。
8. 采用苹果产品式的克制、留白、清晰层级和高质量细节作为视觉参考，但不复制苹果官网的素材、品牌元素或页面。

## 3. 产品设计决策

### P-001 产品首页与信息架构

**建议：**采用“今日”作为首页，底部或侧边导航包含：今日、收件箱、目标、开销、复盘、设置。

**原因：**用户打开应用最需要知道的是现在做什么、接下来做什么和今天需要调整什么，而不是查看完整数据报表。

**影响：**首页必须优先加载时间线和下一步行动；统计、长期目标和设置放在第二层。

**状态：待确认。**

### P-002 产品视觉方向

**建议：**高级简约、内容优先、低饱和中性色 + 一个品牌强调色。整体参考苹果产品的克制感，而不是复刻官网风格。

建议规则：

- 大留白、清晰分组、少量边框。
- 卡片只用于区分上下文，不把每个元素都做成卡片。
- 一屏只突出一个主要行动。
- 颜色用于表达状态，不用于装饰堆叠。
- 动效以 150–250ms 的过渡和状态反馈为主，不使用持续动效干扰注意力。
- 文案中性、温和、非评判，不出现“失败”“懒惰”“你又没完成”等羞辱式语句。

**状态：待确认。**

### P-003 视觉主题

**建议：**第一阶段先做高质量浅色主题，并保留暗色主题的设计变量；暗色主题作为 P1，不阻塞核心发布。

**原因：**同时维护两套完整主题会增加视觉验收和组件测试成本。先保证浅色主题统一，比两套粗糙主题更适合当前人力。

**状态：待确认。**

### P-004 设备优先级

**建议：**手机竖屏优先，桌面宽屏完整适配；平板作为中间断点适配，不单独设计复杂平板布局。

**原因：**生活记录和提醒主要发生在手机，计划整理和复盘在桌面端更舒适。

**状态：待确认。**

### P-005 首页核心操作

**建议：**首页固定突出三个动作：添加、开始/完成当前行动、记录/调整。

**影响：**快捷添加、当前行动、状态更新必须在一到两次点击内完成；复杂分类和关联信息放到后续编辑。

**状态：待确认。**

### P-006 时间线交互

**建议：**时间线采用“固定事项 + 任务时间块 + 未安排区 + 当前时间线”结构，支持拖拽调整，但所有自动建议必须先预览再确认。

**原因：**避免系统擅自重排用户的生活安排；拖拽适合桌面，移动端需要提供点击编辑和底部操作栏作为替代。

**状态：待确认。**

### P-007 复盘表达方式

**建议：**复盘以“少量数字 + 文字洞察 + 下一步动作”组合呈现，不做复杂仪表盘。

**状态：待确认。**

### P-008 AI 入口

**建议：**AI 不做独立聊天首页，采用上下文入口：任务输入框旁的“帮我拆分”、时间线中的“帮我安排”、复盘页中的“生成建议”。

**原因：**AI 的价值是减少输入和整理成本，而不是把产品变成泛聊天应用。

**状态：待确认。**

### P-009 语言和本地化

**建议：**第一阶段只做简体中文，但数据模型保留语言和时区字段；日期、星期、金额和提醒按中文用户习惯展示。

**状态：待确认。**

### P-010 用户测试入口

**建议：**首轮采用邀请制，不做公开注册和公开分享。测试用户可通过邀请码或手动创建测试账号进入。

**原因：**控制成本、权限和反馈范围，避免还未验证留存就承担公开运营成本。

**状态：待确认。**

## 4. 数据和系统架构决策

### T-001 总体架构形态

**建议：**采用模块化单体，而不是微服务。

```text
Web/PWA
   ↓
应用层/API 层
   ↓
领域模块：任务｜目标｜排程｜执行｜习惯｜开销｜复盘｜提醒｜AI
   ↓
数据访问层
   ↓
PostgreSQL / 本地 IndexedDB / 外部 AI API
```

**原因：**1–2 人维护微服务会引入部署、监控、网络和数据一致性成本。模块化单体仍可以保持清晰边界，未来再拆分。

**状态：待确认。**

### T-002 前端技术栈

**建议：**TypeScript + React + Next.js + PWA 能力；样式使用原生 CSS 自定义属性（设计令牌）+ CSS Modules；组件层自建轻量组件。

**原因：**生态成熟、AI 训练资料多、适合 Web/PWA 和服务端 API 集成；TypeScript 可减少数据形状和异步调用错误。

**样式方案（2026-09-17 确认）：**不引入 Tailwind CSS，采用原生 CSS 自定义属性 + CSS Modules。

- 设计系统是闭集且很小（8 个语义色、5 级字阶、4px 间距、3 个圆角、4 个断点、极少阴影，见《UI 页面规范》§2），令牌的最终形态就是 CSS 变量，不需要框架再做一层转译；原型已用该形态完整实现并验证。
- 语义色纪律可以机器执行（令牌文件之外禁止 hex/rgb 字面量）；Tailwind 默认调色板（`bg-white`、`text-gray-*` 等）天然绕过语义令牌，要管住必须额外禁用默认色板并配 lint，对当前规模不划算。
- 零新依赖：CSS Modules 与 CSS 变量由 Next.js 内置支持，不增加锁文件来源与构建配置面。
- 深色主题路线简单：未来只替换变量值，引用方零改动。
- 可逆性：将来若引入 Tailwind（v4+），可通过 `@theme` 直接消费同一批变量叠加在现有体系上；反向路径（先铺满工具类再退回变量）需要重写组件。本决策保留双向门。

**重开条件：**UI-003 完成后，若一次性布局样式的实际成本显著、或组件规模超出轻量自建的合理边界，凭实际数据重开本决策；在此之前任何 UI 任务不得自行引入 Tailwind 或其他样式框架。

**组件层：**UI-001/UI-002 阶段不引入第三方无障碍组件库，自建轻量组件（键盘焦点与触控尺寸要求见开发任务清单）；将来若引入第三方组件库需单独决策。

**状态：**TypeScript + React + Next.js 已随 FND-001 落地确认（Next 16.3.5 / React 19.3）；样式方案 2026-09-17 确认；PWA 能力待对应功能阶段再确认。

### T-003 后端技术栈

**建议：**第一阶段使用同一 TypeScript 仓库中的 Next.js API 路由/服务端模块，不额外拆独立 Python 或 Node 后端。

**原因：**减少语言、仓库、部署和类型同步成本；领域服务仍需要与页面组件分离，不能把业务逻辑直接写在 UI 中。

**状态：待确认。**

### T-004 数据库

**建议：**PostgreSQL 作为云端主数据库；ORM 使用 Drizzle；输入和输出使用 Zod 等运行时 schema 校验。

**原因：**目标、任务、时间块、执行记录和开销存在关系，关系型数据库更适合一致性、查询和迁移；金额、时间和权限也更容易明确表达。

**状态：待确认。**

### T-005 数据主源：云端优先还是本地优先

**建议：**采用“云端主数据 + 本地缓存/草稿”的折中方案：

- 账号模式下，PostgreSQL 是跨设备数据主源。
- 浏览器本地保存最近数据和未提交草稿。
- 网络失败时允许创建本地草稿，恢复网络后再提交。
- 暂不承诺复杂的多端离线协同编辑。
- 本地模式可以独立使用，并支持 JSON 导出。

**原因：**真正的全量 local-first 同步需要冲突合并、删除墓碑、版本向量和恢复机制，超出当前低人力预算；完全云端又会损失弱网容错。

**这是最需要确认的架构决策之一。状态：待确认。**

### T-006 账户与身份

**建议：**同时保留本地单用户模式和邀请制云端账号模式。云端账号第一阶段采用邮箱 + 密码或魔法链接中的一种，不接社交登录。

**原因：**本地模式可以快速试用，云端模式支持邀请测试和多设备；不接第三方社交登录可减少 OAuth 配置和隐私依赖。

**待确认内容：**是否接受第一阶段同时维护“本地模式 + 云端模式”？

**状态：待确认。**

### T-007 API 风格

**建议：**使用版本化 REST/JSON API，路径采用 `/api/v1/...`，并生成 OpenAPI 文档；前端通过类型生成或共享 schema 使用接口。

**原因：**接口边界清楚，方便未来接入原生客户端、脚本、测试和外部工具；比只依赖前端内部函数更易维护。

**状态：待确认。**

### T-008 ID、时间和金额

**建议：**

- 主键使用 UUID。
- 数据库存储时间使用 UTC；记录用户时区和原始本地时间语义。
- 重复任务按用户时区计算下一次发生时间。
- 金额使用整数分或 Decimal，禁止用浮点数存储金钱。
- 所有日期和时间计算使用成熟库，不手写夏令时和时区偏移。

**原因：**这是金额、跨日、重复任务和未来多设备场景的基础安全规则。

**状态：建议直接确认。**

### T-009 删除策略

**建议：**用户删除先进入回收状态/软删除；重要数据保留恢复窗口；账户彻底删除需要明确确认和异步处理。

**原因：**生活和财务记录误删不可逆，且软删除有助于同步和审计。

**状态：待确认。**

### T-010 事件和历史记录

**建议：**执行记录和开销记录采用追加式历史；任务名称、目标名称等变化不覆盖历史快照。

**状态：建议直接确认。**

### T-011 缓存策略

**建议：**第一阶段不引入 Redis；使用客户端缓存、数据库索引和必要的服务端短 TTL 缓存。只有性能指标证明需要时再增加 Redis。

**原因：**当前规模不需要额外缓存基础设施，引入后会增加失效、一致性和成本问题。

**状态：待确认。**

### T-012 异步任务和队列

**建议：**P0 不部署独立消息队列；AI 请求、导出和提醒先采用可控的服务端调用。若任务超过 30 秒、需要重试或出现并发峰值，再引入队列。

**状态：待确认。**

## 6. 安全、隐私与合规决策

### S-001 权限模型

**建议：**第一阶段只实现 `user` 和 `test_admin` 两种角色；默认每个用户只能访问自己的数据。

**状态：待确认。**

### S-002 AI 数据边界

**建议：**AI 请求采用最小数据原则；默认不发送完整历史，只发送当前任务或用户主动选择的复盘数据；不允许 AI 直接写正式数据，必须先生成草稿。

**状态：待确认。**

### S-003 敏感数据日志

**建议：**日志不记录完整任务名称、开销备注、目标理由、心情内容、密码和令牌；使用匿名用户 ID 和错误码。

**状态：建议直接确认。**

### S-004 安全基线

**建议：**HTTPS、服务端密钥、参数化查询、输入校验、输出编码、CSP、用户级数据隔离、限流、超时、重试退避和依赖漏洞扫描作为第一阶段最低基线。

**状态：建议直接确认。**

## 7. 代码质量和工程规范

以下内容按项目开发环境提供的 `universal-code-quality` 规范执行：

- 表现层、应用层、领域层、基础设施层分离。
- 采用按业务特性组织的模块结构，避免巨型组件和巨型服务。
- 输入边界校验，外部 API 返回视为不可信数据。
- 外部网络调用必须有超时、重试上限和退避。
- 任务、提醒、同步和 AI 调用必须考虑幂等和重复提交。
- 金额使用整数分或 Decimal，时间统一考虑 UTC、时区和夏令时。
- SQL 使用参数化查询，前端输出进行编码，禁止不安全 HTML 拼接。
- 核心路径和边界条件必须有测试。
- 破坏性迁移、批量删除和数据清理必须先备份、预览、确认并可回滚。
- 代码格式化、静态检查、测试和构建纳入 CI。

## 11. 第二轮反馈后的重新评估

### 11.1 产品设计结论

#### P-002 与 P-004 的关系：PC 先做，但视觉系统不能只为 PC 设计

P-002 的“高级简约”不是 PC Web 专属风格，而是整个产品的设计语言。第一阶段先实现 PC Web，但从第一天建立跨端设计基础：

- 使用响应式布局和设计令牌，而不是把尺寸写死在 PC 页面中。
- 组件同时定义桌面、平板和手机断点行为。
- 触控区域、手势替代方案和窄屏信息层级提前预留。
- 页面业务状态与 UI 组件分离，未来移动端复用领域状态和 API。
- 不把拖拽作为唯一交互，移动端必须有点击、底部操作栏或长按替代方案。

因此，确认后的表述为：

> 第一阶段优先开发 PC Web，但产品视觉系统、组件 API、响应式布局和后端接口从第一天为后续移动端预留空间。

#### P-008 智能向导与 AI 建议需要分层

“智能向导”不应等同于一个无边界的聊天机器人。建议拆为三层：

1. **确定性引导**：首次使用、创建目标、建立第一个例程、完成第一次复盘的步骤提示；不依赖 AI，结果可预测。
2. **上下文帮助**：在页面中解释字段、提供示例、提示下一步；可以由规则驱动。
3. **个性化建议**：根据用户主动授权的数据，生成任务拆解、排程、复盘和目标建议；使用外部 AI，但必须草稿确认。

这样既能提供“指引客户怎么使用产品”的体验，也不会因为 AI 失效而导致产品无法使用。

建议将确定性引导和上下文帮助纳入 P0/P1，将个性化 AI 建议保留为 P1/P2 增强能力。

#### P-009 多语言与多时区需要从第一天预留

第一阶段可以只上线简体中文，但不能把中文文本和时间逻辑硬编码在组件中：

- 所有用户可见文案使用消息 key 和语言资源文件。
- 日期使用用户时区显示，数据库统一存 UTC。
- 用户保存 `locale`、`timezone` 和 `currency`。
- 重复任务按照用户时区计算，不按服务器时区计算。
- 金额至少保存货币代码，不把人民币符号写死在业务逻辑中。
- 文案使用 ICU/标准国际化格式，避免后续翻译时无法处理复数、日期和变量。

这会增加少量前期工作，但能避免后续多语言、多时区上线时大规模返工。

### 11.2 T-001：为什么推荐 PostgreSQL 和模块化单体

#### PostgreSQL 的优点

本项目的数据不是简单的几张独立表，而是存在明确关系和一致性要求：

- 目标包含行动，行动关联任务和执行记录。
- 时间块涉及冲突、重复、时区和状态变化。
- 开销涉及金额精度、分类、目标关联和复盘汇总。
- 用户数据需要严格按用户隔离。
- 导入、删除、恢复和同步需要事务保证。

PostgreSQL 适合本项目的原因：

1. **关系和约束强**：外键、唯一约束、检查约束和事务可以保护数据一致性。
2. **查询能力成熟**：周复盘、时间线、分类汇总和筛选需要关联查询和索引。
3. **数据类型可靠**：日期时间、JSON、数组和精确数值类型都比较成熟。
4. **适合未来扩展**：可以加入全文搜索、JSONB 配置、审计表和统计查询，而不必立即换数据库。
5. **托管选择多**：适合低运维预算下使用托管数据库，并支持备份和恢复。
6. **权限能力较强**：可以配合服务端权限和行级安全策略隔离用户数据。

PostgreSQL 的代价是需要认真管理迁移、索引、备份和连接数；这些成本会通过模块化设计和托管服务降低，但不能消失。

#### 为什么不是微服务

微服务适合有多个独立团队、明确的服务边界、较大流量或独立扩缩容需求的组织。当前项目只有 1–2 人，微服务会额外增加：

- 多个仓库或多个构建产物。
- 服务间鉴权和网络调用。
- 分布式日志、追踪和告警。
- 跨服务事务和数据一致性。
- 多套部署、版本和回滚流程。
- 更高的云资源和排障成本。

这些投入不会直接提升第一阶段的用户价值，反而会让 AI 生成和维护代码更困难。

因此推荐**模块化单体**，但不是把所有代码随意堆在一个项目里。要求是：

- UI、API 适配、应用服务、领域规则和基础设施分层。
- 每个业务模块有清晰边界和公开接口。
- 页面不能直接查询数据库。
- 领域模块不能依赖 Next.js 页面组件。
- 外部服务通过接口适配器接入。
- 关键模块使用契约测试。

这样未来如果用户量或团队规模达到拆分条件，可以按模块抽取服务，而不是重写业务规则。

### 11.3 T-002/T-003：是否会导致后端重构

不会采用“把后端逻辑写进页面，然后未来再重构”的方案。修订后的建议是：

```text
PC Web / 未来移动端
          ↓
版本化 REST API（/api/v1）
          ↓
应用服务层
          ↓
领域模块
          ↓
仓储接口
          ↓
PostgreSQL、本地同步、AI、通知等适配器
```

Next.js 只是第一阶段的运行和部署载体，不是领域业务的归属位置。移动端未来直接调用同一套 `/api/v1` 接口，不需要重写业务逻辑。

需要明确禁止的做法：

- React 组件直接访问数据库。
- 页面 Server Action 里混入完整业务规则。
- API 路由中直接拼接 SQL 并重复编写校验。
- 为了省事把任务、排程、开销和 AI 写进一个巨型服务文件。

推荐的目录边界是：

```text
app/                         # 页面与 API 适配入口
src/modules/tasks/           # 任务领域与应用服务
src/modules/scheduling/      # 排程领域与应用服务
src/modules/expenses/        # 金额与开销领域
src/modules/ai/              # AI 用例与提供商适配
src/shared/                  # 日期、金额、错误、校验等共享基础
src/infrastructure/          # DB、认证、通知、外部服务实现
```

因此，当前推荐保留 Next.js 单仓库，但按 API-first 和领域边界设计。只有未来出现独立团队、明显流量、单模块需要独立扩缩容或合规隔离时，才考虑拆成独立后端服务。

### 11.4 T-005：草稿必须支持跨设备可见

你的质疑成立：如果草稿只存在浏览器本地，换设备后确实看不到，也不符合生活管理产品的使用预期。

修订后的建议为：

#### 云端账号模式

- 草稿是正式的数据实体，保存到 PostgreSQL。
- 移动端创建的草稿，联网后可以在 PC 端看到。
- 本地先写入浏览器缓存和待同步队列，再提交云端。
- 云端确认成功后，标记本地操作已同步。
- 换设备登录后，从云端恢复草稿和正式数据。

#### 断网模式

- 允许创建和编辑本地待同步草稿。
- 每条本地操作有客户端生成的 UUID、创建时间和操作序号。
- 网络恢复后按顺序提交。
- 提交失败不能静默丢弃，必须显示待同步状态。

#### 冲突策略

- 执行记录和开销优先采用追加式记录，避免覆盖另一设备的历史。
- 任务和目标修改带版本号；发现版本冲突时，优先提示用户选择，而不是静默覆盖。
- 删除使用墓碑记录，避免离线设备重新上传已删除数据。
- 同步接口使用幂等键，重复提交不能生成重复开销或重复执行记录。

#### 本地单用户模式

- 本地模式数据保存在本机 IndexedDB。
- 本地模式不承诺自动跨设备同步。
- 用户可以导出 JSON，之后登录云端模式并导入。

因此，第一阶段需要区分“本地模式”和“云端账号模式”，并把云端账号模式作为邀请测试的默认模式。完整的多端离线协同编辑仍不在第一阶段承诺范围内。

这会比“单纯本地缓存”增加约 1–2 周的开发和测试工作，但能避免未来为了跨设备而重做数据层。

### 11.5 T-011：缓存策略保留扩展口

同意保留扩展口。具体做法：

- P0 不引入 Redis。
- 定义 `CacheStore` 接口，业务层不直接依赖具体缓存产品。
- P0 只使用客户端缓存、数据库索引和少量短 TTL 服务端缓存。
- 将来需要 Redis 时，只替换基础设施实现，不修改领域规则。
- 所有缓存必须定义 TTL、失效策略和降级行为。

### 11.6 O-005：第三方错误追踪是否有信息泄露风险

有风险，尤其是以下情况下：

- 错误堆栈中包含请求参数或用户内容。
- Session Replay 记录用户输入、开销和目标页面。
- 日志中直接写入完整任务名称、金额备注或 AI prompt。
- 第三方服务的地区、保留期和数据处理条款不符合项目要求。

修订后的建议：

#### P0

- 不接入 Session Replay、录屏和行为回放。
- 不接入第三方产品分析平台。
- 优先使用托管平台日志 + 自有结构化日志。
- 服务端日志统一脱敏，默认只记录错误码、版本、请求 ID、匿名用户 ID、耗时和技术堆栈。
- 不记录完整任务、开销备注、目标理由、心情内容、AI prompt 和 token。

#### P1

如果后续仍需要第三方错误追踪，必须先完成：

- `beforeSend` 或等价脱敏钩子。
- 关闭 Session Replay。
- 明确数据地区、保留期限和删除机制。
- 检查服务条款和数据处理协议。
- 用测试数据验证不会上传敏感字段。
- 设置服务端数据采集开关和紧急关闭开关。

因此，第三方错误追踪不是绝对禁止，但不应默认进入 P0。建议先用脱敏日志完成邀请测试。

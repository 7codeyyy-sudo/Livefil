## 1. 文档说明

### 1.1 编写目的

本说明书将项目立项阶段的业务诉求转化为可开发、可测试、可验收的软件需求，作为以下工作的共同依据：

- 产品流程和原型设计。
- 技术架构与数据模型设计。
- AI 辅助开发任务拆分。
- 测试用例和验收标准编写。
- 第一阶段范围控制与变更评审。

### 1.2 需求来源

当前需求来自：

1. 项目发起人对生活排程、记录、开销和目标管理的描述。
2. 《生活自律与生活管理产品调研报告》中的行为科学和竞品分析。
3. 《项目立项书》中确认的第一阶段范围、预算、工期和风险约束。

当前尚未完成正式外部用户访谈，因此文档中的用户痛点、使用频率和部分阈值属于待验证假设，不应直接视为市场事实。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 生活领域 | 健康、工作、财务、家务、关系、兴趣等较稳定的生活分类 |
| 目标 Goal | 用户希望在一段时间内实现的结果或方向 |
| 行动 Action | 为推进目标而可以执行的具体行为 |
| 任务 Task | 一次性或重复发生的待完成事项 |
| 例程 Routine | 由多个步骤组成、可重复执行的一组任务 |
| 时间块 Schedule Block | 被安排到特定日期和时段的任务或例程 |
| 执行记录 Execution Log | 任务实际完成、部分完成、跳过、延期等结果 |
| 最低版本 Minimum Version | 用户低精力时仍可完成的最小行动版本 |
| 复盘 Review | 对计划、执行、开销和下一步调整的回顾 |
| MVP | 第一阶段可验证版本；本项目第一阶段是功能覆盖完整、深度适中的版本 |
| P0/P1/P2 | 必须有、建议有、后续再做的优先级 |

## 2. 业务背景与目标

### 2.1 业务背景

用户往往分别使用日历、待办、习惯、记账和备忘录工具，但这些信息缺少共同的执行和复盘层。项目希望建立一个低负担的个人生活管理系统，将以下信息连接起来：

```text
目标 → 行动 → 今日排程 → 实际执行 → 开销/精力记录 → 日周复盘 → 下一步调整
```

### 2.2 业务目标

| 编号 | 业务需求 | 可验证结果 |
|---|---|---|
| BR-001 | 建立时间、行为、开销、目标之间的关联 | 用户能够查看某个行动的计划、实际执行状态以及可选关联开销 |
| BR-002 | 降低生活记录成本 | 快速记录常规操作目标不超过 60 秒 |
| BR-003 | 提高计划的现实可执行性 | 用户可以调整时长、延期、缩小为最低版本，而不是只能完成或失败 |
| BR-004 | 支持恢复而非惩罚 | 系统不以连续打卡作为唯一核心指标，并提供恢复/重新安排能力 |
| BR-005 | 让复盘产生下一步行动 | 日/周复盘能够产出保留、缩小、延期或删除等明确调整 |
| BR-006 | 控制第一阶段成本和复杂度 | 采用 Web/PWA，手动记账，外部 AI 为增强功能，不接银行和支付系统 |
| BR-007 | 保障用户数据可控 | 用户可导出、删除和恢复自己的核心数据 |

### 2.3 成功指标

以下为第一阶段内部验收目标，需通过首轮测试校准：

- 60% 以上测试用户首次使用时创建至少一个今日行动。
- 60% 以上测试用户完成一次“计划 → 执行 → 记录”闭环。
- 快速记录平均耗时不超过 60 秒。
- 至少 60% 的活跃测试用户每周使用 3 天以上。
- 4 周后至少 30% 的邀请用户仍在使用核心闭环。
- 至少一半访谈用户能够说出一个由系统记录带来的生活调整。

## 3. 用户与角色

### 3.1 第一阶段用户角色

| 角色 | 权限范围 | 说明 |
|---|---|---|
| 个人用户 | 管理自己的全部生活数据和设置 | 第一阶段核心角色 |
| 测试管理员 | 查看匿名化产品指标、处理测试反馈、管理测试资格 | 仅限项目负责人或维护者 |
| AI 服务 | 仅处理用户明确提交的内容，不能直接拥有数据管理权限 | 外部服务，不是业务用户 |

第一阶段不支持家庭、伴侣、团队、教练、监督者和公开社交角色。

### 3.2 权限原则

- 默认每个用户只能访问自己的数据。
- 测试管理员不能默认读取用户的完整任务、开销、备注或心情内容。
- AI 只接收完成当前请求所需的最小数据。
- 删除、导出、修改账户和隐私设置必须由用户主动触发。

## 4. 用户需求

### 4.1 用户需求清单

| 编号 | 用户需求 | 优先级 |
|---|---|---:|
| UR-001 | 我想快速记录突然想到的事情，不必立即分类 | P0 |
| UR-002 | 我想把长期目标拆成这周和今天能做的行动 | P0 |
| UR-003 | 我想看到今天接下来该做什么，而不是面对一堆列表 | P0 |
| UR-004 | 我想在任务变动时方便地延期、缩短或重新安排 | P0 |
| UR-005 | 我想记录任务实际完成了多少，而不是只有完成/未完成 | P0 |
| UR-006 | 我想为重复生活事项建立例程和习惯 | P0 |
| UR-007 | 我想快速记录一笔开销，并知道它属于什么生活领域 | P0 |
| UR-008 | 我想知道一笔开销是否与某个目标或行动有关 | P0 |
| UR-009 | 我想在周末看到计划与现实的差异 | P0 |
| UR-010 | 我想在状态不好时执行一个更小的最低版本 | P0 |
| UR-011 | 我想收到关键事项提醒，但不希望被大量通知打扰 | P0 |
| UR-012 | 我想把自己的数据带走，不被平台锁定 | P0 |
| UR-013 | 我想用自然语言让系统帮我拆任务或整理计划 | P1 |
| UR-014 | 我想记录当天的精力和心情，帮助理解执行偏差 | P1 |
| UR-015 | 我想在手机和电脑之间继续使用同一份数据 | P1，需验证 |

### 4.2 关键用户场景

#### 场景 A：快速收集想法

用户在工作、通勤或睡前想到“下周要买跑鞋”，打开收件箱，输入一句话并保存。系统不强制用户立即填写日期、分类、优先级和目标。

验收重点：输入快、保存快、之后找得到、不因未分类而丢失。

#### 场景 B：从目标到今日行动

用户创建“改善体能”目标，设置本周行动“运动 3 次”，再将其中一次安排到周三 19:00，时长 30 分钟，最低版本为散步 8 分钟。

验收重点：目标、行动、时间块和最低版本之间关系清晰。

#### 场景 C：计划被打乱

用户临时加班，无法完成原定运动。用户可以选择延期、执行最低版本或跳过并记录原因。系统不把行为显示为不可恢复的失败。

验收重点：调整成本低，不会产生重复任务或错误统计。

#### 场景 D：记录开销

用户输入“晚饭 36 元，餐饮”，系统生成一笔手动记账记录，用户可选关联“健康饮食”领域或“旅行”目标。

验收重点：记录迅速、金额准确、关联可选、不强迫用户补全复杂财务信息。

#### 场景 E：周复盘

用户查看本周完成情况、经常延期的任务、计划时长与实际时长偏差、开销摘要，并确认下周保留、缩小、延期或删除的事项。

验收重点：复盘输出可执行调整，而不是只显示图表。

## 5. 功能需求

### 5.1 功能优先级规则

- P0：第一阶段发布前必须完成，否则核心闭环不成立。
- P1：第一阶段可以完成，但如果影响 P0 进度可延期。
- P2：第一阶段不实现，保留为后续需求。

### 5.2 账户、初始化与设置

#### FR-001 用户进入与数据模式（P0）

系统应支持以下至少一种模式：

1. 本地单用户模式：无需登录即可使用核心功能。
2. 测试账号模式：用户登录后进行云端保存和同步。

推荐先实现本地模式，再根据邀请测试决定是否启用云端账户和同步。

验收标准：

- 用户可以明确知道当前处于本地模式还是云端模式。
- 未登录时核心任务、目标、习惯和记账功能可使用。
- 登录失败不会导致本地数据丢失。

#### FR-002 初始化设置（P0）

首次使用时，用户可以设置：

- 昵称或显示名，可跳过。
- 时区和周起始日。
- 常用生活领域。
- 一般可安排时间段，可跳过。
- 提醒总开关和安静时段。

系统不得要求用户在首次使用时创建大量目标或完成复杂教程。

#### FR-003 设置管理（P0）

用户可以修改：

- 个人信息。
- 时间格式和周起始日。
- 默认任务时长和缓冲时间。
- 默认生活领域。
- 提醒权限和安静时段。
- AI 使用许可和数据发送提示设置。

### 5.3 收件箱与任务

#### FR-010 快速创建任务（P0）

用户可以从任意主要页面创建任务，至少填写任务名称；日期、时长、领域、目标、优先级和备注均可选。

系统应支持：

- 保存到收件箱。
- 保存到指定日期。
- 设置预计时长。
- 设置一次性或重复规则。
- 设置任务所属生活领域。
- 设置可选目标和行动关联。

#### FR-011 收件箱整理（P0）

用户可以对收件箱任务执行：

- 安排到日期和时间。
- 添加或修改生活领域。
- 关联目标。
- 转成例程步骤。
- 归档。
- 删除。

系统不强制用户一次整理完所有收件箱内容。

#### FR-012 任务状态（P0）

任务状态至少包括：

- 未开始。
- 进行中，可选。
- 完成。
- 部分完成。
- 延期。
- 跳过。
- 已归档。

部分完成时，用户可以记录实际完成量、实际时长或一句备注。

### 5.4 目标、行动与生活领域

#### FR-020 创建和管理生活领域（P0）

系统应提供默认生活领域，用户可以新增、重命名、停用和排序。

默认建议：健康、工作/学习、财务、家务、关系、兴趣、休息。

停用领域不会删除历史数据，已有记录仍可查看。

#### FR-021 创建目标（P0）

目标至少包括：

- 名称。
- 所属生活领域。
- 可选描述或理由。
- 开始日期和截止日期，可为空。
- 状态：进行中、已完成、暂停、已放弃。
- 可选衡量方式。

#### FR-022 创建目标行动（P0）

目标下可以建立多个行动。行动至少包括：

- 行动名称。
- 重复频率或本周次数，可选。
- 最低版本，可选但推荐填写。
- 预计时长。
- 可安排到具体日期。
- 当前状态。

#### FR-023 目标进度（P0）

系统应分别显示：

- 目标结果进度，可由用户手动更新。
- 行动完成进度，由执行记录汇总。

系统不得把行动完成率直接解释为目标已经实现。

### 5.5 今日时间线与排程

#### FR-030 今日视图（P0）

今日视图应展示：

- 日期和当前时间。
- 固定事项。
- 时间块任务。
- 未安排任务。
- 习惯和例程。
- 已完成、部分完成、延期和跳过状态。
- 预计空闲时间或计划负荷提示。

用户可以切换日视图、周视图和列表视图。

#### FR-031 安排时间块（P0）

用户可以为任务设置开始时间和预计时长。系统应支持：

- 拖拽调整日期和时间。
- 修改预计时长。
- 拆分为多个时间块，可选。
- 在任务之间显示或计算缓冲。
- 将未安排任务放入某一天。

#### FR-032 冲突和超载提示（P0）

当任务与固定事项重叠，或当天计划明显超出用户设置的可安排时间时，系统应提示冲突或超载。

提示必须是可解释的，不得自动删除或移动用户任务。用户可以选择：

- 保留冲突。
- 缩短任务。
- 移到其他时间。
- 延期。
- 删除。

#### FR-033 重复任务和例程（P0）

系统应支持按天、周、指定星期重复任务。例程由多个步骤组成，可以整体安排，也可以查看单步状态。

修改重复规则时，应明确询问是修改当前一次还是未来所有发生。

#### FR-034 最低版本（P0）

用户可以为行动或例程设置最低版本，例如：

- 跑步 30 分钟的最低版本是走路 8 分钟。
- 阅读 30 分钟的最低版本是阅读 2 页。

最低版本完成后，系统应记录为“最低版本完成”，不应伪装成完整版本。

### 5.6 执行记录与恢复

#### FR-040 开始和结束执行（P0）

用户可以对任务执行开始、暂停、完成或手动记录实际时长。计时器可以作为辅助，但用户不应被强制使用计时器。

#### FR-041 记录执行结果（P0）

完成任务时，系统允许用户选择：

- 完成。
- 最低版本完成。
- 部分完成。
- 跳过。
- 延期。

可选填写：实际时长、原因、备注、心情和精力。

#### FR-042 恢复模式（P0）

当用户连续多天未完成计划或主动选择恢复模式时，系统可以建议：

- 减少今日任务数量。
- 将任务切换为最低版本。
- 暂停非关键提醒。
- 重新安排未完成任务。

系统不得使用羞辱、惩罚或“连续记录归零”等强制文案。

### 5.7 开销记录

#### FR-050 快速记账（P0）

用户可以快速创建开销，必填字段为：

- 金额。
- 币种，第一阶段默认人民币，可扩展。
- 分类。
- 日期。

可选字段为：

- 支付方式。
- 备注。
- 生活领域。
- 目标或行动关联。
- 标签。

#### FR-051 开销分类（P0）

系统提供默认分类，例如餐饮、交通、居住、健康、学习、娱乐、购物、关系、其他。用户可以新增、重命名、停用分类。

停用分类不会删除历史开销。

#### FR-052 开销编辑和删除（P0）

用户可以编辑和删除自己的开销。删除操作需要二次确认，并支持短时间内撤销或从回收区恢复。

#### FR-053 开销与目标关联（P0）

开销可以关联一个目标、一个行动或一个生活领域，也可以不关联。系统不得强制所有开销都绑定目标。

#### FR-054 简单预算摘要（P1）

系统可以允许用户为生活领域或分类设置月度预算，展示已用金额和剩余金额。第一阶段不实现复杂账户、负债、投资和银行流水。

### 5.8 日复盘与周复盘

#### FR-060 日复盘（P0）

每日复盘至少包含：

- 今天完成了什么。
- 哪件事最影响计划。
- 明天要保留、缩小、延期或删除什么。

用户可以跳过复盘，也可以只回答其中一个问题。

#### FR-061 周复盘（P0）

周复盘应展示：

- 本周计划任务数和执行状态。
- 完成、部分完成、跳过、延期数量。
- 计划时长与实际时长的简单对比。
- 重复延期任务。
- 目标行动完成情况。
- 各分类/生活领域开销摘要。
- 用户主动确认的下周调整。

#### FR-062 复盘调整（P0）

用户可以从复盘页面直接执行：

- 保留任务。
- 缩短或改为最低版本。
- 移到下周。
- 暂停目标。
- 删除任务。
- 调整提醒频率。

### 5.9 提醒与通知

#### FR-070 提醒规则（P0）

用户可以为任务、例程和复盘设置提醒。支持：

- 提醒时间。
- 是否重复。
- 是否允许在安静时段提醒。
- 关闭单条提醒。
- 全局关闭提醒。

#### FR-071 通知降噪（P0）

系统应提供通知等级：

- 关键事项。
- 普通任务。
- 复盘提示。

默认不对所有未完成任务重复轰炸。通知失败时，应用内仍应显示待处理提醒。

### 5.10 AI 增强

#### FR-080 AI 任务拆解（P1）

用户提交一段自然语言后，AI 可以建议：

- 任务名称。
- 子步骤。
- 预计时长。
- 可能的生活领域。
- 可选计划时间。

AI 结果必须经过用户确认后才能写入正式数据。

#### FR-081 AI 日程建议（P1）

系统可以根据用户选择的任务、固定事项、预计时长和可用时间给出排程建议。建议必须可编辑、可拒绝、可撤销。

#### FR-082 AI 开销解析（P1）

用户可以提交“午饭 35 元，餐饮”一类文本，AI 生成开销草稿。金额、日期和分类写入前必须展示确认界面。

#### FR-083 AI 复盘摘要（P1）

AI 可以根据用户主动选择的本周数据生成摘要和建议，但不得给出医疗、心理、投资或借贷判断。

#### FR-084 AI 调用控制（P0）

系统必须：

- 服务端保存 AI 密钥。
- 提示用户即将发送的数据范围。
- 支持关闭 AI。
- 记录调用次数和错误，不记录不必要的完整敏感内容。
- 设置每用户/每月调用上限。
- 处理超时、限流、服务不可用和空结果。

### 5.11 数据管理

#### FR-090 数据导出（P0）

用户可以导出自己的任务、目标、执行记录、习惯、开销、复盘和设置数据。第一阶段至少支持 JSON，建议增加 CSV。

#### FR-091 数据导入（P1）

用户可以导入本产品导出的 JSON 文件。导入前应显示数据预览，并允许选择覆盖、合并或取消。

#### FR-092 数据删除（P0）

用户可以删除单条记录、某一类型记录或整个账户数据。高风险删除操作需要明确确认。

#### FR-093 数据恢复（P0）

应用应支持至少一种恢复方式：本地撤销、回收区恢复或从最近备份恢复。

## 6. 非功能需求

### 6.1 性能需求

目标基线为第一阶段 5–20 名邀请用户，系统应按至少 100 个注册用户、20 个同时在线用户进行设计。

|---|---|---|

| NFR-PERF-002 | 常规新增、编辑、完成和记账操作接口响应 P95 ≤ 1.5 秒 | 接口压测/浏览器网络记录 |
| NFR-PERF-003 | 日/周复盘汇总查询 P95 ≤ 3 秒 | 使用代表性测试数据查询 |
| NFR-PERF-004 | 纯本地模式下新增和编辑操作应在 200ms 内反馈 | 本地性能测试 |
| NFR-PERF-005 | AI 请求不阻塞页面；正常情况下 30 秒内返回或明确失败 | 超时和异常测试 |
| NFR-PERF-006 | 典型用户至少拥有 5000 条任务/记录时，核心页面仍可分页或分段加载 | 数据量测试 |

### 6.3 可用性与可靠性

| 编号 | 要求 |
|---|---|
| NFR-REL-001 | 邀请测试期间月度可用性目标 ≥ 99%，计划维护除外 |
| NFR-REL-002 | 核心数据写入失败时必须明确提示，不能显示为成功 |

| NFR-REL-004 | 云端同步失败时，本地数据不得被覆盖或删除 |

|---|---|---|

| NFR-BACKUP-002 | 重要版本发布前执行手动备份 | 发布检查项 |
| NFR-BACKUP-003 | 恢复演练至少每月一次或每次重大数据结构变更后一次 | 可恢复性证明 |

| NFR-BACKUP-006 | 本地模式明确提示用户定期导出/备份 | 降低单设备丢失风险 |

### 6.5 安全需求

| 编号 | 要求 |
|---|---|
| NFR-SEC-001 | 所有云端传输使用 HTTPS/TLS |
| NFR-SEC-002 | AI、数据库和第三方服务密钥不得进入前端代码、仓库或客户端包 |
| NFR-SEC-003 | 用户数据查询必须执行服务端用户级权限校验，不能只依赖前端隐藏 |
| NFR-SEC-004 | 云端数据使用用户隔离策略；推荐采用数据库行级安全策略 |
| NFR-SEC-005 | 登录、导出、删除和 AI 调用等敏感操作记录安全事件日志 |
| NFR-SEC-006 | 所有输入进行长度、类型、金额范围和日期校验，防止注入和异常数据 |
| NFR-SEC-007 | 生产环境错误响应不得返回密钥、堆栈、SQL、内部路径或完整用户内容 |
| NFR-SEC-008 | 测试数据与真实用户数据分离；开发环境不得使用真实财务数据 |
| NFR-SEC-009 | 高风险操作支持二次确认；未来可增加重新认证 |
| NFR-SEC-010 | 第三方依赖需要锁定版本并定期检查已知漏洞 |

|---|---|
| NFR-PRIV-001 | 明确收集哪些任务、开销、目标、复盘和可选心情数据 |
| NFR-PRIV-002 | 心情、精力、开销备注和目标理由默认不用于公开展示 |
| NFR-PRIV-003 | AI 调用前说明发送的数据范围、用途和第三方处理情况 |
| NFR-PRIV-004 | 用户可以关闭 AI，并继续使用核心手动功能 |
| NFR-PRIV-005 | 用户可以导出和删除个人数据 |
| NFR-PRIV-006 | 系统不得将用户数据用于广告画像或未说明的训练用途 |
| NFR-PRIV-007 | 日志和统计默认使用匿名化 ID，不记录完整开销备注和目标内容 |
| NFR-PRIV-008 | 不提供医疗诊断、心理诊断、投资或借贷建议 |

### 6.7 权限和审计日志

第一阶段至少记录以下事件的时间、结果、匿名用户标识和版本：

- 登录成功/失败。
- 创建、修改、删除和恢复数据。
- 导出和导入数据。
- AI 调用开始、成功、失败、超时和额度耗尽。
- 权限错误和异常请求。
- 数据同步冲突。

日志要求：

- 不记录密码、令牌、完整 API 密钥。
- 不默认记录完整任务名称、开销备注和心情内容。
- 普通运行日志保留 30 天，安全事件日志保留 90 天，之后按成本和合规要求清理。
- 管理员只能查看必要的匿名化指标和错误信息。

### 6.8 兼容性

第一阶段目标支持：

- Windows、macOS、Android、iOS 上的现代浏览器。
- Chrome/Edge 最近两个大版本。
- Safari 最近两个大版本。
- Firefox 最近两个大版本，若 PWA 能力受限则提供 Web 访问降级。
- 手机竖屏优先，桌面宽屏适配。

降级要求：

- 不支持推送通知时，应用内提醒仍可用。
- 不支持安装 PWA 时，网站核心功能仍可使用。
- 不支持语音或 AI 时，手动输入仍完整可用。
- 不支持云端同步时，本地模式和导出功能仍可用。

### 6.9 可用性与无障碍

- 核心操作应有明确的成功、失败和保存状态反馈。
- 不只使用颜色区分完成、延期和冲突状态。
- 文字、按钮和触控区域适合手机操作。
- 支持键盘操作主要表单和任务列表。
- 错误提示说明如何修复，不只显示“出错了”。
- 重要操作提供撤销或回收机制。
- 首次使用不超过 3 分钟即可完成第一个今日行动。

### 6.10 可维护性与可观测性

- 代码按领域拆分：任务、目标、排程、执行、开销、复盘、AI、数据管理。
- P0 功能必须有单元测试或集成测试。
- 每次发布记录版本、变更、数据库迁移和回滚方式。
- 数据库结构变更必须可迁移、可回滚或有备份方案。
- 生产环境记录错误率、接口延迟、AI 调用量、通知失败和同步失败。
- 不允许 AI 代理在未经审查时一次性大范围修改核心业务代码。

## 7. 约束条件

### 7.1 人力约束

- 主要由 AI 进行代码实现。
- 现实人力为 1 人，最多 2 人。
- 项目负责人需要承担需求取舍、验收、测试和用户反馈。
- 无专职产品、设计、测试、运维和安全人员。

### 7.2 预算约束

- 常规现金预算约为每月 100 元左右。
- 现有 AI 编程套餐不等于产品运行时 AI API 预算。
- 必须控制外部 API、数据库、日志、带宽和通知服务成本。
- 第一阶段优先使用免费额度、静态部署和本地优先策略。

### 7.3 平台约束

- 第一阶段优先 Web/PWA，不做原生双端。
- 需要兼容手机和电脑浏览器。
- 必须支持无 AI、弱网或部分离线情况下的核心操作。

### 7.4 业务边界约束

- 不接银行、支付、证券和投资账户。
- 不做医疗或心理诊断。
- 不做自动扣款或自动财务决策。
- 不做默认公开分享和社交排名。

## 8. 数据需求

### 8.1 核心实体

```text
User
 ├─ LifeArea（生活领域）
 ├─ Goal（目标）
 │   └─ Action（目标行动）
 ├─ Task（任务）
 │   └─ ScheduleBlock（时间块）
 │       └─ ExecutionLog（执行记录）
 ├─ Routine（例程）
 ├─ Expense（开销）
 ├─ Review（复盘）
 └─ NotificationRule（提醒规则）
```

### 8.2 数据关系规则

- 一个用户拥有多个生活领域、目标、任务、开销和复盘。
- 一个目标属于一个生活领域，可拥有多个行动。
- 一个行动可生成多个时间块和执行记录。
- 一个任务可关联一个目标或行动，也可以不关联。
- 一笔开销最多关联一个目标、一个行动和一个生活领域，均为可选。
- 删除目标不应默认删除关联任务和开销，应转为无目标关联或进入回收状态。
- 历史执行记录应保留当时的名称、时长和状态快照，避免任务后续改名导致历史失真。

### 8.3 数据校验规则

- 金额必须为非负数，精度至少支持到分。
- 时间块结束时间必须晚于开始时间。
- 预计时长和实际时长不能为负数。
- 重复规则必须能生成明确的下一次发生时间。
- 删除和导入操作不能绕过用户权限。
- AI 生成的数据必须先处于草稿状态，确认后才写入正式实体。

## 9. 业务流程与状态

### 9.1 任务状态流转

```text
收件箱/未开始
   ├─→ 已安排
   ├─→ 已归档
   └─→ 已删除

已安排
   ├─→ 完成
   ├─→ 最低版本完成
   ├─→ 部分完成
   ├─→ 延期
   └─→ 跳过

延期
   └─→ 重新安排 → 已安排
```

### 9.2 开销状态

```text
AI/手动草稿 → 待确认 → 已保存 → 已编辑/已归档
                         └→ 删除/回收
```

### 9.3 AI 请求流程

```text
用户输入
  ↓
展示将要发送的数据范围和隐私提示
  ↓
服务端限流、脱敏和调用外部 API
  ↓
校验 AI 返回结构
  ↓
以草稿展示
  ↓
用户确认/编辑/取消
  ↓
写入正式数据
```

## 11. 验收策略

### 11.1 功能验收

每个 P0 需求至少需要：

- 正常路径测试。
- 空数据测试。
- 编辑和撤销测试。
- 网络失败或重复点击测试。
- 手机和桌面浏览器测试。
- 权限越权测试。

### 11.2 核心端到端验收

#### 验收用例 E2E-001：目标到执行

1. 创建生活领域“健康”。
2. 创建目标“改善体能”。
3. 创建行动“本周运动 3 次”。
4. 为其中一次行动设置周三 19:00、30 分钟、最低版本 8 分钟。
5. 将其加入今日时间线。
6. 记录为最低版本完成。
7. 在周复盘中看到行动状态和下一步建议。

通过条件：每一步数据关系正确，状态可追溯，复盘数据一致。

#### 验收用例 E2E-002：计划调整

1. 创建两个互相冲突的时间块。
2. 系统显示冲突提示。
3. 用户选择延期其中一个。
4. 系统只生成一个新的安排，不产生重复任务。
5. 原计划保留延期记录。

通过条件：历史可追溯，无数据重复或静默覆盖。

#### 验收用例 E2E-003：开销关联

1. 创建一笔 36 元餐饮开销。
2. 将其关联到指定生活领域和目标。
3. 在周复盘中查看分类和目标关联摘要。
4. 编辑金额后重新查看汇总。

通过条件：金额、分类、目标关联和汇总保持一致。

#### 验收用例 E2E-004：数据导出与恢复

1. 创建任务、目标、执行记录、开销和复盘。
2. 导出 JSON。
3. 删除测试数据。
4. 从导出文件恢复。

通过条件：恢复后核心关系、金额和历史状态一致。

#### 验收用例 E2E-005：AI 草稿确认

1. 提交一段自然语言任务或开销。
2. 查看发送数据提示。
3. 生成 AI 草稿。
4. 修改或取消草稿。
5. 确认后写入正式数据。

通过条件：未确认的 AI 草稿不能修改正式数据；API 失败时手动路径仍可用。

### 11.3 非功能验收

测试至少覆盖：

- 20 个同时在线用户的基本并发。
- 5000 条用户记录下的列表和复盘查询。
- 弱网、断网、恢复网络和重复提交。
- 数据库备份与恢复。
- 未授权访问其他用户数据。
- 前端是否泄露密钥。
- AI 限流、超时、服务不可用和额度耗尽。
- Chrome、Edge、Safari、Firefox 目标版本。
- 手机竖屏和桌面宽屏。

## 12. 待访谈与待确认问题

以下问题在首轮用户访谈前暂不固化为强制需求：

1. 用户最愿意每天记录的是任务、习惯、开销、心情还是精力？
2. 用户是否愿意把开销关联到目标，还是认为这会产生被评判感？
3. 用户更喜欢时间线、列表还是“下一步行动”首页？
4. 多设备同步是否是首轮测试的必要条件？
5. 用户需要怎样的提醒频率才不会关闭通知？
6. 用户能否接受外部 AI 处理部分任务、开销和复盘文本？
7. 用户更重视月度预算，还是只需要记账和回顾？
8. 最低版本是否真的能提高中断后的恢复率？

## 13. 需求变更管理

### 13.1 变更原则

任何新增需求都必须说明：

- 解决的用户问题。
- 受影响的业务目标。
- 是否会改变数据模型。
- 是否会增加外部依赖和费用。
- 是否影响安全、隐私或合规。
- 对工期的影响。
- 是否需要从同级别需求中移除其他内容。

### 13.2 变更规则

- P0 需求变更需要项目负责人确认。
- 会影响数据结构、安全、隐私、预算或工期的变更，必须更新本 SRS。
- AI 生成的功能代码不能绕过需求编号和验收标准。
- 未完成用户访谈验证的需求，默认标记为“假设”，不能直接扩大第一阶段范围。
- 每个版本发布前冻结需求，冻结后只接受缺陷修复和高优先级安全问题。

## 14. 当前需求基线

第一阶段需求基线为：

> 覆盖完整生活闭环，但每个模块保持轻量；优先 Web/PWA、本地优先、手动核心流程和可导出数据；AI 作为可关闭、可控、可撤销的增强能力；不接银行、支付、医疗、投资和社交系统。

该基线与《项目立项书》一致，是后续原型设计、技术设计和开发任务拆分的依据。

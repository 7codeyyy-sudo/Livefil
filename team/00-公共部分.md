# 6AI 团队公共协作规范与项目上下文

> 本文件是所有岗位共享的协作基础。每个岗位的提示词会要求你先阅读本文件，再执行岗位专属职责。改规则只改本文件，不影响各岗位提示词。

---

## 一、协作机制

1. 你是 6 人 AI 虚拟团队的一个岗位。AI 之间不能直接对话，所有跨岗交接通过用户（最终决策者）转发完成。
2. 跨岗交接必须写书面报告，报告写到 `team/0X-岗位/reports/` 目录下，接收岗位凭报告执行，不依赖对话记忆。
3. 报告必须自包含——接收方没有你的上下文，报告中不能出现"上面提到的事""之前说的那个"等指代，所有背景、结论、请求事项必须写完整。
4. `team/` 目录在项目根目录下，与 `doc/` 平级，纳入 git 跟踪，豁免 prettier 格式化。

## 二、代码与文件访问权限矩阵

所有岗位均可读全部项目文件，但无权修改 git 配置和 .git/ 目录。可写范围如下：

| 岗位 | 可写目录 | 禁止修改 |
|------|----------|----------|
| 项目总监 | `team/01-项目总监/` | `src/`、`app/`、`tests/`、`drizzle/`、`scripts/` 下任何文件 |
| 产品经理 | `doc/03-requirements/`、`doc/04-product-design/`（勘误，需终审） | `src/`、`app/`、`tests/`、`drizzle/`、`scripts/` 及其他 `doc/` 子目录 |
| 全栈研发 | `src/`、`app/`、`drizzle/`、`scripts/`、`composition-root.ts`、`doc/05/06`（需终审） | `tests/`（测试用例由测试岗维护） |
| 测试交付 | `tests/` | `src/`、`app/`、`drizzle/`、`scripts/` 下任何文件 |
| 市场行政 | `team/05-市场行政综合/` | `src/`、`app/`、`tests/`、`drizzle/` 及所有 `doc/` |
| 商务客服 | `team/06-商务客服/` | `src/`、`app/`、`tests/`、`drizzle/` 及所有 `doc/` |

铁律：
- 只有全栈研发岗可以修改业务代码（`src/`、`app/`、`drizzle/`、`scripts/`）。
- 只有测试交付岗可以修改测试代码（`tests/`）。
- 其他岗位一律禁止修改任何代码文件和测试文件，违者等同越权。

## 三、报告规范

### 报告编号

格式：`{岗位前缀}-{YYYYMMDD}-{三位序号}`
岗位前缀：总监=PD、产品=PM、研发=RD、测试=QA、市场行政=MA、商务客服=BC
示例：`QA-20260922-001`

### 报告模板

每份报告固定头部，正文分四区：

```markdown
---
编号: QA-20260922-001
日期: 2026-09-22
来源: 测试交付岗
去向: 项目总监（预审）→ 最终决策者（终审）
类型: 测试报告 | 风险上报 | 交付物 | 请示 | 任务分发单 | 预审意见 | 复盘报告
状态: 草稿 | 待预审 | 待终审 | 执行中 | 已闭环 | 已上报 | 已决策
关联: 任务 SCHED-003；doc/05-technical-design/接口文档.md §6
---

## 背景
（为什么有这份报告，自包含，不引用对话）

## 结论 / 内容
（是什么，自包含）

## 请求事项
（下一步具体动作，明确到可执行）

## 变更记录
（只追加不改写：审查意见、终审结论、执行反馈按时间顺序追加）
```

### 状态机

主链五态：`草稿 → 待预审 → 待终审 → 执行中 → 已闭环`
风险短链：`已上报 → 已决策 → 已闭环`

### 变更规则

- 变更只追加不改写：审查意见、终审结论、执行反馈以追加段落写入"变更记录"区，旧内容保留。
- 同一份报告反复修改导致版本过多时，在变更记录区顶部加一行摘要，让接收方不用读完整历史就能知道最终结论。

## 四、台账规则

1. `team/01-项目总监/registry.md` 是所有流转中报告的单一事实来源。
2. 每份报告从诞生到闭环在台账里有一行：编号、标题、当前状态、当前持有人、下一步。
3. 你被唤起时，第一步永远是读台账和相关报告获取上下文，不要凭空猜测。

## 五、流转路径

- 方案类：产品经理/全栈研发出方案 → 总监预审 → 决策者终审 → 下发执行。
- 测试类：研发交付 → 测试验收 → 测试报告 → 总监预审 → 终审 → 研发修复 → 复验 → 闭环。
- 风险类：任何岗位发现风险 → 即时上报总监 → 总监判断是否同步决策者。

## 六、逐级上报与预审

1. 所有关键产出、重大风险与决策事项必须逐级上报：执行岗 → 项目总监 → 最终决策者，禁止越级提交终审。
2. 五类关键产出必须经项目总监预审后才能提交终审：产品需求文档、上线方案、正式合同、核心宣传物料、财务报表。
3. 项目总监只有审查权、建议权、协调权，没有最终决策权。所有重大事项由最终决策者拍板。

## 七、记录留痕与归档

1. 所有关键决策、产出变更、问题处理均需形成书面记录。
2. `team/` 是过程稿（请示、预审意见、测试报告、风险上报），流转完留在岗位目录归档。
3. `doc/` 是定稿档案。终审确认的结论由对应岗位沉淀回 doc/ 正式文档：需求结论进 SRS/产品设计勘误，技术决策进工程决策记录，事故进事故记录，任务状态进开发任务清单。
4. 项目总监负责在 Phase 收尾复盘时检查"该沉淀到 doc/ 的结论有没有沉淀"。

## 八、项目上下文：Livefil

### 项目概况

- 项目名称：Livefil，个人生活管理与自律系统（PC Web/PWA）。
- 项目根目录：`E:\MyWork\Code\small_tool\livefil`。
- 核心闭环：快速记录 → 目标/任务整理 → 今日排程 → 执行 → 记录实际 → 日/周复盘 → 调整。
- 第一阶段约束：1-2 人、主要靠 AI 开发、每月约百元预算；只做本地单用户 Web 版 + 5-20 人邀请测试。不做银行接入、原生多端、社交和全自动 AI。

### 技术栈

Next.js 16 + React 19 + TypeScript strict + PostgreSQL + Drizzle ORM + Zod，API-first 模块化单体 + DDD 分层。composition-root.ts 是唯一装配点（懒加载单例），页面/路由不得直接访问数据库实现——有架构断言测试守护。

### 文档体系

`doc/` 下有完整的中文文档链，`doc/README.md` 是文档地图：

01-research 调研报告 → 02-project-initiation 立项书 → 03-requirements SRS → 04-product-design 产品设计 + UI 规范 → 05-technical-design 概要/详细设计/数据库/接口文档 → 06-development-plan 开发任务清单/工程决策/事故记录/开发环境规范。

### 任务驱动开发

- `doc/06-development-plan/开发任务清单.md` 是任务唯一入口，按 Phase 0-10 推进。
- AI 一次只做任务清单里的一个任务，先给实现计划和将修改的文件，再动手。
- 任务 ID（如 SCHED-002、EXP-001）是跨岗引用的共同语言，报告的"关联"字段必须引用这些 ID 和 doc/ 文档章节。

### 工程规则（所有岗位必须遵守）

- 契约冻结先行：开发前先冻结契约（写文档/勘误），再写代码。
- 提交规范：单 PR 多 commit，按模块拆 commit，commit message 用 `feat(phaseX):` / `docs(phaseX):` / `fix:` / `team:` 前缀。
- 测试三层：Vitest（unit/integration 双 project）+ Playwright（desktop/mobile 双 project）+ node:test 验收脚本。`npm run check` 全绿是最低门槛。
- 令牌纪律：tokens.css 之外禁止颜色/字号/圆角/时长/层级字面量，有验收脚本断言。
- 架构断言：页面不直接访问数据库实现，领域层不依赖 Next.js 页面组件，有依赖边界测试。
- 金额用整数分/Decimal，时间用 UTC + 用户时区。
- 事故记录 001 教训：所有改动尽快提交推送远程，不要让大量未提交改动堆积在工作区。

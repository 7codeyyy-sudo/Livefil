## 四、`manual_merge` 返 400 的语义说明

**行为**：`POST /api/v1/sync/conflicts/{conflictId}/resolve` 收到 `resolution: "manual_merge"` 时，返回 **400 `VALIDATION_ERROR`**，`message` 为「manual_merge 顺延，本批不支持」；请求体中的 `mergedPayload` 字段**保留但不读取、不校验**（向后兼容）。

**为什么不静默降级为 `keep_server`**：若把 `manual_merge` 当成 `keep_server` 处理，调用方拿到的是「已保存」，实际效果却是服务端版本原样留存、本地改动静默丢弃——这是**无提示的数据丢失**。宁可让调用方拿到明确失败码，也不接受一个假装成功的默认行为。这也是「保留取值与端点语义」与「不提供 UI」两件事能同时成立的原因：**契约面**留好扩展位，**本批行为**显式拒绝而非猜测。

**`resolve` 三种失败语义并列**（便于客户端分流）：

| HTTP | 触发条件 |
|---:|---|
| `400` | `resolution = manual_merge`（本批不支持）；`resolution` 取值非法 |
| `404` | 冲突不存在，或不属于当前用户（共用 404，不泄露存在性） |
| `409` | 该冲突已经处理过（含并发解决：读与写之间被其他请求抢先） |

前端侧无第三按钮、无占位，符合终审口径 3。

### 6.4 真机查出的两处缺陷（已修复）

**缺陷 1：同一 `operationId` 重放 push 返 500（应为 `already_applied`）**

- 根因：drizzle-orm 0.45.2 把驱动抛出的 pg 错误包成 `DrizzleQueryError`，原始 `code`（`23505` / `23503`）挂在 `.cause` 上；而 4 处本地辅助函数只读**顶层** `error.code`，永远匹配不上，于是「先 INSERT 占位、撞唯一约束再回读既有行」这条可预期分支被当成未知异常，升级成 500。
- 影响面：`idempotency-store.drizzle.ts`、`user-repository.drizzle.ts`、`life-area-repository.drizzle.ts`（均 `23505`）、`sync-apply.drizzle.ts`（`23503`，create 带不存在 `goalId` 本应判 `rejected` 也返 500）。**非本次新增**，是既有实现随 drizzle 升级而失效。
- 修复（commit 8）：新增 `src/shared/errors/postgres-error.ts` 导出 `hasPostgresErrorCode(error, code)`，沿 `cause` 链遍历（深度上限 8 + `seen` 集合防环）；4 处替换为该共享辅助。
- 复验：重放 → `already_applied`；create 带不存在 `goalId` → 该条 `rejected`；**回归面**——同 `Idempotency-Key` 普通写请求两次仍为 409 `IDEMPOTENCY_REPLAY`、同名生活领域仍为 409 `CONFLICT`（语义未被改坏）；本轮服务端**无任何 `INTERNAL_ERROR`**。

**缺陷 2：离线新建不入队（SYNC-005 ② 未通过）**

- 根因：`app/(app)/_lib/api-client.ts` 的 `OPERATION_BY_METHOD` 只映射 `PATCH`/`PUT`/`DELETE`，`POST` 被刻意排除（注释「本批不猜」），而服务端 `SYNC_OPERATION_TYPES` **本就包含 `create`**、`sync-apply` 也已实现 create 落库——是**客户端缺了一段**。
- 修复（commit 9）：新增 `COLLECTION_WRITE_PATH` 与 `describeFailedCreate`——离线时对「正好是白名单集合本身」的 POST，由客户端 `crypto.randomUUID()` 生成实体 id、入队 `operationType:'create'`、并返回与在线同形的成功信封（`{ data: { id, version: 0, ...payload } }`），调用方无需为离线态分叉；`queries.ts` 首页合并本地 pending 快照并按 `id` 去重（客户端 UUID 即服务端主键，推送成功后不会重复）；`local-store` 端口新增 `listSnapshots` / `markSnapshotSynced`（两实现均补齐），`sync-client` 的 `#applyPushResult` 在 applied/already_applied 时把 `pending` 快照转 `synced`，避免该快照永久挡住后续 pull。
- 复验：见 §6.3 ②。

### 6.5 真机暴露的既有问题（非本次引入，未修）

## 七、建议测试点清单（交测试交付岗落用例）

> 依分发单要求，开发侧不改 `tests/`；以下 12 条为建议测试点（≥8 条，第 1 条为页面禁访 `indexedDB` 断言）。

1. **【架构断言】页面不得直接访问 `indexedDB`**：`app/**`、`src/modules/*/presentation/**`、`src/shared/ui/**` 内出现 `indexedDB` / `IDBDatabase` / `IDBObjectStore` 等标识符即失败（唯一例外 `src/modules/sync/infrastructure/local-store.indexeddb.ts`）。载体已落 `eslint.config.mjs` 的 `INDEXED_DB_ACCESS_RULES`，**建议在 `tests/unit/architecture/` 下以删除式探针断言**：临时写入违规标识符 → 期望 lint 报 1 error → 删除后恢复全绿。
2. **安全滞后窗口防漏读**：构造「事务 A 先取 `changeAt` 时刻、事务 B 更晚取时刻并**先**提交」的场景，断言 A 提交后仍能被 pull 拉到（即 `changeAt <= now() - lag` 条件生效）。这是 S2 的唯一正确性前提，**必须有**。
3. **push 逐条幂等与单条失败不回滚整批**：同批中一条 `already_applied`、一条 `applied`、一条 `rejected`，断言 HTTP 整体 200、各条状态独立、已 `applied` 的操作**不因同批失败被回滚**。
4. **`sync:` 保留前缀**：普通写请求携带 `Idempotency-Key: sync:xxx` 时被拒；sync push 自身携带非 `sync:` 前缀时行为符合契约。
5. **`conflict` 条目的幂等落态**：断言 `conflict` 走 `release`（**不** `complete`、不写快照）→ 同 `operationId` 重试按全新请求重评估；冲突未解决时复用同一 `conflictId`，解决后该条转 `applied`。
6. **同 `operationId` 异指纹**：断言该条 `rejected`（`VALIDATION_ERROR`）。
7. **错误码沿 `cause` 链识别（本次缺陷 1 的回归护栏）**：对 `hasPostgresErrorCode` 做单元测试——单层包装 `23505`、多层包装 `23503`、不匹配码、`cause` 成环、超深度、非对象入参，逐项断言；并**至少一条集成用例**断言「同 `Idempotency-Key` 重放普通写端点返 409 `IDEMPOTENCY_REPLAY`」与「同名生活领域返 409 `CONFLICT`」（防止共享辅助替换改坏既有语义）。
8. **冲突二选**：`keep_server` 只标解决不写实体；`keep_local` 用本地 payload 无条件覆盖（`baseVersion: null`，不产生新冲突）；`manual_merge` 返 400；重复解决返 409；非本人冲突返 404。
9. **离线续用 e2e**：已打开页面断网 → DOM 未变、离线横幅出现、已预取路由可软导航；恢复联网横幅消失。**不得**写成「断网刷新后仍可用」（无 SW，口径 2 明确排除）。
10. **离线新建入队（本次缺陷 2 的回归护栏）**：断网时 `POST` 白名单集合 → 入队 `create`、本地快照 `pending`、页面立现该项；联网后 push → 服务端以**客户端 UUID** 落行 → 快照转 `synced`。同时断言 `POST /tasks/batch`、`POST /tasks/{id}/archive` 这类带更深路径的 POST **不**入队。
11. **LocalStore 事务规则**：断言「一次读改写落在同一事务内」；`markSnapshotSynced` 对不存在/已 `synced` 的快照静默忽略；`applyRemoteChange` 对 `pending` 快照一律 `ignored`（本地未确认改动不被远端覆盖）。
12. **墓碑传递四类**：软删 5 表、`schedule_blocks` 状态即墓碑、`execution_logs` 只读无墓碑、`life_areas`/`goals` 的 `deleted` 恒 `false`（§4.18.3 勘误后的口径）；级联硬删按父级墓碑级联清理子行。

## 一、件①：redaction `prompt` 阻断三件套（设计披露，未落码）

### 1.1 缺口事实（回查原文，非推测）

- 《详细设计说明书》§9 的禁止字段清单**已含「完整 AI prompt」**，且该清单就是实现文件 [redaction.ts](file:///e:/MyWork/Code/small_tool/livefil/src/shared/telemetry/redaction.ts#L4-L6) 头部注释自陈的依据（注释原文：「《详细设计说明书》§9 的禁止字段清单：密码、token、API key、完整 AI prompt、完整任务名称、开销备注、目标理由。」）。
- 但 `FORBIDDEN_FIELD_NAME_FRAGMENTS`（同文件 L20-31）实际十项为 `password` / `passwd` / `secret` / `token` / `apikey` / `authorization` / `cookie` / `session` / `credential` / `privatekey`——**不含 `prompt`**。现状下 `prompt` 只受 `MAX_TEXT_LENGTH = 200` 的**截断**（保留前 200 字符），与「不记录完整 AI prompt」的保守方向不一致。
- 风险当前**未现实化**：`src/modules/ai/` 现为 `.gitkeep` 空占位（实查），全仓无任何以 `prompt` 为日志字段名的调用点。故 RD-006 预审判定 1 定为「归 Phase 9 AI-003 批落地，不另立 FND 勘误 PR」。

### 1.2 三件套设计

**第 1 件｜禁止清单增补（`src/shared/telemetry/redaction.ts`，仅此一行）**

在 `FORBIDDEN_FIELD_NAME_FRAGMENTS` 增一项 `'prompt'`。命中机制为**归一化后子串包含**（`normalizeFieldName`：转小写 + 去非字母数字），因此 `prompt` / `prompts` / `systemPrompt` / `prompt_text` / `PROMPT` 均命中，等价于「任何以 prompt 为语义的字段名整体替换为 `REDACTED_PLACEHOLDER`」。

- **误伤评估**：本仓字段命名表（DB §4.1~§4.16 + 接口各章）中**无**任何合法业务字段名含 `prompt` 子串，故误伤面为零；即便将来出现，也落在文件头已声明的「有意偏向保守——脱敏漏掉的代价远大于多脱一点」口径内（同 `session` 命中 `sessionCount` 的既有先例）。
- **不新增导出、不改签名、不改截断逻辑**（`MAX_TEXT_LENGTH` 保持 200，作为第二道防线）。

**第 2 件｜用例**（落点与授权冲突见「五、请示项 1」）

拟落 `tests/unit/shared/telemetry/redaction.test.ts`（该文件现有 describe 为：禁止字段识别 / 脱敏结果不含敏感原文 / 文本长度截断 / 各类值的处理 / 结构性边界 / 不修改原对象；断言风格为 Vitest `expect`），新增 4 条：

| # | 用例 | 断言要点 |
|---|---|---|
| 1 | `prompt` 字段整体替换 | `isForbiddenFieldName('prompt')` 为 true；`redactValue('很长的一段输入…', 'prompt')` 恒等 `REDACTED_PLACEHOLDER`（**不放行前 200 字符**） |
| 2 | 变体同样命中 | `prompts` / `systemPrompt` / `prompt_text` / `PROMPT` 归一化后全部命中 |
| 3 | 嵌套结构中的 `prompt` | `redactRecord({ context: { prompt: 'x', model: 'm' } })` → `prompt` 被替换、`model` 原样保留（不误伤同级） |
| 4 | 误伤面显式声明 | 含 `prompt` 子串的无关字段同样被替换，断言为「保守方向正确」而非「精确命中」——与文件头注释口径一致 |

## 三、件③：引导完成判定查询口径（四步逐条对既有读端点）

冻结依据：UI v0.22 §5 A 节——判定口径已冻结为「**对应实体存在**」（行动 / 时间块 / 执行记录 / 复盘记录），「进入与离开各核对一次，达即自动打勾进下一步」；**判定查询的实现方式归研发披露**（该补节缺口 3）。

| 步 | 冻结判定 | 拟定查询口径（**全部既有端点，零新端点**） | 边界与代价 |
|---|---|---|---|
| 1 首个行动 | 存在 ≥1 个行动 | **无全局行动读端点**——实查：`GET /goals` 响应为纯目标列表 DTO，**不含 `actions`**（[route.ts](file:///e:/MyWork/Code/small_tool/livefil/app/api/v1/goals/route.ts#L36-L54) → `toGoalDto`）；`GET /goals/{goalId}` 才回带 `actions`（`GoalDetailDto.actions`）。口径二选一见「五、请示项 3」 | **甲案**（`GET /goals?limit=100` + 逐目标 `GET /goals/{goalId}` 判 `actions.length > 0`，命中即短路）：零新端点，代价为 N+1，但引导仅首启判一次、且目标数有上界 100；**乙案**（新增只读端点）属契约缺口，按 PD-018 §五停手上报 |
| 2 安排时间 | 存在 ≥1 个时间块 | `GET /schedule-blocks?from&to&timezone`（§6：`from`/`to`/`timezone` 均必填，窗口 ≤42 天，窗口内不分页、返数组） | 取 `[今日 − 42 天, 今日]` 一次查询即可覆盖引导场景下的新建块；**更早的时间块不计入判定**（首启引导场景下影响为零，如实声明） |
| 3 完成一次执行记录 | 存在 ≥1 条执行记录 | `GET /execution-logs?limit=1`（§7：游标分页，`limit ≤ 100`、默认 50，按 `occurredAt` 降序） | 取 1 条即判存在，无需增量拉全量 |
| 4 第一次复盘 | **当日**复盘记录存在（跳过不产生记录、不判完成） | `GET /reviews/daily/{date}`（§10：**无记录时返回 `200` + `data: null`，不是 404**） | `data !== null` 即判完成；与 A 节「跳过不产生记录」天然一致，无需额外状态位 |

**核对时点**：按 A 节「进入与离开各核对一次」，引导条**挂载时与页面离开（可见性/路由变更）时各查一轮**；步 1 因短路与上界，实际请求数为 `1 + min(目标数, 100)` 且通常在首个含行动的目标处终止。

**零新端点结论（除步 1 的乙案外）**：步 2/3/4 完全落在 §6/§7/§10 既有端点上；步 1 请裁定甲乙案。若采乙案，我**停手等裁定**，不自行加端点。

#### 1.1.1 weekly 快照的物化时机与不变性（预审执行要求①，本批定稿）

- **物化时机**：`GET /reviews/weekly/{weekStart}` 在**该周已结束**（`weekStart + 7 天 <= 用户时区当日`）且尚无该周 `reviews` 行时，计算 B2 七项的「事实」部分并 upsert 落库（`snapshot` + `snapshot_schema_version = 1`）。
- **周未结束时**：实时计算并直接返回，**不落库**（当周数据仍在生成，落库即污染历史）。
- **写入后不变性**：`snapshot` 一旦落库**不再重算**——后续读取一律返回存量，与本批之后的输入变化无关；本批无「重新生成快照」入口，故不可变。
- **两点取舍如实声明**：① 物化是**惰性**的（该周首次被访问才落库），故一个从未被访问的过去周，其快照反映的是「首次访问时」的计算结果，而非该周结束时的状态；② 快照带 schema 版本，保证结构演进时可迁移（DB §4.11）。

## 二、披露 B：同步接入扩展方案（拍板 1）

### B.1 entityType 白名单扩项

| 文件 | 改动 |
|---|---|
| `src/modules/sync/domain/sync-change.ts` | `SYNC_ENTITY_TYPES` 追加 `'expense'`、`'review'` |
| `src/modules/sync/infrastructure/sync-entities.ts` | `SYNC_ENTITY_SPECS` 追加两条 spec（下表） |

**expense spec**：`deletion: 'soft-delete'`、`deletedOf: softDeleted`、`versionColumn: expenses.version`、`changeAt: coalesce(updatedAt, createdAt)`、`readOnly: false`；`writable` = `categoryId`/`lifeAreaId`/`goalId`/`actionId`/`amountMinor`/`currencyCode`/`occurredOn`/`paymentMethod`/`note`/`source`（覆盖 DB §4.10 全部业务列）；`requiredOnCreate` = `['categoryId','amountMinor','currencyCode','occurredOn']`（对应 NOT NULL 且无默认值）。

**review spec**：`deletion: 'unsupported'`、`deletedOf: neverDeleted`（**无删除语义**，对标 `goals` 既有写法——预审裁定 C.4 采 B）、`versionColumn: reviews.version`；`writable` = `reviewType`/`periodKey`/`answers`/`energyLevel`/`snapshot`/`snapshotSchemaVersion`；`requiredOnCreate` = `['reviewType','periodKey']`。

**不追加 `review_adjustment`**：拍板 1 明文「两实体」；调整清单经 `GET /reviews/weekly/{weekStart}` 读取（随批勘误 4），不走同步链。

**金额跨线口径（零 float）**：`amountMinor` 在 DB 为 `bigint`，在接口 §9 为**字符串**，故在 payload / 快照 / 入队记录中**一律保持字符串**，任何环节不得经 `Number()`。既有 `readVersion` 对 `version`（bigint 计数，非金额）做 `Number()` 属既有实现，不在本次改动范围。→ 零 float 源码扫描断言将覆盖新模块。

### B.2 客户端写路径映射（含一处对 PD-009 原话的技术更正）

**更正**：`COLLECTION_WRITE_PATH` 是正则 `/^\/api\/v1\/([^/]+)$/`，对任意集合名都成立，**本身无需扩项**；拦住未登记集合的是 `SYNC_ENTITY_BY_COLLECTION` **映射白名单**（未登记返回 `null`，不入队）。故 PD-009 §三「`COLLECTION_WRITE_PATH` 扩项」在本批落为**映射表扩项，正则不动**。

| 改动 | 内容 |
|---|---|
| `SYNC_ENTITY_BY_COLLECTION` | 追加 `expenses: 'expense'`、`reviews: 'review'` |
| 新增日期键匹配器 | 见下（reviews 的真实缺口） |

**reviews 的写路径缺口（本次披露的关键点）**：接口 §10 的日复盘写端点是 `PUT /api/v1/reviews/daily/{date}`（日期键 upsert），它**既不匹配** `ENTITY_WRITE_PATH`（第二段必须为 uuid）**也不匹配** `COLLECTION_WRITE_PATH`（要求单段集合路径）。照现状，reviews 的一切实体写入都无法入队，同步只覆盖 pull。三个处置选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| **甲（推荐）** | 新增 `PERIOD_REVIEW_WRITE_PATH = /^\/api\/v1\/reviews\/(daily\|weekly)\/(\d{4}-\d{2}-\d{2})$/`（`PUT`）；客户端 `crypto.randomUUID()` 生成 entityId，payload 由路径回填 `reviewType`/`periodKey`；离线成功信封形状对齐在线 PUT。服务端 push 的 `create` 以该 uuid 落行，同日在线再调 PUT 时按唯一约束 `(user_id, review_type, period_key)` 命中同一行，不重复建行 | 需建该唯一索引（本已在披露 C 内）；需为复盘取数补"本地新建合并" |
| 乙 | 只对"本地已有该 review 快照"的字段更新入队（update），离线首次创建不支持 | 离线记复盘不可用，缺口明显 |
| 丙 | reviews 只 pull 不 push（只读同步） | 同上，且浪费已建的 version 列 |

**刻意不做**：`POST /reviews/weekly/{weekStart}/adjustments` 路径更深（`adjustments` 为子资源），**不入队**；离线提交调整走普通失败路径并提示失败（本批已知限制，见 B.7）。

### B.3 IndexedDB 快照范围

LocalStore 三 store（`entity_snapshots` / `pending_operations` / `sync_cursor`）**按 entityType 泛化**：`applyChanges` 依 `change.entityType` 落盘、`listSnapshots(entityType)` 按型取，**无类型白名单 → 新增两实体零改动即覆盖**。

需接线的是两处**按型取数**的客户端代码：

| 位置 | 现状 | 本批改动 |
|---|---|---|
| `app/(app)/_lib/queries.ts` `makeInboxQueryFn` | 只合并 `'task'` 的本地新建 | 为 `/expenses` 列表提供同型"本地新建合并"（`listPendingLocals('expense')`），去重依据仍是 id（客户端生成的 UUID 即服务端 create 主键）；否则离线记账后翻页看不到刚记那条 |
| `/review` 日复盘取数 | 单对象 + `data:null` 空态 | 空态/离线时以本地快照兜底 |

快照 payload 同样保持 `amountMinor` 字符串。

### B.4 冲突检测白名单与金额冲突提示

- **服务端**：push 的 CAS 由实体注册表驱动（`versionColumn` 非空即参与乐观并发）→ 两条 spec 一登记，冲突检测自动覆盖，**无需另立白名单**。
- **客户端**：`sync-client.ts` 的冲突处理**按 operation 泛化、不按 entityType 分支**，`SyncStatusBanner` / `ConflictDialog` 照 §4.9.2 冻结形态展示两版。但**实测发现两处会让 expense/review 的冲突卡片变成空卡或 UUID 标题**：

| 实测问题 | 证据 | 本批改动 |
|---|---|---|
| 摘要字段表不含 expense/review 的任何字段，`summarizeFields` 将返回**空数组** | `sync-client.ts` L58-67 `SUMMARY_FIELDS` 仅含 `title/name/status/localDate/dueDate/startsAtUtc/estimatedMinutes/minimumVersion`；L659-682 按该表取值 | 追加 `['amountMinor','金额']`、`['currencyCode','币种']`、`['occurredOn','日期']`、`['periodKey','复盘日期']`（**追加在表尾**：既有 8 项的优先级与 `MAX_SUMMARY_FIELDS=3` 截断行为逐字不变，expense 实际得到「金额/币种/日期」3 行） |
| 可读名候选键只有 `title`/`name`，expense/review 均无 → 标题退化成 UUID | `sync-client.ts` L617-625 `entityDisplayName` | 候选键扩为 `['title','name','note','periodKey']`，仍取不到才退化 id（既有实体行为不变） |

**金额冲突提示的接线结论**：§4.9.2 浮层无需为金额做专用 UI——`expenses` 的 payload 含 `amountMinor`/`currencyCode`，上表扩项后两版金额逐行可见即满足「金额冲突必须提示」。**不引入字段级 diff 编辑器**（§4.9.2 第 8 条，且 `ConflictDialog` 文件头已明确不做）。

### B.5 墓碑传递

按 DB §4.18.1(3) 四类分类：

| 实体 | 形态 | pull 传递 | 备注 |
|---|---|---|---|
| `expenses` | 软删（`deleted_at`） | 软删是一次 UPDATE，`changeAt` 前移自然进流；`deleted` 非空即墓碑，客户端清理本地行 | `DELETE /expenses/{id}` 必须经 Drizzle `update()`（不得原生 SQL），否则漏读 |
| `reviews` | **无删除语义** | 无墓碑：`deleted` 恒 `false`，push 的 delete 判成拒绝 | 本批**无删除入口**（B1「跳过今天」纯前端不落记录）；**不建 `deleted_at`**（预审裁定 C.4 采 B） |
| `review_adjustments` | 不参与同步 | — | 追加式，无墓碑需求 |

**必须同批补的索引（新发现，必须披露）**：`expenses` 现有索引 `(user_id, occurred_on)` / `(user_id, category_id, occurred_on)` / `(user_id, goal_id)` **均不含 `updated_at`**，无法支撑 `(user_id, changeAt, id)` keyset 扫描；`reviews` 更是新表。故 EXP-001 / REVIEW-001 迁移内各补一个 `(user_id, updated_at, id)` keyset 索引（对标 Phase 5 新增的 9 个 keyset 索引）。缺此则 `GET /sync/pull` 的跨表 UNION 会退化为全表扫描。

## 三、披露 C：`reviews` / `review_adjustments` 字段清单

### C.3 快照结构与五动作 payload

`snapshot`（`snapshot_schema_version = 1`，B2 的"事实"部分——只存**当时算出的值**，不存重算路径）：

## 四、披露 D：A2.2 存储口径（选中行动时的 `goal_id`）

**口径：选中行动时，同时写 `action_id` 与父目标 `goal_id`。**（不选行动时 `action_id` 为 null；选目标时 `goal_id` 有值、`action_id` 为 null；「不关联」两列皆 null。）

**依据**：

1. DB §4.10 的 `goal_id` / `action_id` 是**两列独立可空 FK**，不存在 XOR 约束；「目标 ⊕ 行动互斥单选」是 A2.2 **选择器层的单选约束**（一次只选一项），不是存储层互斥；
2. 与既有 `tasks` 表口径一致——`tasks` 的 `writable` 同时含 `goalId` 与 `actionId`（`sync-entities.ts` L153-165），本项目既有的"行动挂在目标下"的关联就是两列并存；
3. 与拍板 4③「归档目标的开销照进目标关联汇总」同向。

**对 `groupBy=goal` 的含义**：目标关联汇总＝`WHERE goal_id = :goalId`（单列过滤，命中既有索引 `(user_id, goal_id)`，**无需 JOIN `actions`**）。因此「经行动关联的开销」照进目标汇总，「直接关联目标的开销」与「行动关联的开销」在同一目标下合并统计。

**若改存只写 `action_id`（`goal_id` 恒 null）的后果（如实列出）**：`groupBy=goal` 必须 JOIN `actions` 才能纳入行动关联开销；且行动一旦归档/软删，历史开销会从目标汇总中掉出——与拍板 4③ 的精神相反。

**唯一代价（如实声明）**：`actions.goalId` 是可写列，若某行动被改挂到另一目标，历史开销的 `goal_id` 是**记账当时父目标的快照**，不随后续改挂重算。判定可接受：①开销是历史事实，与「goals 无删除、归档不删行」的既有口径同向；②本批 UI 无「行动改挂目标」入口（仓库现无 `POST /actions` 路由，行动仅经 `POST /goals/{goalId}/actions` 创建）。若预审要求"跟随改挂"，则需改为运行时 JOIN 并承担上述 3 的代价——**不建议**。

## 五、披露 E：A3「最近使用分类」数据口径

契约未写（`expense_categories` 仅 `is_default`，无 `last_used_at`），且预审明确「不得为此加无界全表扫描」。定稿规则：

| 项 | 规则 |
|---|---|
| 数据源 | **已加载的 `/expenses` 列表首页**（`GET /api/v1/expenses?limit=<页大小>`，排序 `occurred_on DESC, created_at DESC`，与 A5 冻结排序同源）。Drawer 只从 `/expenses` 进入（A1/A6），该首页已在同页 query cache 内 → **零新端点、零新列、零额外查询** |
| **筛选态边界** | 列表带筛选参数时**不得**以筛选结果推导「最近使用」（筛选结果不是"最近使用"的样本）；无「无筛选态首页」缓存时直接走降级路径（组空、预选回落默认首项）——**预审执行要求②** |
| 「最近使用组」 | 无筛选态首页各行 `categoryId` 按**首次出现顺序**去重，取前 ≤3 项；该顺序即"最近使用倒序" |
| 预选 | 最近使用组首项；无历史（首页为空/不可解析）→ 默认分类组按 FR-051 顺序首项「餐饮」 |
| 编辑态 | 回填原分类（不参与最近使用计算）；原分类已停用时仍回填并附「已停用」Badge（A3 原文） |
| 分组展示 | 最近使用组（≤3）→ 默认分类组（9，FR-051 顺序）→ 自定义组（创建时间倒序）；搜索跨组保持组序 |
| 查询上界 | 列表页大小（A5 分页同口径），复用既有 `(user_id, occurred_on)` 索引；**无无界扫描** |
| 降级 | 首页落错误态（离线且无本地快照）→ 最近使用组为空 → 预选回落默认首项，不阻塞 Drawer 打开 |

**语义边界（如实声明）**：「最近使用」按 `occurred_on` 倒序定义（＝列表首条即「用户最近一笔开销」），故**补记**（`occurred_on` 早于记账时刻）会排在其日期位置而非记账时刻位置。这与 A3 原文「该用户最近一笔开销的分类」及 A5 列表排序**同口径**。若预审要求按"记账时刻"排序，则需新增 `(user_id, created_at)` 索引 + 新查询——**不建议**（新增索引与查询为无界需求，且与 A5 排序口径分叉）。

**9 个默认分类的惰性创建**（拍板 4②，对标 IAM-003）：播种条件＝**该用户无任何 `expense_categories` 行（含已停用）**；顺序＝FR-051 的餐饮/交通/居住/健康/学习/娱乐/购物/关系/其他（`sortOrder` 1~9），`is_default = true`；触发点＝首次访问 `/expenses`（含分类列表端点被调用时）。

## 六、三项新缺口提请（不属披露四项，但影响实现路径）

### 1. `expense_categories` 端点缺失（影响 EXP-002 的 A6，阻断级）

### 2. 复盘调整的「记录 vs 执行」语义未写（影响 REVIEW-003）

### 3. 冲突摘要的两处接线（影响拍板 1 的「金额冲突提示」）

已在 B.4 列出实测证据（`SUMMARY_FIELDS` 空表 → 摘要为空；`entityDisplayName` 无候选 → 标题退化 UUID）。本批按 B.4 同批修复，**既有实体的摘要优先级与截断行为逐字不变**。此项不属契约变更，仅作知悉。

## 2. 交付 1：schema 详设

### 2.1 `users` 加列（批 A-DB 小批）

| 列 | 类型 | 约束 | 语义与判据 |
|---|---|---|---|
| `username` | `varchar(30)` | 可空（本地用户为 NULL）；**唯一索引** | 档 A 登录标识 A-2（PD-016 L107/L112②）。写入前 `trim` + ASCII 小写归一（`toLowerCase`），故唯一索引即大小写不敏感；**字符集 `^[a-z0-9_一-龥]{3,20}$`（归一后）**——不含 `@`，与邮箱**天然无重叠**（交付 3 登录标识判定的零歧义前提）。本地模式唯一索引对全 NULL 不生效（PG 语义），存量行零影响 |
| `password_hash` | `varchar(160)` | 可空 | scrypt 编码串（交付 7 定格式 `scrypt$N$r$p$salt$hash`）。本地用户恒 NULL |
| `email_verified_at` | `timestamptz` | 可空 | 注册流验证码核验通过时写入（＝注册时刻）；改邮箱成功时更新（交付 3 §4.4）。云端用户恒非空（应用层不变式） |
| `deleted_at` | — | **本批不加** | **归属划分（预审点 5）**：准据 DB §4.1 L90「账户删除随 data-management 批次（含云端模式）实施，届时按加列迁移补」＋入档批次顺序批 1 先行（PD-016 L102）——**该列归属批 1（data-management / OPS-002）**，批 A-DB **只读消费不加列**，两批各出独立迁移文件，**不存在同一列加两次的路径**。批 A 的消费点：登录/注册对 `deleted_at` 非空账户统一拒绝（§4.3）；跨批接口：批 A 向 data-management 暴露 `revokeAllSessions(userId)` 端口，账户删除落库后由批 1 调用吊销会话（方向：data-management → identity，避免反向依赖） |

**DB 级 CHECK（本批新增，防应用层漂移）**：

```sql
ALTER TABLE users
  ADD CONSTRAINT users_cloud_requires_credentials
  CHECK (mode = 'local' OR (email IS NOT NULL AND password_hash IS NOT NULL));
```

理由：既有代码只有两种 mode 语义（`drizzle/schema.ts` L86），云端用户必须同时具备登录标识与凭据；存量行全部 `mode='local'`，约束对存量零破坏。**不加** `username` 的 CHECK（应用层 Zod 校验为唯一权威，避免双真相）。

**不进同步白名单**：`username`/`password_hash`/`email_verified_at` 随 `users` 维持现状——`users` 本就不在同步实体集合（`sync-change.ts` L22-34），密码哈希无任何进入同步载荷的路径（预审点 3 之 #7 日志/泄露面的结构性保证）。

### 2.2 `sessions` 表（新表，兑现 §8.1 L621「云端会话形态随云端批次重定」＝甲案可吊销+多设备+设备标签）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `uuid` | PK（`defaultRandom`） | **sessionId，签入令牌载荷**（§2.4 扩展路径） |
| `user_id` | `uuid` | NOT NULL，FK `users(id)` ON DELETE CASCADE | 账户物理清库时会话行级联消失（data-management 异步终清的兜底） |
| `device_label` | `varchar(120)` | 可空 | 登录时取 User-Agent **截断+去控制字符**落存，不做 UA 解析库（零依赖，交付 7）；粗粒度可读标签即可 |
| `created_at` | `timestamptz` | NOT NULL，defaultNow | 首次签发 |
| `last_seen_at` | `timestamptz` | NOT NULL，defaultNow | **更新节流 ≥5 分钟**（防每请求写放大） |
| `expires_at` | `timestamptz` | NOT NULL | 签发＝`now+30 天`；**滑动续期**见 §3 流 4 |
| `revoked_at` | `timestamptz` | 可空 | 吊销＝置值（登出/改密/重置/账户删除）；非空即失效 |

- **不设** `version`/`deleted_at`/`token_hash`：对齐 `notification_rules` 取舍先例（DB §4.12.1 L484「不入同步白名单 ⇒ 无 CAS 与墓碑需求，不留无写入路径的死列」）；`token_hash` 的取舍见 §2.3。
- **索引**：`sessions_user_idx (user_id)`（吊销批量扫）、`sessions_expiry_idx (expires_at)`（清理）。会话行清理＝**惰性**（登录时顺手删本人已过期/已吊销行）＋ `scripts/` 可选清理入口，不引入 cron（零依赖）。
- 公共字段：只取 `createdAt/updatedAt` 语义中的 `created_at`（`$onUpdate` 的 `updated_at` 在本表无消费者，不加）。

### 2.3 令牌形态选型：签名令牌 + sessions 行（对 spike §4.1 草案 `token_hash` 的偏差与论证）

| 方案 | 机制 | 优 | 劣 |
|---|---|---|---|
| **（b）签名令牌 + sessions 行（本详设选定）** | 载荷 `{userId, sessionId, issuedAt, exp}` 经既有 `createSessionSigner` HMAC 签名；验签后按 `sessionId` 查行判吊销/过期 | **复用现网签名器与全部测试**；坏令牌先验签、不打库；换实现不影响调用方（端口 `SessionTokenService` 注释已预留，`session-token.ts` L74-77） | AUTH_SECRET 泄露下攻击者可**签发**合法令牌（仍须命中未吊销行） |
| （a）不透明随机令牌 + `token_hash`（spike §4.1 L77 草案） | 32B 随机串，行内存 sha256(token) | 密钥泄露不危及既有令牌 | 弃用签名器（item 7「签名器复用路径」落空）；每请求必查库；哈希与签名为双真相 |

**选定 (b) 的三条理由**：① PD-023 交付 7 明确要求「会话签名器复用/扩展路径单列」——(b) 是唯一复用路径；② 泄露面对称（两种方案下 COOKIE 被盗均可活到过期，(a) 并不更强）；③ 与现有 `verify()` 快速拒绝路径一致，`AUTH_SECRET` 的装配期强制（§8.3）覆盖云端部署。**与 spike 草案的差异如实申报**：spike §4.1 为评估级字段草列，非契约；若预审倾向 (a)，切换代价＝弃用签名器 + 每请求必查库 + 已写测试重写（约 0.5 人日），标注为**待裁定项 1**（§11）。

### 2.4 `email_verification_codes` 表（新表，验证码通道正身——挂账 5 解锁落点）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `uuid` | PK | |
| `email` | `varchar(320)` | NOT NULL，归一小写 | 收码邮箱 |
| `purpose` | `varchar(16)` | NOT NULL，`register｜login｜password_reset｜change_email` | **跨 purpose 不可用**（安全矩阵 #8 的落点） |
| `code_hash` | `char(64)` | NOT NULL | **HMAC-SHA256（AUTH_SECRET 分域派生，消息＝`purpose｜email｜code`）**——库泄露≠码泄露；不存明文 |
| `attempts` | `smallint` | NOT NULL default 0 | **≥5 作废**（每次错验 +1，同码累计） |
| `expires_at` | `timestamptz` | NOT NULL | `created_at + 10 分钟` |
| `consumed_at` | `timestamptz` | 可空 | 验证成功/作废/被新码取代即置值；**一次性** |
| `created_at` | `timestamptz` | NOT NULL，defaultNow | 频控计数依据 |

- **索引**：`(email, purpose, created_at)` 支撑「每邮箱限流」计数与「单活跃码」判定。
- **单活跃码规则**：同 `(email, purpose)` 发新码时先置旧码 `consumed_at`（同事务）——并行双码互扰的口子关死。
- **不设** `version`/`user_id`（register 时用户尚不存在；按 email 归属），对齐 §2.2 取舍理由。

## 3. 交付 2：认证流程时序

> 按修正口径（§1 差异声明）执行：无邀请生成/分发/激活流，代之以注册、双通道登录、会话生命周期、密码重置四组时序。文字时序＝步表（team/ 无 mermaid 先例）。

### 流 1：注册（页面三步 ⇒ 后端两端点）

| 步 | 客户端 | 服务端 | 关键校验 / 落库 |
|---|---|---|---|
| 1 | 输入邮箱 → `POST /auth/cloud/verification-codes {email, purpose:'register'}` | 频控判定 → 生成 6 位码 → 单活跃码置旧 → HMAC 落行 → 邮件服务商 HTTP API 发信 → **恒回 200 统一信封** | 见 §4.5 频控表；**API 侧不区分邮箱是否已注册**（防枚举）：已注册 ⇒ 邮件侧改发「你已注册，请直接登录」提示信（差异只存在于邮箱，收件人即邮箱主人） |
| 2 | 输入验证码（单框，`inputmode=numeric` / `autocomplete=one-time-code`）| —（前端步内流转，不发校验请求） | 校验后移到步 3 原子执行，避免「先验后建」两跳竞态 |
| 3 | 账号 + 名字（可留空）+ 密码 → `POST /auth/cloud/register {email, code, username, displayName?, password}` | **单事务**：核码（码存在/未过期/attempts<5/未消费/同 purpose）→ 核 username 唯一 → 建用户（mode=cloud、email 小写归一、`email_verified_at=now`、`password_hash=scrypt`）→ 建会话行 → 签新令牌 → `Set-Cookie` | 核码失败：统一 400「验证码不正确或已过期」（**不区分过期/错误/不存在**）；码 attempts+1，≥5 置 `consumed_at`；username 撞名：**409 CONFLICT 字段级提示「该账号名已被使用」**——枚举边界见 §9-B2；CHECK 约束兜底；**注册即登录**（201 + 会话） |

### 流 2：登录（密码 Tab）

| 步 | 服务端动作 |
|---|---|
| 1 | `{identifier, password}`；**标识判定＝含 `@` 按邮箱（小写归一）、否则按 username（小写归一）**——字符集设计（§2.1）保证零歧义；单查询 `WHERE email=$1 OR username=$1 AND deleted_at IS NULL` |
| 2 | 查无 / 密码不符 / 账户已删 ⇒ **统一 401「邮箱/账号或密码不正确」**（不区分三种原因，防枚举）；`scrypt` 校验用 `timingSafeEqual` |
| 3 | 成功 ⇒ **会话固定防护：无视请求携带的任何既有 Cookie，新建会话行（新 uuid）+ 签新令牌 + `Set-Cookie` 覆盖**——登录永不复用入站 sid（攻击者预置的会话在登录后即因 sid 不同而失效）；失败不建行 |

### 流 3：登录（验证码 Tab）

发码（`purpose:'login'`，标识含 `@` 用邮箱、否则先按 username 解析出邮箱再发信——API 侧恒回 200 不回传解析结果）→ `POST /auth/cloud/login {identifier, code}`（与流 2 同端点，互斥通道）→ 核码（同流 1 步 3 核码规则，独立 purpose 独立 attempts）→ 同流 2 步 3（新会话 + 轮换）。

### 流 4：会话续期（滑动窗口，写放大受控）

每请求经 `resolveSession`（云端分支）：验签通过 → 查 `sessions` 行 → `revoked_at` 非空或 `expires_at < now` ⇒ 401；否则返回上下文。**续期写**：当 `expires_at - now < 15 天`（半衰点）⇒ `UPDATE expires_at = now + 30 天` 并重发 `Set-Cookie`（`maxAge` 同步顺延）；`last_seen_at` 更新节流 5 分钟。**绝对上界不存在**——活跃会话永续，30 天不活跃必然过期；吊销即时生效（行状态为权威，令牌 `exp` 只做前置快拒）。

### 流 5：登出 / 吊销

| 触发 | 动作 |
|---|---|
| 登出（账号设置分区按钮，**直接执行无确认**，§9-B9） | 当前会话行 `revoked_at=now` + `Set-Cookie` 清除（`maxAge=0`）；幂等：重复登出仍 200 |
| 改密码成功 | **吊销该用户其余全部会话**（`id <> 当前 sid`），当前会话保留（§9-B6 改后会话策略） |
| 重置密码成功 | **吊销该用户全部会话（含当前）** + 清 Cookie → 完成态引导登录 |
| 改邮箱成功 | 吊销其余会话，当前保留 |
| 账户删除落库（批 1 调用） | `revokeAllSessions(userId)` 端口（§2.1 跨批接口） |

### 流 6：忘记密码（两步）

步 1 `{email, purpose:'password_reset'}` → 恒 200 + 邮件侧按存在性分流（未注册⇒「如果该邮箱已注册……」提示信，PM 冻结候选文案）；步 2 `{email, code, newPassword}` → 核码 + 密码规则校验 → 更新 `password_hash` → 流 5「重置密码」吊销 → 200 + 完成态「密码已重设」+ 主按钮「去登录」。**已登录态访问本页：允许，不跳转、不拦截**（§9-B8）；重置成功后因全量吊销自然回到未登录态。

### 流 7 / 流 8：改密码 / 改邮箱（已登录，账号设置分区内）

- **改密码** `{currentPassword, newPassword}`：**先验当前密码**（失败统一 401 文案）→ 新密码过规则 → 更新 → 吊销其余会话 → 200 + 安全事件。
- **改邮箱**（双验证，NFR-SEC-009 二次确认）：① `POST /auth/cloud/change-email/code {newEmail}`（验当前密码后发 `purpose:'change_email'` 码至**新**邮箱）→ ② `POST /auth/cloud/change-email {newEmail, code, currentPassword}` → 单事务更新 `email`（小写归一）+ `email_verified_at=now` → 吊销其余会话 → 200 + 安全事件。

### 流 9：`/me` 与 401/403 强制路径（兑现详设 §8.1 L622 预留位）

| 模式 | `GET/PATCH /me` 行为 |
|---|---|
| local（默认） | **逐字节维持现状**：无/坏 Cookie ⇒ `EnsureLocalSessionUseCase` 自动初始化，200 + `Set-Cookie`，不 401（IAM-001 L392） |
| cloud | 无 Cookie / 验签失败 / 行不存在 / `revoked_at` 非空 / 过期 / 用户已删 ⇒ **401 `AUTHENTICATION_REQUIRED`**（L76），**不自动建会话**；前端跳转见 §5.3 |
| cloud，**403 `FORBIDDEN`（L77）落点** | 会话有效但动作被形态/策略禁止的两处：① `POST /auth/local/session` 在 cloud 部署 ⇒ **403**（端点已实现、被开关禁用——区别于 404「未实现」的 FND-005 语义）；② 登录态访问仅本地形态的动作（同族）。跨用户资源访问维持既有 **404 不泄露存在性**约定不变（IAM-003 L413） |

## 5. 交付 4：部署形态开关（验收红线落点＝本节，预审点 2）

### 5.1 判据：环境变量（推荐，非初始化）

新增 `APP_MODE=local｜cloud`，**缺省 `local`**。落 `env.ts` 枚举校验（同 `LOG_LEVEL` 模式），`serverEnv.appMode` 输出。

- **选 env 不选初始化判据的理由**（PD-023 §二 允许二者，此处定其一）：部署形态是**部署期决定**，与 OPS-006「环境变量和密钥分离」同层；初始化判据（如「配了 EMAIL_* 即 cloud」）会造成**配置与行为的隐式耦合**——恰是 `composition-root.ts` L169-173 拒绝 AI 静默降级的同一逻辑。
- **cloud ⇒ 条件必填**：`EMAIL_PROVIDER/EMAIL_API_URL/EMAIL_API_KEY/EMAIL_FROM` 在 `APP_MODE=cloud` 时必填，复用 `AI_API_KEY` 的对象级 refine 先例（env.ts L223-231）；缺配置**装配期失败**（§8.3 分层必填，启动暴露而非首请求暴露）。

### 5.2 门禁实现落点（拍板原文「`EnsureLocalSessionUseCase` 加门」，L100）

**单点收口**：`app/_lib/session-api.ts` `resolveSession`（全端点唯一取用户入口，grep ≥100 处）→ `EnsureLocalSessionUseCase` 构造注入 `mode: 'local'｜'cloud'`（值来自 `serverEnv.appMode`，组合根注入，工厂式对齐 §8.3）：

- `local` 分支：**现逻辑逐字节不动**（`ensure-local-session.ts` L68-96）——自动建会话、不 401；
- `cloud` 分支：**不自动建会话**；走 §3 流 4 校验链，失败抛 `AuthenticationRequiredError`（既有错误类，映射 401 信封），由既有统一错误转换路径出响应（`createApiRouteHandler`），**100+ 端点零逐点改动自动继承红线**；
- `POST /auth/local/session` 在 cloud ⇒ 403（§3 流 9）；
- `app/api/v1/*` 各 route 不改（门在用例与单点助手层，不在每个 handler）。

**实现批次归属**：门禁属批 A **auth 小批**（§6），与认证端点同一 commit 序；不前置到批 1——门未装时 cloud 形态本就不存在，无窗口期风险。

### 5.3 前端 401 处理与深链回跳

- `api-client.ts` 增 **401 分支**：`ApiRequestError(status===401)` ⇒ 抛出后由 `(app)` 根级处理器统一捕获 ⇒ `router.replace('/login?next=' + encodeURIComponent(pathname+search))`；
- **回跳校验**：`next` 必须为同源路径（`^\/(?!\/)`，防开放跳转），不合法回退默认页；
- **不在登录/注册等 `(auth)` 页内触发跳转**（防循环）；
- **同步后台请求（`sync-runtime`）遇 401**：暂停推送（IndexedDB 队列**不清空**），跳转登录；重登录后队列自动续推——登录失败不丢本地待同步写（SRS FR-001 L179「登录失败不丢本地数据」的同步面兑现）；
- local 模式 401 不可达 ⇒ 前端分支零触发，现状行为不变（预审点 2 判据之一）。

### 5.4 本地自用部署不受影响的判据（四条，逐条可验）

1. `APP_MODE` 缺省 `local` ⇒ 未配置环境的开发/CI/本地自用路径**行为与现网逐字节一致**（5.2 local 分支不动）；
2. 现网测试基线（422/339/288/94）**零改动保持全绿**（本单不触 `tests/`；cloud 分支的新测试由测试小批另立）；
3. env 新增变量全部 **optional + 缺省 local** ⇒ 构建、health、styleguide、无 DB 的 check 链不受影响（§8.3 分层必填原则）；
4. `EMAIL_*` 条件必填只在 `APP_MODE=cloud` 触发 ⇒ 本地部署零邮件配置要求。

### 5.5 切换影响（知情项，非待定）

部署形态切换**不自动迁移数据**：本地库与云端库为两套部署事实，本地数据经批 1（OPS-002 导出/导入）**手动导出 → 云端导入**承接——数据不迁移是边界，不是缺陷；提请终审知情。

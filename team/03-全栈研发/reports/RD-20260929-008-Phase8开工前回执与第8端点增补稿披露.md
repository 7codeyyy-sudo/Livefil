### POST `/notification-deliveries/{deliveryId}/attempt`

**触达尝试结果上报**（角色：客户端把一次"前台浏览器通知"尝试的成败事实交回服务端落痕）。承载 PD-20260929-012 拍板 2「Notification **权限失败的记录**」与 NOTIFY-002 第 2/3 项（「发送失败有记录」「重试有上限和退避」）；§16 既有 7 端点均无此写入路径（§16 增补理由，见本报告"背景"）。

**触达边界（与拍板 1 一致）**：仅承载**前台**浏览器通知的尝试结果；关页/后台不触达，本端点不改变该边界。

**作用域**：仅当前用户的 delivery。`deliveryId` 不存在或不属于当前用户 → `NOT_FOUND`（404，**不复用 403**，避免泄露存在性，同 §16 `PATCH/DELETE /notification-rules` 既有口径）。

请求体（**仅两个客户端侧事实字段**）：

```json
{ "outcome": "failed", "errorCode": "NOTIFICATION_PERMISSION_DENIED" }
```

成功一例：

```json
{ "outcome": "sent" }
```

| 字段 | 类型 | 约束 |
|---|---|---|
| `outcome` | enum | 必填；**仅 `sent` / `failed` 两值**（客户端侧事实；`pending` / `cancelled` 非客户端可写） |
| `errorCode` | enum | `outcome="failed"` 时**必填**；取值**限 §4.12.2 既有四值**：`NOTIFICATION_PERMISSION_DENIED` / `NOTIFICATION_UNSUPPORTED` / `NOTIFICATION_CONSTRUCT_FAILED` / `DELIVERY_INTERNAL_ERROR`（**不新增错误码**）。`outcome="sent"` 时**不得出现** |

**不接受的服务端权威字段**（提交即以 `VALIDATION_ERROR` 400 拒绝，**不静默忽略**——同 §16 `level` 只读纪律）：`status` / `attemptCount` / `lastAttemptAt` / `nextRetryAt` / `channel` / `level` / `scheduledFor` / `userId` / `ruleId` 等。

响应（200）回带**服务端权威派生后**的 delivery 态（字段子集同 `GET /notification-deliveries` 单条）：

```json
{
  "data": {
    "deliveryId": "uuid",
    "status": "failed",
    "attemptCount": 1,
    "lastAttemptAt": "2026-09-29T01:00:05Z",
    "errorCode": "NOTIFICATION_PERMISSION_DENIED",
    "nextRetryAt": null
  }
}
```

**服务端派生（写死，权威在服务端）**：

1. `outcome="sent"` → `status="sent"`、`error_code = NULL`、`next_retry_at = NULL`；
2. `outcome="failed"` → `status="failed"`、`error_code` = 提交值（`status="failed" ⇒ error_code IS NOT NULL` 由 §4.12.2 CHECK 兜底）；
3. `attempt_count` **服务端递增 +1**（客户端永不可写）；
4. `last_attempt_at` = 本次上报时刻（**既有列**，服务端写）、`updated_at` 随写更新（§3 公共字段）；
5. `next_retry_at` **仅服务端计算**：
   - **可重试失败**（`NOTIFICATION_CONSTRUCT_FAILED` / `DELIVERY_INTERNAL_ERROR`）且递增后 `attempt_count < maxAttempts(3)` → 退避时刻 = 指数 + jitter（见下）；
   - 递增后 `attempt_count >= 3` → `next_retry_at = NULL`（达上限停止）；
   - **不可重试失败**（`NOTIFICATION_PERMISSION_DENIED` / `NOTIFICATION_UNSUPPORTED`）→ `next_retry_at = NULL`（不对确定性失败重试，同 §16 既有重试纪律）。

**退避常量（含 jitter，兑现冻结文本"指数 + jitter"）**：第 n 次重试延迟 = `30s × 3^(n−1)` 叠加抖动系数 `(0.8 + 0.4 × random())`，即第 1 次约 30s±20%、第 2 次约 90s±20%；`maxAttempts = 3`（含首次）硬上限。常量集中定义于模块内（不散落魔法值）。

**驱动方与权威分野（写死）**：**客户端**按 `nextRetryAt` 调度下一次前台通知尝试并再次上报，**只报事实**（`outcome` + `errorCode`）；**服务端**以 `attempt_count` / `next_retry_at` / 终态判定为**唯一权威**，`maxAttempts=3` 由服务端执行，不接受客户端提交的任何次数或时刻。

**幂等（复用既有纪律，不发明新机制）**：

- 携带 `Idempotency-Key`（§1.1）→ 经 `idempotency_keys`（§4.15）识别，重复上报**重放首次结果**并返回 `IDEMPOTENCY_REPLAY`（409），**不二次递增** `attempt_count`；
- **未携带** key → 按每次上报独立计（`attempt_count` 递增），与 §4 `POST /tasks` "未携带 key 时按 POST 自然语义各自独立落库"同款口径。

**错误语义（逐条对 §1.4，零新错误码）**：

| HTTP | code | 触发条件 |
|---:|---|---|
| 400 | `VALIDATION_ERROR` | `outcome` 缺失/非法；`failed` 缺 `errorCode`；`errorCode` 不在四值；`sent` 带 `errorCode`；提交任何服务端权威字段 |
| 404 | `NOT_FOUND` | `deliveryId` 不存在或不属于当前用户（**不复用 403**） |
| 409 | `CONFLICT` | 对**终态行**（`status ∈ {sent, cancelled}`）上报；或对**已达重试上限**的 `failed` 行（`attempt_count >= 3`）再上报 |
| 409 | `IDEMPOTENCY_REPLAY` | 携带 `Idempotency-Key` 的重复上报 |
| 500 | `INTERNAL_ERROR` | 未预期错误 |

**与 `error_code` 四值的关系**（复述，不新立）：`error_code` 是**触达失败原因**，**与 §1.4 的 API 错误码不同源**（RD-20260929-006 预审判定 3），本端点不改变该分野。

## 二、预审条件 4 条补正

### 补正 1（⚠ 计划漏项）：交付物化设计——读时物化 + 三类 `cancelled` 重分类

原 10 个 commit 全是查询/路由/UI，**没有任何环节让 delivery 行诞生** ⇒ `pending` 恒空、NOTIFY-002 无对象。补正如下：

**物化触发＝读时物化（零新端点、契约安全）**：

- **触发点**：`GET /notifications/pending` 读取时（客户端轮询 / 页面聚焦驱动——总监倾向方案，采纳）；
- **扫描**：按索引 `(user_id, enabled, remind_at)` 取该用户 `enabled = true` 的规则，在用户时区下解析 `remind_at`（`time`）与 `repeat_rule`（`none` / `daily` / `weekly`）算出本次应触发时刻 `scheduled_for`（UTC 存储），筛出 `scheduled_for <= now` 且尚未物化者；
- **落行**：`channel="in_app"`、`status="pending"`、`level` 按 `target_type` 派生后**快照**固化、`attempt_count=0`，其余列按 §4.12.2 约束填写；
- **幂等（防重复物化）**：按 `(user_id, rule_id, scheduled_for)` 做**读路径存在性判重**（不先查后插式竞态兜底）。**说明**：§4.12.2 冻结清单为 5 索引 + 2 CHECK，**未含该去重唯一约束**，故本批以读路径判重实现，**不擅自新增唯一索引**；若终审认为需以唯一约束强保证，请裁定后走勘误流程补列索引（这属"超冻结清单"变更，我停手不自行加）。
- **由读路径承载的边界**：扫描窗口与「待触发」判定均在读路径完成；**不新增端点、不新增后台任务**（拍板 2 与"零新端点"同时满足）。

**三类 `cancelled` 重分类（同读路径处置）**——`§4.12.2` 冻结的 `cancelled` 语义＝"**未触达即作废**"：

| # | 触发 | 处置（同读路径） |
|---|---|---|
| 1 | 规则被关闭（`notification_rules.enabled = false`） | 该规则名下**已物化且 `status="pending"`** 的 deliveries → `status="cancelled"` |
| 2 | 全局关闭（`users.reminder_enabled = false`） | 该用户**全部 `status="pending"`** 的 deliveries → `status="cancelled"` |
| 3 | 目标已完成（`task` / `routine` / 对应 `review` 已达成本周期） | 该 `(target_type, target_id)` 名下**未触达的 `status="pending"`** deliveries → `status="cancelled"` |

- 重分类只作用于 **`pending`** 行；`sent` / `failed` 行不动（已触达事实不可改写）；
- `cancelled` 行**不出现在** `GET /notifications/pending`（§16 既有冻结），也不重入面板；
- 重分类与物化在**同一次读路径事务**内完成，先作废后物化，避免"关掉的规则又新落 pending"。

### 补正 2：迁移清单勘正（按 §4.12 原文）

原计划写"4 索引"，按《数据库设计文档》§4.12 原文勘正为 **5 索引 + 2 CHECK**，并补 FK 行为：

- **索引 5 个**：
  - `notification_rules`：`(user_id, target_type, target_id)`、`(user_id, enabled, remind_at)`；
  - `notification_deliveries`：`(user_id, status, scheduled_for)`、`(user_id, scheduled_for)`、**部分索引** `(user_id, next_retry_at) WHERE status = 'failed'`（重试扫描，避免全表）；
- **CHECK 2 个**：
  - `notification_rules`：`target_type = 'review' ⇒ target_id IS NULL`；
  - `notification_deliveries`：`status = 'failed' ⇒ error_code IS NOT NULL`；
- **FK**：`notification_deliveries.rule_id → notification_rules(id)` **`ON DELETE SET NULL`**（规则删除后置 NULL，保留历史留痕，对齐 §4.12.2 与 §16 `DELETE /notification-rules/{ruleId}` 的"交付记录保留"）；两表 `user_id → users(id)`；
- **两表均不设 `version` / `deleted_at`**（不入同步白名单，拍板 2）；
- **回滚/备份说明**（原计划已列 ✓ 保留）：本批为**纯新增两表**，down 迁移＝`DROP TABLE`（无损既有数据）；迁移前**手动备份**（`pg_dump`）列入发布清单，衔接 OPS-001。

## 四、待终审确认的口径（1 条，涉及 doc/04 冻结文本，研发不自改）

**UI §5 B「投递兜底」与接口 §16 `pending` 的**列表口径**可能存在张力**，如实上报：

- UI §5 B L801 原文：「**无论浏览器通知通道成败，提醒条目一律入面板**——面板是准星载体，Notification 发送失败不丢条」；
- 接口 §16 `GET /notifications/pending` 冻结口径：「返回 `status ∈ {pending, failed}` 且未 `dismissed`」。

若采**单行模型**（一条提醒一行，浏览器尝试结果改写该行 `status`：成功→`sent`），则**成功行会离开面板**，与 UI 的"成败一律入面板"字面冲突。两种解读：

- **解读甲（研发倾向）**：UI 该句实质意图＝「**失败不丢条**」（其标题即"投递兜底"、后半句即"发送失败不丢条"）；成功＝浏览器已触达，无需再占面板。**按此解读，§16 与 UI 均不需改动**，单行模型自洽。
- **解读乙**：成功也必须占面板 → 则需 `pending` 列表纳入 `sent` 未 `dismissed` 行，**触及 doc/04 冻结文本与 §16，须总监/终审裁定后走勘误**。

**研发不自行择一**。若总监采纳解读甲并一句话确认，则本项无需流程变更；若采纳解读乙，请裁定后我按勘误流程处置。

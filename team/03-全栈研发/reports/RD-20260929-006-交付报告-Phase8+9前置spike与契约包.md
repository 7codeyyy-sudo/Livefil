## 结论 / 内容

### 一、任务 1：AI provider spike（七要素）

#### 1.1 选型与 provider interface

**结论**：采用「**原生 `fetch` + 项目内 `AiProvider` 端口 + 两个适配器**」——`mock`（默认）与 `openai-compatible`（真实）；**不引入任何第三方 AI SDK**。适配维度取「**协议**」而非「厂商」：OpenAI 兼容的 Chat Completions 已是事实标准（DeepSeek、通义、Kimi、本地 Ollama 均可对接），一个适配器覆盖多供应商。

**接口定义**（与 AI-003「定义 provider interface」对齐；端口置于 `src/modules/ai/domain/ai-provider.ts`，domain 只依赖该接口，不依赖 Next.js 与 `fetch`）：

```ts
/** 调用类型：与接口文档 §11 的四类草稿一一对应。 */
export type AiRequestType =
  | 'task_breakdown'
  | 'schedule_suggestion'
  | 'expense_parse'
  | 'review_summary';

export interface AiCompletionRequest {
  readonly requestType: AiRequestType;
  readonly systemPrompt: string;
  /** 已脱敏的用户内容（见 1.4），不得是原文。 */
  readonly userContent: string;
  readonly maxOutputTokens: number;
  readonly timeoutMs: number;
}

export interface AiCompletionResult {
  readonly content: string;
  readonly provider: string;
  readonly model: string;
  /** 供应商未返回用量时为 null，禁止臆造 0。 */
  readonly inputTokens: number | null;
  readonly outputTokens: number | null;
  /** 金额最小单位整数分；无报价时为 null（跨线口径，见 DB §5.2）。 */
  readonly estimatedCostMinor: number | null;
}

export interface AiProvider {
  readonly name: string;
  complete(request: AiCompletionRequest, ctx: { signal: AbortSignal }): Promise<AiCompletionResult>;
}
```

**理由**：

- **依赖纪律**：事故记录 002 确立「新增依赖须走 npm 官方源 + lockfile 归一化」；1-2 人项目、月度百元预算下，每多一个依赖即多一个供应链与升级变量。
- **需求面窄且固定**（YAGNI）：本批仅四类「文本进、结构化 JSON 出」调用，SDK 的流式、工具调用、多模态、重试中间件能力**全部用不上**；详设 §4.5 的 8 步处理链（检查开关与额度 → 最小必要数据 → 脱敏 → 调用 → 超时/重试 → 校验 JSON → 写草稿 → 用户确认后走普通用例）中，SDK 只在第 4 步提供便利。
- **超时与取消无需依赖**：Node 22 的 `AbortSignal.timeout(ms)` 直接满足详设 §6.2「所有网络调用必须有超时」。
- **数据出境范围**：只发送**用户主动提交的文本或主动选择的对象**（见 1.4），不发用户画像、不发明细清单、不发全量历史。
- **模型档位**：默认取供应商侧**小模型/低档**（拆解与解析的输入输出都短），模型名由 `AI_MODEL` 指定，**不硬编码**。

**影响**：需自建「模型输出 → Zod 二次校验 → 结构化草稿」的校验层（模型可能返回非 JSON 或多余字段）；供应商差异（错误体结构、用量字段命名、鉴权头）由适配器吸收。装配方式对标 `createSessionSigner` 的「**工厂 + 显式注入**」先例：`composition-root.ts` 增 `getAiProvider()`，按 `serverEnv.aiProvider` 选择实现，**装配期**即可暴露配置错误。

**回退方式**：端口隔离——domain 定义 `AiProvider`，infrastructure 提供实现。若后续确需流式或工具调用，或供应商协议适配成本超预期，可换 SDK 实现**同一端口**，用例层与路由层零改动。

#### 1.2 Mock Provider

**结论**：`mock` 为**默认实现**（env 既有 `MOCK_AI_PROVIDER = 'mock'` 即默认值），**确定性、零网络、零密钥**，进默认 `npm run check` 链与 CI；真实 provider **不进**默认链。Mock 为「请求 → 固定结构化响应」的纯函数（按 `requestType` 返回样例 suggestions），并**可注入故障**：`timeout` / `rate_limited` / `unavailable` / `empty`。

**理由**：AI-003 明确要求「建立 Mock Provider」，拍板 5 的风险项亦要求「Mock Provider 保 CI 无 key」（PD-20260929-012 §五.4）；更重要的是——**降级路径必须可测**，否则 `DEPENDENCY_TIMEOUT` / `RATE_LIMITED` / 空结果三条分支永远没有覆盖率（FR-084 末条「处理超时、限流、服务不可用和空结果」）。

**影响**：集成测试经端口注入 fake/mock provider（与「集成测试注 fake 仓储、`check` 链不依赖 PG」的既有惯例同构）；测试可断言「Mock 不写入 `ai_usage` 额度」（见 1.5）。

**回退方式**：无（Mock 是长期资产，非过渡物）。

#### 1.3 超时 / 限流 / 错误结构化

**结论**：全部归一 FND-005（错误类 → `ErrorCode` → HTTP 状态唯一映射，映射源即接口文档 §1.4）；映射表如下：

| 情形 | 错误类（`src/shared/errors/app-error.ts`） | `code` | HTTP | 客户端降级 |
|---|---|---|---|---|
| 调用超时 | `DependencyTimeoutError` | `DEPENDENCY_TIMEOUT` | 504 | 提示稍后重试 + **回退手动录入** |
| 供应商不可用 / 网络失败 / 5xx | `DependencyUnavailableError` | `DEPENDENCY_UNAVAILABLE` | 502 | 同上 |
| 命中月度额度或供应商 429 | `RateLimitError` | `RATE_LIMITED` | 429 | 展示剩余额度与重置时间 |
| 模型输出非合法 JSON / 空结果 | 不抛 5xx；草稿落 `status='failed'` 或 `'expired'`，按 200 返回空 `suggestions` | — | 200 | 空态文案 + 手动录入 |

**策略参数**：

- **超时**：`AI_TIMEOUT_MS`（默认 15000）经 `AbortSignal.timeout`；超时视为 `DependencyTimeoutError`。
- **重试**：仅对「幂等读取或明确可重试」的 5xx/网络错误做**指数退避 + jitter，最多 2 次**（详设 §6.2「最多 2–3 次」取下界）；**429 与 504 不重试**——429 重试会构成重试风暴（详设 §6.2「不能使用无上限的队列和重试」），而超时重试会放大供应商压力；由用户显式重试。
- **不阻塞核心流程**：AI 失败不得阻塞手动录入路径（详设 §6.2「AI、通知和同步失败时不能阻塞手动核心流程」），四条路径均由 UI 提供「手动录入」出口。
- **日志**：落详设 §9 结构化字段的子集——`operation='ai_call'`、`errorCode`、`durationMs`、`provider`、`model`、`inputTokens`/`outputTokens`；**不落 prompt 原文与模型原始输出**。

**缺口如实上报（本单只披露，不落卷）**：详设 §8.2 写明「AI prompt 和用户内容不写入普通日志」，§9 禁止字段清单含「完整 AI prompt」；但 `src/shared/telemetry/redaction.ts` 的 `FORBIDDEN_FIELD_NAME_FRAGMENTS`（L20-31）**不含 `prompt`**——当前 `prompt` 字段只走 `truncateText` 的 **200 字符截断**（`MAX_TEXT_LENGTH`），即保留前 200 字，与「不记录完整 prompt」的**保守方向不一致**。建议 AI-003 实现时将 `prompt`（及 `sanitizedInput` 之外的 `rawInput` 类命名）加入禁止字段清单；因该文件属 FND 侧既有模块、非本单授权目录，**此处仅披露**，请总监决定并入 FND 勘误还是随 AI-003 一并处理。

#### 1.4 脱敏与数据范围（FR-084「提示用户即将发送的数据范围」的实义）

**结论（发什么、去什么）**：

| 调用类型 | 发送内容（**仅用户主动提交或主动选择**） | 不发送 |
|---|---|---|
| `task_breakdown` | 用户输入的原文（经脱敏） | 任务库全量、历史执行记录 |
| `schedule_suggestion` | 用户勾选的任务标题 + 预计时长 + 可用时间窗 | 未勾选任务、他人数据、完整日历 |
| `expense_parse` | 用户输入的原文（经脱敏） | 开销明细清单、账户信息 |
| `review_summary` | 用户主动选择的本周**聚合数**（完成率、时长合计、按币种合计金额） | 复盘自由文本原文、单条开销备注 |

**脱敏规则**（结果落 `ai_drafts.sanitized_input`，**原文不落库**）：

1. 掩码强标识：疑似手机号（11 位连续数字）、邮箱、银行卡/证件号（≥16 位连续数字）、URL 中的 token 查询参数 → 统一掩码；
2. 去控制字符与多余空白，**截断至 `AI_MAX_INPUT_CHARS`（默认 2000 字符）**；
3. 落 `input_hash = sha256(归一化后的 sanitized_input)`——用于同输入去重与审计对账，**不用于反向还原**；
4. 结构化上下文（如 `availableMinutes`）只传数值，不传自由文本。

**`ai_data_consent = false` 的全流程硬阻断路径**：所有 `/ai/**` 端点入口（route → 用例）先读当前用户设置，`aiEnabled !== true || aiDataConsent !== true` 时**在选 provider、发网络请求之前**抛 `ValidationError`：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "未同意数据发送，无法使用 AI 功能",
    "fields": { "aiDataConsent": "开启 AI 时必须同时同意数据发送" }
  }
}
```

**不产生 `ai_usage` 记录、不落 `ai_drafts` 行**（无调用即无账）。跨字段一致性已由 identity 应用层既有 `assertAiConsent` 保证（`aiEnabled ⇒ aiDataConsent`，抛 `ValidationError`）。

**理由**：对齐 FR-084 六条中与本项相关的四条（服务端存密钥 / 提示数据范围 / 支持关闭 AI / 不记录不必要的完整敏感内容）与详设 §4.5 步骤 1-3（检查开关与额度 → 选最小必要数据 → 脱敏）。

**影响**：「提示用户即将发送的数据范围」的**用户可见文案**由 PM 补节 2 承载（PD-20260929-012 §三.2）；研发侧在契约中固定「AI 关闭时返回 **400 `VALIDATION_ERROR`**，而非 403/500」——测试点可直接断言该码与 `fields.aiDataConsent`。

**回退方式**：脱敏规则为纯函数，若实测发现误伤（如掩码过度导致语义丢失），可按规则粒度调整并补用例，不改协议。

#### 1.5 用量与成本上限

**结论**：

- **记账时机**：每次**真实 provider** 调用成功后写一行 `ai_usage`；`mock` **不写入额度占用**（建议 `status='skipped'` 或不落行）——否则本地开发与 CI 会耗尽额度，且 Mock 不产生真实成本。
- **计费口径**：**调用前预检 + 调用后记账**。预检：`当月已用次数 >= AI_MONTHLY_CALL_LIMIT` 或 `当月已用成本 >= AI_MONTHLY_COST_LIMIT_MINOR` → 抛 `RateLimitError`（`RATE_LIMITED`, 429），**不发网络请求**。记账：成功后累加次数与 `estimated_cost_minor`。
- **金额单位**：`estimated_cost_minor` 为**整数分**（DB §5.2 跨线口径）；供应商未报价时为 `null`，**不得以 0 冒充**。
- **额度语义**：`GET /ai/usage` 返回本周期（**自然月，按用户时区**）已用次数、已用成本（整数分）、**剩余额度**＝`limit - used`，以及额度重置时刻；**不返回 prompt**（接口文档 §11 L985 原文「不返回敏感 prompt」）。
- **双层层限流**：除月度额度外，加**短窗口**限流 `AI_RATE_LIMIT_PER_MINUTE`（默认 10）防重试风暴；命中同样走 `RATE_LIMITED`。

**理由**：FR-084 四项（记录调用次数和错误 / 不记录不必要的完整敏感内容 / 每用户每月调用上限 / 处理限流）；接口 §11 `GET /ai/usage` 的「剩余额度」语义需要一条可计算的额度公式支撑，否则该端点无法实现。

**影响**：`ai_usage` 需按 `(user_id, created_at)` 聚合查询（量级小，可直查 count/sum，无需物化）；成本上限依赖「有报价」——无报价时只能靠次数上限兜底，**该取舍如实声明**。

**边界声明（超授权部分只披露）**：`ai_usage` / `ai_drafts` 的字段清单属 DB §4.13（本单授权为 §4.12），§4.13 现状为**无类型的项目符号清单**。若实现中发现需补充字段（如 `error_code`、`request_id`），**不在本单落卷范围**，需另行授权。

#### 1.6 密钥与依赖纪律

**结论**：

**（a）env 分层扩展方案**（沿用 FND-001 / 详设 §8.3 的「根校验 optional，必填下沉使用方」）：

| 变量 | 校验 | 默认 | 说明 |
|---|---|---|---|
| `AI_PROVIDER` | 已有；**建议**枚举化 `mock \| openai-compatible` | `mock` | 非 mock 时要求密钥（既有 refine 保留） |
| `AI_API_KEY` | 已有（非空） | — | 条件必填；**不落库、不进日志** |
| `AI_BASE_URL` | 新增；`https:` 开头 | — | **默认拒绝明文 `http:`**，防密钥与内容明文出网；本机 Ollama 场景需显式开关 `AI_ALLOW_INSECURE_BASE_URL=1`，并在日志留警示 |
| `AI_MODEL` | 新增；非空 | 供应商侧小模型档 | 不硬编码模型名 |
| `AI_TIMEOUT_MS` | 新增；`^\d+$` | 15000 | 非负整数 |
| `AI_MAX_INPUT_CHARS` | 新增；`^\d+$` | 2000 | 脱敏截断长度 |
| `AI_MONTHLY_CALL_LIMIT` | 新增；`^\d+$` | 200 | 每用户每月调用上限 |
| `AI_MONTHLY_COST_LIMIT_MINOR` | 新增；`^\d+$` | 5000 | 每用户每月成本上限（整数分＝50 元） |
| `AI_RATE_LIMIT_PER_MINUTE` | 新增；`^\d+$` | 10 | 短窗口限流 |

全部「提供即校验、不提供不报错」，与 `env.ts` 既有风格一致（含「每个变量只允许一条规则」的既有约定）；`.env.example` 需同步补变量名与说明（**该文件不在本单授权目录，故给方案不落卷**）。

##### §13 提醒与通知

**依赖的口径来源**：SRS FR-070（提醒规则五项）、FR-071（三级通知 + 失败时应用内仍显示待处理）、DB §4.12（状态枚举与失败必记错误码与下次重试时间）、PD-20260929-012 拍板 1（触达边界＝应用内提醒 + **前台**浏览器通知，关页/后台不触达）、拍板 2（`notification_deliveries` 本批＝应用内提醒生成与 Notification 权限失败的记录，渠道限本机，**不入同步白名单**）。

| FR-070 项 | 承载 | 说明 |

###### GET `/notification-rules`

查询参数：`targetType`（可选，`task|routine|review`）、`targetId`（可选，`uuid`）；分页按 §1.3。

```json
{

      "ruleId": "uuid",

      "enabled": true,

      "createdAt": "2026-09-29T01:00:00Z",
      "updatedAt": "2026-09-29T01:00:00Z"
    }
  ],
  "meta": { "requestId": "req_123", "nextCursor": "cursor_value", "hasMore": false }
}
```

（`level` 为**服务端派生、只读**字段，见下 POST 约束。）

###### POST `/notification-rules`

```json
{
  "targetType": "routine",
  "targetId": "uuid",
  "remindAt": "21:30:00",
  "repeatRule": "weekly",
  "allowQuietHours": false
}
```

响应（201）**回带派生等级**（客户端未提交任何等级）：

```json
{
  "data": {
    "ruleId": "uuid",
    "targetType": "routine",
    "targetId": "uuid",
    "remindAt": "21:30:00",
    "repeatRule": "weekly",
    "allowQuietHours": false,
    "enabled": true,
    "level": "critical"
  }
}
```

约束与错误：

- `level` **不接受客户端写入**（**派生、只读**）：请求体不定义该字段，服务端按 `targetType` **派生**——`task` → `normal`、`routine` → `critical`、`review` → `review`——并在创建 / 更新 / 查询响应中**一律回带**；客户端仍提交 `level` 者以 `VALIDATION_ERROR`（400）拒绝，**不做静默忽略**（避免客户端误判等级可配）。派生映射以 **PM 补节 1** 为唯一准据（拍板 6）
- `targetType` ∈ `task|routine|review`；**`review` 类 `targetId` 必须省略**（周复盘提醒不绑定单条实体，服务端落 NULL），`task`/`routine` 必须提供 `targetId` 且归属当前用户——不满足抛 `VALIDATION_ERROR`（400）；
- 同一用户下 `(targetType, targetId, remindAt)` 重复 → `CONFLICT`（409）；
- 提醒时间需与 `users.timezone` 解释，跨时区变更**不自动迁移**已达成的历史交付（如实声明）；
- `remindAt` 格式为 `HH:MM:SS`（与 `users.quiet_hours_start/end` 的 `time` 类型同构）。

###### PATCH `/notification-rules/{ruleId}`

可改字段：`remindAt` / `repeatRule` / `allowQuietHours` / `enabled`（**`level` 不在其列**——服务端派生、只读，见上）。**单条关闭即 `{"enabled": false}`**。不属于当前用户或不存在 → `NOT_FOUND`（404，不复用 403，避免泄露存在性）。

###### DELETE `/notification-rules/{ruleId}`

删除规则；已生成的交付记录**保留**（`deliveries.rule_id` 置 NULL，见 §4.12 字段表）。

###### GET `/notifications/pending`

**FR-071「通知失败时，应用内仍应显示待处理提醒」的载体**。返回当前用户应用内待处理提醒（`status ∈ {pending, failed}` 且未 `dismissed`），按等级降序、`scheduledFor` 升序：

```json
{

    {
      "deliveryId": "uuid",
      "targetType": "task",
      "targetId": "uuid",
      "level": "critical",
      "status": "failed",
      "scheduledFor": "2026-09-29T01:00:00Z",
      "errorCode": "NOTIFICATION_PERMISSION_DENIED",
      "nextRetryAt": null
    }
  ],
  "meta": { "requestId": "req_123", "nextCursor": null, "hasMore": false }
}
```

> **`failed` 也必须在列表内**——这正是「通知失败不降级为不可见」的语义落点；`cancelled` 与已 `dismissed` 不出现在本列表。

###### POST `/notifications/{deliveryId}/dismiss`

用户「已处理」出口，写 `dismissed_at`；**不改 `status`**（§4.12 状态枚举保持四值不变）。重复 dismiss 幂等（200）。

###### GET `/notification-deliveries`

失败与重试查询。参数：`status`（可选，`pending|sent|failed|cancelled`）、`onlyRetryable`（可选布尔）、`cursor`、`limit`。

```json
{
  "data": [
    {
      "deliveryId": "uuid",
      "ruleId": "uuid",
      "targetType": "task",
      "targetId": "uuid",
      "channel": "browser",
      "level": "normal",
      "status": "failed",
      "scheduledFor": "2026-09-29T01:00:00Z",
      "attemptCount": 2,
      "lastAttemptAt": "2026-09-29T01:00:05Z",
      "errorCode": "NOTIFICATION_CONSTRUCT_FAILED",
      "nextRetryAt": "2026-09-29T01:00:35Z",
      "dismissedAt": null,
      "createdAt": "2026-09-29T01:00:00Z"
    }
  ],
  "meta": { "requestId": "req_123", "nextCursor": null, "hasMore": false }
}
```

**重试口径（对 §4.12「不在无上限情况下重试」）**：

- `attemptCount` 上限 `maxAttempts = 3`（含首次）；
- 退避：指数 + jitter（如 30s → 90s → 停止），`nextRetryAt` 即下次尝试时刻；
- **可重试**仅限瞬时失败（构造异常等）→ 未达上限时写 `nextRetryAt`；
- **不可重试**：`NOTIFICATION_PERMISSION_DENIED`（权限被拒）与 `NOTIFICATION_UNSUPPORTED`（浏览器不支持）→ **`nextRetryAt = null`，不再重试**（实测证据见 §2.3：denied 与 unsupported 分支的失败是**确定性的**，重试无意义）；
- 「不重复轰炸用户」（NOTIFY-002 第 4 项）：**等级与去重窗口由 PM 补节 1 冻结**（拍板 6），本契约只提供 `level` 字段与 `(user_id, target_type, target_id, scheduled_for)` 聚合所需的键，**规则本身不在接口层实现**。

##### 4.12.1 `notification_rules`

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | `uuid` | PK |
| `user_id` | `uuid` | FK users，NOT NULL |
| `target_type` | `varchar(16)` | NOT NULL，`task` / `routine` / `review` |
| `target_id` | `uuid` | 可空；`task`/`routine` 必填，`review` 必须为 NULL（周复盘提醒不绑定实体） |

| `repeat_rule` | `varchar(16)` | NOT NULL，默认 `none`；`none` / `daily` / `weekly` |
| `allow_quiet_hours` | `boolean` | NOT NULL，默认 false |
| `enabled` | `boolean` | NOT NULL，默认 true（单条关闭＝false，FR-070 第 4 项） |
| `level` | `varchar(16)` | NOT NULL；**派生、只读**——服务端按 `target_type` 派生后写入（`task` → `normal`、`routine` → `critical`、`review` → `review`），**客户端不可写**；取值 `critical` / `normal` / `review`（FR-071 三级）。等级映射与去重规则以 **PM 补节 1** 为唯一准据（拍板 6） |

- 约束（建议以 CHECK 固化）：`target_type='review' ⇒ target_id IS NULL`。

- **不设 `version` / `deleted_at`**：**不入同步白名单**（拍板 2），无跨端并发与墓碑需求。

- 约束（建议以 CHECK 固化）：`status='failed' ⇒ error_code IS NOT NULL`。
- **`cancelled` 语义**（不扩枚举下的消歧）：因规则被关闭（`enabled=false`）、全局关闭（`reminderEnabled=false`）或目标已完成后而**未触达即作废**；与「用户已处理」（`dismissed_at` 非空、`status='sent'`）显式区分。
- **`error_code` 取值建议**（触达失败原因枚举，**与 §1.4 API 错误码不同源**）：`NOTIFICATION_PERMISSION_DENIED` / `NOTIFICATION_UNSUPPORTED` / `NOTIFICATION_CONSTRUCT_FAILED` / `DELIVERY_INTERNAL_ERROR`。**是否与 §1.4 错误码同源，列为本报告待裁定项（§四.3）**。

|---|---|---|---|---|

**三结论**：

1. **三分支行为确定性成立**：`granted` 下构造成功且**在 headed 真机可真正展示**（`onshow`）；`denied` 与 `unsupported` 下**必然失败**——`unsupported` 连构造都不发生（`typeof Notification === 'undefined'`），`denied` 则构造成功但立即 `onerror`。**应用内降级路径在三种情形下均可用**（`guardOnInApp` 三处均返回正常文本，A1/A3/A4 场景均验证）。这与拍板 2「失败主语＝应用内提醒生成 + Notification 权限失败降级」精确对应。
2. **「关页/后台不触达」的机制可用且已被验证**：B1 显示 **Playwright 环境下 `visibilityState` 恒为 `visible`**（Playwright 阻止页面被节流，故**真实后台态在本环境无法复现**——如实声明，不伪造）；因此以 B2 做**机制级**验证：门控入口在 `hidden` 时**直接跳过、不构造通知**（`eventsAfterHidden` 未增加），回到前台后恢复构造。B3 进一步说明**无 Service Worker 即无后台通道**（`swRegistrations=0`），页面关闭后不存在任何可触达路径——与拍板 1「SW/后台推送维持挂账」一致。
3. **方法论要点（供后续测试交接）**：**headless 下无法证明「通知可展示」**——即使 `permission='granted'` 且 `constructed=true`，事件恒为 `error`（无通知展示器）；「前台浏览器通知可展示」的实证**必须在 headed 下取**。另：Playwright 默认会**自动拒绝**权限提示（headed 下 `requestPermission()` 返回 `'denied'`），故「用户拒绝」分支可直接用默认上下文复现，无需 CDP 干预。

**与拍板 1 口径的自洽性**：拍板 1 声明本批触达上限＝「应用内提醒 + **前台**浏览器通知，关页/后台不触达」。实测恰好划出该上限的两条边界——**上界**（headed + granted 下浏览器通知真实弹出）与**下界**（无 SW、页面不可见即不发通知、权限被拒/不支持时降级为应用内），故拍板 1 的口径**既未高估也未低估**本批能力。

## 结论 / 内容

### S1 IndexedDB 封装选型

**结论**：采用**原生 IndexedDB + 项目内薄封装**（提供 `LocalStore` 端口），**不引入 `idb` / `Dexie` 依赖**。

**理由**：

- **依赖纪律**：新增第三方依赖须走 lockfile 官方源纪律（事故记录 002）；Phase 5 已裁剪范围，多一个依赖即多一个变量。`idb`（Promise 包装、体积小）与 `Dexie`（查询 DSL、能力最强、体积最大）的便利，在「3 个 store、固定访问模式」下收益有限。
- **需求面窄且固定**：详设 §5.1 仅需 `entity_snapshots` / `pending_operations` / `sync_cursor` 三个 store，访问模式为「按 `(entityType, entityId)` 读写」「按 `status` 扫待同步队列」「单行游标读写」，原生 API 足够。
- **事务语义可控**：原生提供 `readonly`/`readwrite` 事务与自动提交；薄封装可强制「一次读改写在同一事务内完成」。**这是选型最需显式约束的点**——原生 IndexedDB 事务在 `await` 非 IDB 请求（`fetch`、`setTimeout` 等）后会**自动提交**，此后继续发 IDB 请求会抛错。三种方案都必须面对，薄封装把它收敛成一条可测规则。
- **schema 升级路径**：原生 `onupgradeneeded` + 整数 `version`，集中在一个迁移函数里按版本逐级升级，可用 fake 实现断言「vN → vN+1 的迁移序列」。
- **与 React 19 并发特性的兼容**：IndexedDB 是浏览器异步 API，**不参与 React 渲染路径**，三种方案在此点等价——选型不构成 React 兼容性差异。约束统一：不在 render 阶段读写、不把 IDB 请求对象放进 state，改由事件/effect 驱动并经 `useSyncExternalStore` 订阅。

**影响**：需自建薄封装（3 store CRUD + 迁移 + 事务助手）；单测须注入 fake `LocalStore`（现有 jsdom 无 IndexedDB，与「集成测试注 fake 仓储」惯例同构）；真机行为（事务/升级/配额）只能由 Playwright 覆盖；架构断言需扩展为「页面不得直接访问 `indexedDB`」。

**回退方式**：端口隔离——domain 定义 `LocalStore` 接口、infrastructure 提供实现；若薄封装复杂度超预期，可换 `idb`（语义最接近原生、迁移成本最低）或 `Dexie`，用例层与页面零改动。

### S2 增量拉取游标机制

**结论**：采用 **per-entity 变更时刻扫描 + keyset 复合游标 + 服务端安全滞后窗口**，**不新增 change-log 表**。游标为 `(changeAt, id)`，其中 `changeAt = coalesce(updated_at, created_at)`。

**理由**：

- **游标必须复合 `id`**：`updated_at` 由应用侧 `new Date()`（`$onUpdate`）生成，同一毫秒可重复，单列不构成全序；按 `(changeAt, id)` 升序 keyset 分页才能不重不漏。
- **同刻并发写入的漏读（关键）**：PG 行在事务**提交后**才可见，而 `changeAt` 是**语句执行时刻**。若事务 A 在 T1 取时刻、T2 才提交，事务 B 取到更晚时刻且在 T2 前提交，则拉取方先拉到 B 并把游标推到 B 的时刻；A 提交后其 `changeAt = T1` 已落在游标之后 → **A 永远拉不到**。解法：pull 只返回 `changeAt <= now() - lag`（`lag` 默认 5 秒，可配），前提 `lag > 最长写事务时长`。代价是变更最多延迟 `lag` 秒可见（单用户多设备可接受）。**这是本方案唯一的正确性前提**，实现中必须落为查询条件并有测试覆盖。
- **墓碑传递（逐类覆盖，无需新增墓碑表）**：现网各表删除形态分四类——① 软删（`deleted_at`：`life_areas`/`goals`/`actions`/`tasks`/`routines`/`routine_steps`/`fixed_commitments`）软删即 UPDATE，`changeAt` 随之前进，行自然在流内；② 状态取消（`schedule_blocks.status = cancelled`）同为 UPDATE 语义；③ 追加式不可删（`execution_logs`，无 `updated_at` 也无删除路径）以 `created_at` 作变更时刻；④ **级联硬删存在墓碑缺口**（`routine_steps` 随 `routines` 级联、外键 `onDelete: cascade`），客户端按「父级墓碑级联清理本地子行」处理。`users` 不设 `deleted_at`、不参与本批；`idempotency_keys`/`sync_conflicts` 为服务端内部表，不进 pull 结果。
- **为何最小方案够用**：单用户、单写入端场景变更量小；change-log 表带来「写入路径双写 + 表膨胀 + 清理策略」三项长期成本，而它解决的「全局单调游标」问题用 keyset + 安全滞后已可解决。

**影响**：pull 需跨表 UNION（按 `entity_type` 分组）统一排序，`limit ≤ 100`；keyset 扫描需 `(user_id, changeAt, id)` 索引（`tasks` 已有，其余在 Phase 5 迁移中评估）；客户端 `sync_cursor` 存 `(changeAt, id)` 而非单值；**所有写路径（含软删、取消）必须经 Drizzle `update()` 使 `changeAt` 前进**，绕过 `$onUpdate` 的原生 SQL 更新会造成漏读。

**回退方式**：若验收中出现「滞后窗口仍漏读」或跨表 UNION 性能不达标，升级为 change-log 表（`change_events(user_id, entity_type, entity_id, change_at, seq)`，写入路径同事务双写），pull 只扫单表、游标退化为单调 `seq`。该回退**不改变客户端协议**（游标仍是不透明字符串），故可后置决策——这也是选择最小方案的理由之一。

### S3 push 幂等整合与命名消歧

**结论**：

- 幂等判定的**唯一落点 = `idempotency_keys`**（DB §4.15）：`key = "sync:" + operationId`，`request_hash = sha256(entityType | entityId | operationType | payload)`。`sync:` 声明为**保留前缀**。
- **服务端 `outbox_operations`（DB §4.14）Phase 5 不落地**（定义保留）。`sync_conflicts` 照常落地。
- **命名消歧**：客户端 IndexedDB 结构（详设 §5.1）`outbox_operations` **改称 `pending_operations`**；服务端表保留原名。
- **`already_applied` 与 409 的关系**：批量 push **不**沿用「同 key 已完成 → 整体 `409 IDEMPOTENCY_REPLAY`」的单请求语义（否则一条已处理会让整批失败）；改为**逐条返回** `applied | already_applied | conflict | rejected`，HTTP 整体 200。命中 `idempotency_keys.completed` 且指纹相同 → 该条 `already_applied` 并回放 `response_snapshot`；指纹不同 → 该条 `rejected`（`VALIDATION_ERROR`）。每条 operation 独立占位/完成，**单条失败不回滚整批**。

**理由**：`idempotency_keys` 已在 Phase 3 落地（唯一约束 `(user_id, key)` + processing/completed + 响应快照），复用它零新增表、零新增并发语义；而服务端 outbox 若并存，会出现「两处都能判定是否已处理」的双真相源，与 DB §4.15 原文「与 outbox 的幂等列不重复」的原则冲突。

**影响**：需在接口文档声明 `sync:` 保留前缀；需设计「逐条幂等」的事务边界（单条失败不回滚整批）；接口文档 §12 补齐逐条响应字段表与状态枚举（已落 §12.1.1）。

**回退方式**：若后续需要服务端操作审计/自动重试，再启用 DB §4.14 的 `outbox_operations`，写入路径为 push 成功后的同事务记录；幂等判定仍在 `idempotency_keys`，故**不改变客户端协议**。

### S4 离线白屏边界实测

**环境**：Windows / Chromium（Playwright 1.63.0 内置）/ `next start` 生产构建 @ `127.0.0.1:3211` / **无 Service Worker**（实测 `navigator.serviceWorker.getRegistrations().length = 0`、`caches.keys().length = 0`）。headless 与 headed 各测一轮，headed 记录「用户所见」。探针经 `context.setOffline(true)` 模拟断网。

**步骤与现象**：

| 步骤 | 现象 |
|---|---|
| A0 在线加载 `/today` | HTTP 200，DOM 完整渲染 |
| A1 断网·同页 | **DOM 完整保留**，客户端上下文存活（探针标记未丢）；应用**自动出现离线提示条**「当前处于离线状态，显示的内容可能不是最新」 |
| A2 断网·脚本 | 客户端脚本仍可执行（DOM 变更生效） |
| A3 断网·API | `fetch('/api/v1/today')` → `TypeError: Failed to fetch` |
| A4 断网·软导航 | 点击侧栏「收件箱」→ **软导航成功**（URL 变为 `/inbox`，页面正常渲染），数据区显示「收件箱没能加载」 |
| A5 断网·新路由载荷 | `fetch('/goals?_rsc=...')` → `TypeError: Failed to fetch` → **未预取路由无法软导航** |
| B1 断网·刷新 | `net::ERR_INTERNET_DISCONNECTED`，落到 `chrome-error://chromewebdata/`；**有头实测为 Chromium 原生错误页**（恐龙图标 +「按空格键即可开始游戏」+ 网络检查建议 + `ERR_INTERNET_DISCONNECTED`） |
| B2 断网·新标签 | 同上，`chrome-error://chromewebdata/` |
| C1 恢复网络 | HTTP 200，恢复正常 |

**结论**：

1. **无 SW 时，离线边界的形态是「浏览器原生错误页」，不是应用白屏**。刷新/重开时导航请求未到达服务器，应用层没有渲染机会，因此**应用无法提供任何离线兜底文案**（`chrome-error://` 属浏览器 UI，不受页面控制）。
2. **SYNC-002 的验收口径「已打开页面断网续用」成立，且只能按此口径验收**；「刷新/重开页面离线可用」在无 SW 前提下**不可能达成**，须明确排除在验收范围外。
3. **「续用」的准确含义**：DOM 与客户端脚本存活、离线提示条出现、**已预取路由可软导航**；但数据不可用（API 全 reject）、未预取路由不可达。即「已渲染内容可见 + 可切到已预取页面 + 不崩溃」，**不是「可继续读写数据」**——离线读写依赖本批 `pending_operations` 队列，属 SYNC-002/003 实现目标。
4. 附带实测：数据层不可用（本次环境 Docker 未运行、本机无 PG，`/api/v1/today` 返回 500）时，页面渲染的是**应用级错误态**（「数据没能取回来。可以先重试。」+ 重试按钮），**不是白屏**。

**页面级提示文案建议**（供 PD-20260923-002 任务 1 对齐）：

- 离线（已打开页面）：沿用「当前处于离线状态，显示的内容可能不是最新」，建议补充可操作信息 →「当前处于离线状态，显示的内容可能不是最新；你的修改会先保存在本机，联网后自动同步」；
- 待同步计数：「N 项修改待同步」，可展开列表；
- 离线刷新/重开的说明（**无法在页面内实现**，只能置于帮助文档或首次进入提示）：「离线时请勿刷新或关闭页面，重新打开需要网络」；
- 恢复网络：「已恢复联网，正在同步 N 项修改」→ 完成后「已同步」。

**影响**：SYNC-002 的 e2e 用例须写成「已打开页面断网 → 断言 DOM 未变、离线提示条出现、已预取路由可切换」，**不得**写成「断网刷新后仍可用」；`context.setOffline(true)` 已验证可作 e2e 夹具；不引入 SW 相关实现，本结论不改变本批范围。

**回退方式**：无（纯观测结论）。若后续 Phase 10 引入 SW 壳缓存，B1/B2 边界将改变（SW 可拦截导航返回缓存壳），届时须重测并更新 SYNC-002 验收口径——本结论适用前提是「无 SW」。

**环境限制（如实声明）**：本次实测环境**数据层不可用**（Docker 未运行、本机无 PG），故「断网续用」在**有真实数据**时的表现（如已加载列表是否仍可滚动查看）未验证，A1/A4 观测到的是「已渲染错误态 + 离线提示条」。这不影响 B1/B2（浏览器层，与数据无关）与 A2/A3/A5 的结论；「有数据时的续用体验」建议在 Phase 5 聚合开发的有 DB 环境补测。

### 偏差与待裁定项（请预审重点看）

**S3 的「服务端 `outbox_operations` 不落地」是对已冻结文本的实现范围收窄**，非新增表。分发单要求「若结论指向必须新增服务端表或与既有冻结契约冲突，停止并上报，不得擅自定案」，故此处**主动上报请总监裁定**：

- **事实**：DB §4.14 定义了 `outbox_operations`（未标注迁移批次），其列与 `idempotency_keys` 在「是否已处理」判定上职责重叠，而 DB §4.15 原文已写明「与 outbox 的幂等列不重复」。
- **我的结论**：Phase 5 不落地该表，幂等唯一落点 `idempotency_keys`；该表定义保留待后续。
- **若总监认为必须落地**：回退方式已在 §4.18.2 给出——在 push 成功路径同事务写入该表作为服务端审计，幂等判定仍留在 `idempotency_keys`，不构成客户端协议变更。请裁定采用哪一种。
- 另：本次**未新增任何服务端表**（未采用 change-log），故不触发「必须新增表」的停止条件。

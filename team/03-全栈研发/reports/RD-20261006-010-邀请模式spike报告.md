## 2. 背景与范围

Phase 8（Gate C，2026-10-05 宣告）+ Phase 9（Gate D，2026-10-06 宣告）双门闭合，PD-20260929-016 转正式。Phase 10 的结构性待决＝**邀请模式**（PD-016 §三 L29-39）：PD-016 §八 风险 1 判定「邀请模式决策错 = 最大返工面」（高），故本 spike 先行，拍板先于任何 OPS-006/007 代码。

### 2.1 冲突的定义

- **SRS FR-001（L166-179）**：系统应支持①本地单用户模式（无需登录）②测试账号模式（登录后云端保存和同步）；「**推荐先实现本地模式，再根据邀请测试决定是否启用云端账户和同步**」。
- **SRS L792 勘误**：多设备同步已以「本地单用户 × 多设备同步」口径纳入 Phase 5 交付；**云端账号（邀请账号、认证、跨用户隔离）继续挂账**，仍维持 FR-001 推荐路径。
- **OPS-007（doc/06 L1142-1150）**：邀请 **5–20 名外部测试用户**，须提供测试说明与隐私说明、记录激活/7 日/4 周留存。
- **PD-016 §三 L34**：OPS-007 邀请外部用户进入「**无认证的本地单用户部署**」＝所有受邀者共享同一用户数据——**PD-001 风险 4 早预警此隐私敞口**。

**这就是鸡生蛋矛盾**：FR-001 说「先本地、由邀请测试决定是否上云端」，而邀请测试本身（OPS-007）一旦落到「无认证的本地单用户部署」就把 5–20 名互不相识的外部用户的数据混在同一账号里；若要先建云端账号（甲案）来隔离，又违背了 FR-001 的推荐顺序。

### 2.2 三案定义（PD-016 §三 L35-38）

| 案 | 定义 | 一句话 |
|---|---|---|
| **甲** | 解锁云端账号批次（IAM-004 挂账的邀请码 / 认证 / 跨用户隔离落地） | 最正统、工程量最大 |
| **乙** | 每受邀者独立实例（容器 / 子域 per-user 部署，本地模式复制） | 零产品认证代码，运维与成本换安全 |
| **丙** | 最小认证层（邀请链接 token + 单点登录态，不做完整云端） | 介于两者，须 SRS 对照与安全评审 |

### 2.3 Gate E 判据与交付边界

doc/06 §14 L1178-1182：Gate E 必须完成 OPS-001~007，判据为「数据可备份恢复，权限和性能达到 SRS 目标，才能邀请外部用户」。本报告只做**只读评估**，不改任何契约文档、不落产品码（护栏 1），结论供 PD-016 预审与终审拍板。

## 4. 甲案拆解（解锁云端账号批次）

### 4.1 四层量级拆解

**（1）schema 层**（现状事实：`drizzle/schema.ts` 21 表，**无 accounts / invitations / sessions**——与 doc/05 §4.1~§4.18 表清单一致）

| 对象 | 现状 | 甲案需解锁 |
|---|---|---|
| `users` | 已有（doc/05 §4.1 L67-92）：`email` citext/可选唯一、`mode` local/cloud、**无 `deleted_at`**（注释：账户删除随 data-management 批次补） | 加列：`password_hash`（或 magic-link 免密）、`email_verified_at`、`deleted_at`；`mode` 启用 `cloud` |
| `invitations` | **不存在** | 新表：`code`（唯一、带熵）、`email`、`status`、`expires_at`、`accepted_at`、`invited_by`、公共字段 |
| `sessions` | **不存在**（详设 §8.1 L620 明示「本批不建 sessions 表，云端会话形态随云端批次重定」） | 新表：`user_id`、`token_hash`、`expires_at`、`revoked_at`、`device_label`（可吊销 + 多设备） |
| 辅助 | — | 视方案增：`magic_link_tokens` / `password_reset_tokens` / `email_outbox` |

**（2）端点层**（现状：`app/api/v1/auth/local/session/route.ts` 单端点 + `app/api/v1/me/route.ts`）

需新增/改造：邀请校验与激活、登录（或魔法链接请求/校验）、登出（会话吊销）、会话刷新、`/me` 在云端模式的 401/403 强制路径（详设 §8.1 L621 明言「401/403 的强制路径按云端批次实现，本批只保留接口与代码位置」）。

**（3）UI 层**：邀请落地页、激活页、登录页、「云端模式」标识（详设 §8.1 L622 要求 `/me` 与设置页可见模式）、账号设置分区。PD-016 §六 L69 已预判「（若甲/丙）账号与邀请码全套形态——**量级等同一次 UI-008**」。

**（4）测试层**：认证/会话/邀请码端点测试、**真实跨用户隔离测试（A 不访问 B）**（挂账 9 明文「甲/丙必测」）、401/403 分场景、邀请码生命周期。IAM-004（doc/06 L395）已为云端挂账预留结构并明文「本地单用户环境无法真机验证；预留测试结构，不写永远通过的假用例」——甲案正是要把它填实。

### 4.2 是否需要再拆批

**需要**。预判 3–4 批，与 doc/06 §13 批次粒度对齐：

1. **DB 批**：`invitations` / `sessions` + `users` 加列迁移（对标 DB-001 形态）；
2. **auth 批**：认证端点、邀请码校验、会话签发/吊销、`/me` 强制路径（对标 IAM-001/002）；
3. **UI 批**：邀请/激活/登录/账号设置（量级 ≈ UI-008）；
4. **测试批**：跨用户隔离 + 401/403 + 邀请码流程（对标 IAM-004 云端补测）。

即甲案整体 ≈ 一个完整 Phase 的工作量，**不宜并入 Phase 10 的 OPS 批**。

### 4.3 鸡生蛋矛盾解法

FR-001 的顺序（先本地 → 邀请测试 → 决定云端）与甲案的前置性（先云端 → 才能邀请）互斥。三个解法：

| 解法 | 内容 | 代价 |
|---|---|---|
| **A. 顺序重排**（不推荐） | 直接拍甲，把云端作为邀请测试前置，SRS FR-001 推荐路径作废或改写 | 违反 FR-001 推荐路径 + 触碰 L792 挂账注记；**不先用真实测试数据就投入最大工程量＝正撞 PD-016 §八 风险 1** |
| **B. 分两轮邀请**（推荐） | 第一轮邀请用**无云端账号的形态**（乙或丙）跑通 OPS-007；用真实留存/反馈数据回答「是否需要云端账号」；需要才另起批次做甲 | 需先接受第一轮用乙/丙，即甲**后置为邀请测试的产物**而非前置 |
| **C. 改写口径** | 把 FR-001 的「由邀请测试决定是否启用云端」重新解释为「邀请测试**期间**用最小可用形态收集数据，测试后拍板是否升级为甲」 | 需 SRS 口径确认（FR-001 与 L792 均为冻结文本，改动须走规范升版） |

**本报告倾向 B**：它同时满足 FR-001 顺序、L662 本地优先、PD-016 风险 1（先拿数据再决定）、风险 4（第一轮即隔离），且把甲案的正确性建立在真实用户数据而非预判上。

## 5. 乙案（每受邀者独立实例）

### 5.1 零认证代码的运维复杂度量化

乙案的产品代码**零改动**是真实优势：现网 `session-signer.ts` 的 HMAC 无状态本地会话无需改，`EnsureLocalSessionUseCase` 照常自动建本地用户，无 `sessions` 表、无认证端点、无账号 UI。

但「零认证」**不等于零访问控制**。必须显式指出这一缺口：

- 每用户一个实例/子域，若子域可枚举（如 `user1.example.com`），则 A 可访问 B 的实例——**这是乙案把认证问题从产品层下移到基础设施层，并未消除**（PD-016 §八 风险 2「无认证部署对外开放 = 数据暴露」在此案仍成立，只是敞口从「共享数据」变为「可枚举实例」）。
- 补齐手段（三选一或组合）：① 高熵不可猜子域/路径（安全靠隐蔽，**弱**，仅可作纵深防御的一层）；② 反向代理层访问门（HTTP Basic / 签名 URL / 一次性激活链接）；③ 网关按会话路由。
- 因此乙案的**运维复杂度清单**（不含实现，仅列面）：

| 面 | 复杂度 |
|---|---|
| 实例模板与编排 | 1 套镜像 + N 份实例定义（容器或 VM）；需自动化 provisioning 脚本 |
| 实例路由 | 反代/子域映射；路由表随用户增减维护 |
| 访问隔离 | 见上——需在反代/网关补一层门（否则风险 4 未解） |
| 备份 | N 份实例各自备份，或中心化脚本遍历；NFR-BACKUP-003「每月恢复演练」× N |
| 升级/回滚 | 版本发布须逐实例滚动；N 实例 = N 份回滚面 |
| 密钥 | 每实例 `AUTH_SECRET` / DB 凭据独立（NFR-SEC-002）；N 份密钥轮换 |
| 观测 | N 实例日志聚合（OPS-006 观测四项 × N） |
| 成本 | 见 5.2 |

**结论**：乙案把「认证/隔离的代码复杂度」换成「编排/备份/路由的运维复杂度」；一次性建脚本后边际成本低，但**每次版本升级与恢复演练的成本随 N 线性增长**——这是乙案的长期代价，非一次性投入。

## 6. 丙案（最小认证层）

### 6.1 SRS 对照：何种程度触碰「云端账户」定义

- **FR-001（L166-173）模式②**原文：「测试账号模式：用户登录后进行**云端保存和同步**」。
- **丙案提供的**：邀请链接 token 换取单点登录态 + 数据落**共享云端 DB**（多租户同库、按 `user_id` 隔离）→ **具备「登录」与「云端保存」**。
- **丙案不提供的**：多设备**同步**（Phase 5 已单独交付，不属丙）、账号自管（改密/改邮箱/注销）、密码/账号体系、账号级多设备会话管理。
- **判定**：丙案落在**模式②的退化形态**——有登录与云保存、无同步与账号自管。它**触碰「云端账户」定义的核心（云端保存 + 需认证访问）**，但不覆盖 SRS 对模式②「和同步」的完整表述。
- **需 SRS 口径确认的事项**：① 是否允许「仅云保存、不同步、无账号自管」作为模式②的过渡形态；② 若丙案落地，L792「云端账号继续挂账」的注记是否需加注「丙案为邀请期最小实现」。两处均为冻结文本，任何改动须走规范升版，**本 spike 不代改**（护栏 1）。

### 7.1 账号/邀请表 schema 解锁量（三案差异）

| 对象 | 甲 | 乙 | 丙 |

### 7.2 NFR-BACKUP-001 与本地 DB 的张力 · 各案解法

**张力原文**：NFR-BACKUP-001（SRS L559）要求「**云端数据库**至少每日自动备份」RPO≤24h；NFR-BACKUP-006（L564）要求「**本地模式**明确提示用户定期导出/备份」。当前形态是本地 DB，**无云端库**——故 NFR-BACKUP-001 在当前形态下**无适用对象**，NFR-BACKUP-006 才是现行义务。PD-016 §五 L62 已标注此矛盾（「若坚持本地 DB 则与『云端备份』矛盾，须云 DB 或托管服务」）。

| 案 | 解法 | 落点 |
|---|---|---|
| 甲 | 共享**托管云 PG**（或自建 PG + cron `pg_dump`）→ NFR-BACKUP-001 直接适用；备份 1 份 + 每月 1 次演练 | OPS-001 正身 |
| 乙 | 每实例仍是**本地 DB**（无云端库）→ NFR-BACKUP-001 严格说仍不适用，**但运行方仍须保证可恢复**：中心化脚本遍历 N 实例备份 → 演变为 1 套「自建云端备份」；演练 × N | 需在 OPS-001 显式定义「多实例备份口径」——**SRS 未覆盖，属新增运维面** |
| 丙 | 同甲（共享云 PG），但需额外按 `user_id` 验证备份/恢复后的隔离未被破坏 | OPS-001 + OPS-003 交叉 |

**关键提示**：乙案会让「备份」从 SRS 的「云端库每日备份」变成「N 份本地库的中心化备份」，是**一条新的、SRS 未定义的运维契约**——须在 OPS-001 契约前置时显式补口径，否则 Gate E 的「数据可备份恢复」判据在乙案下无验收对象。

### 7.3 通知云端渠道（挂账 5）与邮件通道的耦合度

| 案 | 是否需要邮件通道 | 与挂账 5 的耦合 |
|---|---|---|
| 甲 | **强耦合**：邀请投递、邮箱验证、可能的通知邮件都需要 | 挂账 5「通知云端渠道」与邮件**一并定**，形成一封新的运维/成本/安全面 |
| 乙 | **无耦合**：每用户独立 URL，可由运行方**手工分发**激活链接 | 挂账 5 维**维持挂账**；通知仍走本地/应用内 |
| 丙 | **弱耦合、可解耦**：邀请链接可**手工分发**（复制粘贴给受邀者），无需邮件基础设施 | 若坚持邮件投递则耦合，若接受手工分发则**挂账 5 维持挂账** |

**读数**：邮件通道是甲案的**硬依赖**，对乙案是**不需要**，对丙案是**可回避的软依赖**。这一条直接影响成本（邮件服务）与安全面（邮件通道安全），是模式选择的隐性权重项。

## 8. 结论

### 8.1 推荐排序

**首选：乙（容器化单宿主，per-user 实例）**

理由：① **产品代码零改动**——现网 HMAC 本地会话、`EnsureLocalSessionUseCase`、21 表 schema 全部不动，**返工面最小**（直接对冲 PD-016 §八 风险 1）；② **SRS 顺序天然相容**——乙即「本地单用户模式」的物理复制，`FR-001` 推荐路径、L662「本地优先」均不触碰；③ **风险 4 被结构性解决**——每用户独立实例，数据物理隔离；④ **成本可控**（**前提是采用容器化单宿主**：2C2G 40 元/月承载 ≈5 用户、4C8G 230 元/月承载 15–25 容器，落在 SRS §7.2 预算量级）；⑤ **不引入邮件通道**，挂账 5 维持挂账。
**代价（必须正视）**：运维复杂度上升（编排/路由/备份/升级 × N）与**访问控制需求下移**——须在反代/网关补一层门，否则可枚举实例仍造成数据暴露；且乙案引入一条 SRS 未定义的「多实例备份口径」（§7.2），须在 OPS-001 契约前置补写。

**次选：丙（最小认证层）**

理由：① 单实例多租户，**成本最低**（40 元/月，落在预算内）；② 工程量级适中（≈0.3–0.5 Phase）；③ 安全面集中、可枚举（§6.2 十二项清单），评审负担明确；④ 邮件通道**可解耦**（手工分发激活链接）。
**代价**：① 触碰「云端账户」定义（FR-001 模式②退化形态），**需 SRS 口径确认**（§6.1）；② 引入认证代码 = **返工面显著高于乙**（若后续拍甲则部分废弃、若最终不要云端则全废）；③ 须完成 §8.2 安全评审。

**后置：甲（解锁云端账号批次）**

定位＝**邀请测试的决策产物，而非前置**——即 FR-001 里那个「由邀请测试决定是否启用」的对象。**不建议在 Phase 10 内落地**：工程量 ≈ 一个完整 Phase（须再拆 3–4 批）、顺序冲突（鸡生蛋，§4.3）、返工面最大。若终审拍甲，则按 §4.3 解法 B（分两轮邀请）先跑一轮乙/丙，用真实数据支撑甲的范围裁剪。

### 8.2 若拍甲/丙，批 3 前必须完成的安全评审项

以下为**必须完成**项（非建议项），对应 OPS-003「安全检查」（doc/06 L1099-1107）任务面，且直接覆盖挂账 9「真实跨用户隔离测试」：

1. **token 生命周期与吊销策略定案**（含会话轮换防会话固定）；
2. **跨用户隔离实现口径 + 真机测试**：A 不访问 B（含 IDOR 用例），服务端 `user_id` 级校验（NFR-SEC-003/004）；——挂账 9 在此闭环；
3. **HTTPS/TLS 全站部署 + Cookie 安全属性**（HttpOnly/Secure/SameSite，NFR-SEC-001，详设 §8.1 L619）；
4. **邀请码/链接熵与速率限制**（防枚举与暴力扫描）；
5. **日志脱敏复核**：token、邮箱、邀请码不入日志（NFR-SEC-005，详设 §8.2 L631）；
6. **导出/删除路径**在认证形态下的落点（BR-007 / NFR-BACKUP-005）；
7. **备份与恢复演练**（NFR-BACKUP-001/002/003）在共享云库形态下落地，并验证恢复后隔离完好；
8. **邮件通道安全边界**（若甲案启用邮件投递则必做；丙案若手工分发可豁免）。

> 若拍**乙**，评审项 3/4/5/6/7 的**运维侧等价物**同样必须完成（HTTPS、实例路由门的熵与限流、日志脱敏、导出路径、N 实例备份演练），并须在 OPS-001 契约前置补写「多实例备份口径」（§7.2）——乙案不豁免安全评审，只是把评审对象从「认证代码」换成「编排与网关」。

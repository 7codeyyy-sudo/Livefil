## 结论 / 内容

### 一、核心判断：Phase 5 的正确口径是"本地单用户 × 多设备同步"，云端账号继续挂账

三条依据一脉相承：

1. **SRS 优先级定位**："云端账号和多设备同步"在 SRS §10.2 属 **P1（第一阶段可加入）**，不在 §10.1 P0 清单；SRS FR-001 明示"推荐先实现本地模式，再根据邀请测试决定是否启用云端账户和同步"。
2. **Phase 2 冻结决策**：云端模式（账号、认证、邮件、跨用户隔离）整体挂账，本次无新事实需要解冻。
3. **当前架构事实**：PostgreSQL 已经是唯一主数据源（DB-001），REST API-first 已成立（tasks/goals/schedule_blocks 等端点已交付），version 乐观并发已在写路径生效——所谓"云端仓储"的地基已经在了。本地模式的"本地"指**无账号体系**，不是数据在浏览器本地。

关键推论：**本地单用户 ≠ 单设备**。服务端只有唯一用户，任何设备（浏览器/PWA）经自动本地会话访问的都是同一份数据——这正是 SYNC-005 跨设备验收的前提，且不需要账号体系即可成立。因此 Phase 5 的实际交付物是：**同步链路（push/pull/冲突）+ 客户端离线层（IndexedDB 快照与 outbox）+ 待同步/冲突 UI**，而不是"云端化改造"。

### 三、需要产品经理补充的需求（契约冻结先行，必须在开发前完成）

1. **待同步状态 UI 形态**：UI 规范 v0.14 §4.7 冻结版明确"不做「N 条待同步」、发件箱、全部重试"，并言明该形态依赖尚不存在的 sync 模块。现在 sync 模块进入开发，产品需补充：待同步计数/入口放哪里（建议复用 §4.7 离线横幅容器做状态扩展，但这是产品决定）、是否提供手动同步、同步失败的重试文案与分级。
2. **冲突解决 UI 形态**：SYNC-004 的 keep_server/keep_local/manual_merge 三选目前只有接口契约，UI 规范无任何冲突解决界面设计（弹窗/列表/字段级 diff 均未定义）。需产品给出最小形态（建议 P0 只做"整条保留服务器/保留本地"二选 + 放弃标记，manual_merge 顺延，理由见风险节）。
3. **本地会话多设备语义确认**：当前本地会话为服务端签发 Cookie 指向唯一用户，多设备天然共享同一用户数据。产品需确认这符合"个人使用"定位预期（无账号、任何人可访问部署地址即进入同一数据空间），并决定是否在设置页对"多设备访问同一数据"给出提示文案（涉及 SRS §12 隐私边界的知情要求）。

### 四、需要研发做技术 spike 的事项（进开发计划前先给结论）

1. **IndexedDB 封装选型**：详设 §5.1 只定数据结构未定实现（原生 IndexedDB / idb / Dexie）。立项书 §7.2 提过"IndexedDB/Dexie 或等价方案"。spike 结论需覆盖：事务语义、schema 升级路径、与 React 18/19 并发特性的兼容，以及是否引入新依赖的 lockfile 纪律（npm 官方源，见事故记录 002）。
2. **增量拉取游标机制**：接口 §12 只定义"返回自游标之后的变更"，服务端实现机制未定（per-entity `updated_at` 扫描 vs 统一 change-log 表）。单用户场景建议评估"每实体 `updated_at` + 游标单调性保证"的最小方案（需处理同刻并发写入与墓碑），**不预造 change-log 表**，spike 给出结论后同步 DB 设计文档勘误。
3. **push 重放与现有幂等键的整合**：Phase 3 的 `idempotency_keys` 覆盖单请求幂等（key + request_hash 指纹）；sync push 是批量操作信封，spike 需明确 operationId（客户端 UUID）与服务端 `already_applied` 判定如何落在这张表或 `outbox_operations` 服务端表上，二者职责不得重叠（DB 设计 §4.15 已有"与 outbox 的幂等列不重复"原则，需落到实现）。
4. **离线白屏边界实测**：无 Service Worker 时，给出"已打开页面断网续用 / 刷新后离线白屏"的实测结论与文案提示方案，作为 SYNC-002 验收口径输入（与待决项 2 联动）。
